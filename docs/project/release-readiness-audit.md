## 2. Executive conclusion

ACN's `0.3.73` build has no confirmed release-blocking defect. The full automated gate — format, lint, strict type-check, build, 2,992 unit/component tests, and 230 end-to-end tests — passed cleanly both in a fresh local reproduction (under a slightly older, non-equivalent local toolchain) and in the corresponding GitHub Actions run for this exact commit. `npm audit`'s production-dependency scan reports zero known advisories against the six direct runtime dependencies actually shipped in the browser bundle. The application's own security-relevant plumbing — GPX parsing, the geometry-digest-bound `<acn:navigation>`/`<acn:planning>` extensions, the OpenRouteService API key's storage and transport, error redaction, and DOM-injection surfaces — was traced end to end and found deliberately, consistently defensive, with dedicated tests proving the load-bearing claims (a geometry-digest mismatch rejects the whole envelope; an exported name containing `&"<` round-trips through re-parsing without breaking the XML; the API key is never appended to a URL and is stripped from error text before it can reach Diagnostics).

The audit did find five known advisories in transitive **development-only** dependencies (`brace-expansion`, `fast-uri`, `nanoid`, `postcss`, `undici` — all pulled in by ESLint, Vite/PostCSS, `vite-plugin-pwa`'s Workbox tooling, or jsdom, none reachable in the shipped bundle), a handful of CI/supply-chain hardening gaps typical of a single-maintainer static-site pipeline (GitHub Actions pinned to major-version tags rather than immutable SHAs, no CSP, no repository-owned Dependabot/CodeQL), and one genuine, evidence-backed maintainability signal worth acting on before it compounds further: `src/App.tsx`, the file that now hosts the route-switch/unfinished-session coordinator, is simultaneously the most recently hot-churned production file in the repository (15 of its 19 all-time commit touches landed in the last ~90 commits) and the least-covered one (79.78% statement coverage against a 93.53% project average), with the coverage gap concentrated almost exactly in that coordinator's own failure/retry branches.

None of this amounts to "insecure," "unstable," or "not production ready" in an unqualified sense, and none of it should be read that way. It also does not amount to "fully secure" or "fully tested" — this audit is not a penetration test, a formal threat-model certification, or an accessibility conformance certification, and several categories of evidence (GitHub repository settings, raw CI log text, physical Android hardware, sustained real-ride battery behaviour) were not observable from this environment and are recorded as such below, not guessed at.

## 7. Verified strengths and non-findings

All of the following were directly inspected on the live `f8c38b9e` baseline, not assumed:

- **Zero production-dependency advisories.** `npm audit --omit=dev` reports zero vulnerabilities across all 32 resolved production package-tree entries. ACN's own direct runtime dependency list is small and auditable: `@turf/helpers`, `@turf/nearest-point-on-line`, `dexie`, `maplibre-gl`, `react`, `react-dom` — six packages, all mainstream and actively maintained.
- **No DOM-injection surface exists.** A full-tree grep for `dangerouslySetInnerHTML`, `innerHTML =`, `document.write`, `eval(`, and `new Function(` across `src/` returns zero hits. All rendering goes through JSX/React children and typed props; no template-literal HTML construction pattern exists anywhere.
- **The routing-provider API key is never placed in a URL.** It is attached exclusively as an `Authorization` request header (`src/routing/openRouteServiceAdapter.ts`), with an explicit comment recording that choice, and it is provably stripped from any surfaced error text: `sanitiseTransportErrorMessage`/`redactSensitiveSubstrings` (`src/routing/sanitiseErrorMessage.ts`) removes an exact match of the live key plus any URL query/fragment, and — separately — the general Diagnostics error log (`src/platform/errorLog.ts`) redacts coordinate-shaped and 20+ character token-shaped substrings from every logged error, independent of the routing-specific redaction. Provider HTTP error bodies are never forwarded to the UI; only a fixed, numeric ORS error code is read.
- **The `<acn:navigation>`/`<acn:planning>` GPX extensions are geometry-digest-bound and fail closed.** `src/gpx/parseAcnExtension.ts` independently recomputes a SHA-256 digest over the imported track geometry and rejects the entire manoeuvre/waypoint envelope — never a partial list — on any mismatch, version disagreement, out-of-range index, or non-monotonic distance. A dedicated boundary test (`parseAcnExtension.test.ts`) proves the `MAX_ACN_MANOEUVRES = 10,000` cap is enforced by construction, not merely documented.
- **GPX export is a real XML serializer, proven safe against structural injection.** `src/gpx/exportGpx.ts` builds the document via `createElementNS`/`.textContent =`/`XMLSerializer`, never string concatenation, and `exportGpx.test.ts` exports a route literally named `Loop & "Climb" <fast>`, re-parses the output, and asserts zero parser errors and an exact round trip.
- **No straight-line substitution exists for a failed routing leg.** `stitchPlannedRouteLegs` throws rather than drawing a connector on a seam mismatch, and Planning's route hook explicitly documents retaining the previous successful route on a failed recalculation — both matching this project's long-standing rule.
- **No lifecycle history/telemetry, and the redaction discipline is uniform.** No `console.*` call anywhere in `src/` references the API key (grepped exhaustively); Diagnostics only ever derives a boolean `hasKey`.
- **The camera-command dedup and overview-suppression mechanisms CLAUDE.md documents are genuinely present in current source**, not just described historically: the plain monotonic `nextCameraRequestIdRef` counter in `useRideCamera.ts` (confirmed not a timestamp or UUID), and the `hasActionableCameraTarget` latch with exactly the reset condition CLAUDE.md describes. A characterization test (`RidingScreen.test.tsx`) explicitly documents and asserts convergence for the known item-66 same-commit race, corroborating that item's existing "accepted for now, monitored" status — this audit found no new evidence changing that disposition.
- **Route-projection continuity and off-route classification have dedicated, correctly-scoped tests.** `projection.test.ts` has separately named self-intersection and out-and-back continuity cases (not conflated); `offRoute.test.ts` directly asserts the `CONSECUTIVE_TO_ESCALATE = 3` repeated-evidence requirement before a strong warning.

## 9. CI and supply-chain analysis

ACN has exactly one GitHub Actions workflow, `.github/workflows/deploy-pages.yml`, triggered on `push` to `main` and `workflow_dispatch` only (no `pull_request` trigger — consistent with this repository's observed single-maintainer, direct-to-`main` commit pattern rather than a PR-review workflow; not itself a defect, but worth naming, since it means the "verify"/"e2e" jobs gate _deployment_, not merge into `main`). Three jobs: `verify` (format/lint/typecheck/test/build), `e2e` (Playwright in a pinned container), `deploy` (`needs: [verify, e2e]`). `permissions: {contents: read, pages: write, id-token: write}` is scoped narrowly — no broader `write` access is requested. `concurrency: {group: pages, cancel-in-progress: false}` serialises deployments rather than racing them.

**Positive findings, confirmed by direct inspection of the file:** both jobs independently re-verify the exact pinned Node/npm versions with a hard `exit 1` on drift (this is the same check this audit's own local environment would have failed, proving the check is real); the `e2e` job separately verifies `playwright-core`'s resolved version matches the container image tag, explicitly to catch the two ever drifting apart; the production build is stamped with `APP_BUILD_SHA: ${{ github.sha }}`, tying the deployed artefact to a specific commit.

**Hardening gaps (F-2), evaluated for proportionality rather than copied from a generic checklist:** all five `uses:` action references (`actions/checkout@v7`, `actions/setup-node@v7`, `actions/configure-pages@v6`, `actions/upload-pages-artifact@v5`, `actions/deploy-pages@v5`) are pinned to major-version tags, which GitHub allows the publisher to move; the Playwright container is pinned to the tag `v1.61.1-noble`, not an image digest, which a registry-level tag reassignment could in principle change under a maintainer's feet between runs. Neither is a broken control — GitHub's official actions are widely trusted and the workflow's own version-check step would catch most consequences of an unexpected drift — but pinning to immutable SHAs/digests removes that trust assumption entirely, at the ongoing maintenance cost of a manual bump (or a scoped, reviewed automation) whenever a new action version is wanted. No repository-owned Dependabot, CodeQL, or dependency-audit workflow exists; this is an absence, not a broken feature, and any future addition needs a defined triage step (this project's own dependency-remediation discipline — supported-parent-upgrade preference, full-gate verification, no blind `--force`) rather than becoming an unconditional deployment-blocking gate on every advisory, including unreachable dev-only ones like F-1.

**Not observable with current access:** branch protection rules, required-review settings, secret-scanning/push-protection enablement, and any organisation-level security policy. This audit does not assert these are absent — only that they could not be checked from this environment.

## 10. Application security and privacy threat review

**Scope reminder:** ACN is a static, client-only, GitHub Pages-hosted PWA with no server, no accounts, and no cloud database. The threat model below is scoped to that reality — it does not include a remote attacker with server/database access, because none exists.

**Assets traced:** saved/imported routes, planning drafts, active ride/free-roam session state, the locally-stored OpenRouteService API key, preferences/diagnostics, and exported GPX data. All are held exclusively in this origin's IndexedDB (via Dexie); see [§11](#11-data-integrity-and-recovery-analysis) for the storage-layer detail.

**GPX import (`src/gpx/`):** parsed via `DOMParser`, never uploaded. File-level guards: non-empty, ≤20 MiB (`MAX_GPX_FILE_SIZE_BYTES`), `.gpx` extension required. Coordinates and elevations are validated as finite numbers in range per point; any violation throws a typed `GpxParseError` and the import fails outright rather than importing a partially-invalid route. The `<acn:navigation>`/`<acn:planning>` extension parser additionally enforces a manoeuvre cap of 10,000 and a planning-waypoint cap of 300 (both boundary-tested), and rejects the _entire_ extension envelope — never a partial one — on any geometry-digest mismatch, version disagreement, out-of-range index, or non-monotonic distance, degrading to a fixed, non-blocking UI notice while the base route import still succeeds. This is a genuinely fail-closed design for untrusted extension content while remaining fail-open for the base GPX track, matching this project's stated priority that a route must remain usable without trusted manoeuvre data.

**GPX export:** built via `XMLSerializer`/`createElementNS`, proven safe against structural injection by a round-trip test using deliberately hostile characters in a route name (§7). The export filename itself is user-name-derived with no ACN-side sanitisation of path separators or control characters before being assigned to an `<a download>` attribute (F-7) — browsers are relied upon, not ACN's own code, to keep this safe; recorded as an informational, accepted, same-origin-only risk rather than a finding requiring action, since the only party who could supply a hostile route name is the same user exporting it from their own browser.

**Routing-provider request/response handling:** the API key lives in a single Dexie singleton row (`providerKeys`, id `"openrouteservice"`), plaintext (IndexedDB is unencrypted browser storage — see below), attached only via an `Authorization` header, never a query string. HTTP 401/403/429/5xx, network failure, timeout, non-JSON responses, unexpected response shapes, and genuine `AbortSignal` cancellation are each handled distinctly with fixed, generic, redacted messages; the provider's own `error.message` text is never read or forwarded, only a numeric `error.code`. No code path substitutes a straight line for a failed leg (§7).

**Storage-at-rest reality, stated honestly:** the API key and all route/session data sit in ordinary, unencrypted browser IndexedDB storage, readable by any same-origin script. This is not a defect specific to ACN — it is the nature of browser storage, and adding application-level "encryption" using a key the same application also stores would not meaningfully change the trust boundary (same-origin script compromise already has the key either way). The realistic exposure this creates is **disclosure on a lost, shared, or unlocked device** — a different, weaker threat than remote exfiltration, and one no client-only static PWA can fully close without moving key custody outside the browser entirely (which this product's local-first, account-free design deliberately does not do).

**Content-Security-Policy feasibility, investigated but not implemented (F-5, item 90):** ACN currently ships no CSP or related browser policy. A future compatibility investigation would need to account for: MapLibre GL JS's documented requirement of `worker-src 'self'` (`blob:` only becomes necessary if MapLibre were loaded cross-origin from a CDN — ACN bundles it via Vite/npm, so a same-origin worker URL should avoid that requirement, but this needs to be proven against ACN's actual built output, not assumed from general MapLibre documentation); `img-src` allowances for the configured tile source's data/blob/tile responses; whatever `connect-src` the OpenRouteService and tile/style/sprite/glyph hosts require; and Workbox/service-worker allowances for `vite-plugin-pwa`'s generated `sw.js`. GitHub Pages' static hosting means any CSP would most plausibly be delivered via a `<meta http-equiv="Content-Security-Policy">` element rather than a response header — and `frame-ancestors` (and some other directives) cannot be delivered that way at all, a real, documented limitation of the meta-tag delivery mechanism, not an oversight to work around. Absence of a CSP today is a defence-in-depth gap, not evidence of an existing injection vulnerability — none was found (§7) — and item 90 is scoped as an investigation producing a compatibility matrix and fail-first browser evidence, not an implementation.

**Other DOM/URL sinks:** zero `window.open(` calls anywhere in `src/`; both existing `target="_blank"` anchors use `rel="noreferrer"` and point at fixed internal constants (a signup URL, the configured tile attribution URL), never runtime user/GPX/provider input.

## 11. Data integrity and recovery analysis

Dexie schema is at version 4, with three additive-only version bumps (v2, v3, v4 each add new object stores; none has ever needed an `.upgrade()` transform), and `db.migration.test.ts` proves old-shape rows from each earlier version survive being opened by the current schema, plus proves several later-added plain (non-version-bumped) fields default safely when absent from an old-shape row.

Dexie itself performs no schema/type validation on read or write — there is no Zod/io-ts dependency and no route-shape validator, so the `routes` table is trusted as-is. The higher-risk singleton preference/session rows are, however, defensively normalised at read time in `src/storage/mapping.ts`: unrecognised enum-like stored values (ride-session `kind`, routing `profile`, sort order, elevation-view mode) fall back through explicit membership checks to safe defaults rather than being trusted via a bare `??`, and an unrecognised-but-present ride-session `kind` is deliberately turned into a non-resumable `"unsupported"` state offering only discard, rather than silently defaulting to a resumable one. This is a real, load-bearing distinction: corrupt/future-shaped _values_ in known fields fail safe; a _wrong type_ in a field with no explicit guard (e.g. a stored number where a string is expected) would not be caught by any current test or runtime check, since none was found for that specific case.

Active-ride writes are single-row `put`/`delete` operations against one `"active"` singleton, inherently atomic without needing a multi-table transaction. The one genuinely sequential, non-transactional two-write path found is route switching's `confirmPendingSwitch` (`src/App.tsx`): it clears the active ride state, then — for a free-roam target only — separately writes a fresh free-roam row. A crash between those two `await`s leaves the `rideState` table simply empty (no active session), not a mixed or corrupted row, because both operations target the same singleton row; the code already has explicit, user-visible `"clear-failed"`/`"start-free-roam-failed"` retry states for the ordinary (non-crash) failure case. This is judged a bounded, already-reasonably-handled reliability characteristic, not a data-corruption risk — folded into item 91's characterization-test scope rather than raised as its own finding, since it is the same coordinator seam.

The two genuine multi-table Dexie `transaction(...)` calls that do exist in the codebase (`providerKeyRepository.ts`'s save/delete) are exactly where atomicity actually matters most for correctness — preventing a re-saved key from ever inheriting a stale verification outcome.

Storage-health reporting (`useStorageHealth`) is real but shallow: it reports "ok"/"error" purely from whether `db.open()` resolves, with no `navigator.storage.estimate()` quota signal and no live write probe (F-6, item 92) — so "opened successfully but now under quota pressure with writes silently failing" is currently indistinguishable from full health in Diagnostics.

No bulk export/import of the whole route library or settings exists (F-9) — confirmed absent by exhaustive grep, not merely unfound. Given the product's local-only, single-device, explicitly-privacy-first design, and that a route remains individually recoverable via the existing per-route GPX export at any time, this is judged an accepted product constraint rather than a meaningful data-resilience gap warranting a new item — consistent with this audit's instruction not to manufacture a bulk-backup feature out of an informational observation.

## 12. Lifecycle/reliability analysis

The lifecycle mechanisms root `CLAUDE.md` documents as historically fixed were independently traced in current source, not merely assumed still present: the plain monotonic `requestId` counter gating Northwards/Follow-location camera command reapplication; the `hasActionableCameraTarget` latch and its documented reset condition; the `visibilitychange`/`pageshow` handlers that restart the geolocation watch and mark the prior fix stale, but only when a watch was already active (a genuine cold reload starts idle, awaiting an explicit tap); the windowed, self-intersection/out-and-back-aware route projection with dedicated, separately-named tests for each case; and the three-consecutive-fix repeated-evidence requirement before a strong off-route warning escalates (two-fix de-escalation, asymmetric by design).

Route-completion arming (`src/navigation/rideCompletion.ts`) requires genuine departure from the finish, credible interior route-fraction progress, and two consecutive eligible fixes before arming, then a further two consecutive eligible fixes before confirming — a real, multi-stage gate, not a single-fix trigger. `e2e/ridingFinishAndEnd.spec.ts` (497 lines, 5 top-level test cases) exercises it; this audit did not re-investigate item 32's own monitored CPU-contention flake, which remains current-status.md's authoritative record.

The route-switch/unfinished-session coordinator that the most recent commit (item 73's follow-up) touched lives inside `src/App.tsx`, woven through roughly 730 of the file's 1,102 lines rather than isolated in one function — `checkRideTransition`/`requestRouteTransition`/`confirmPendingSwitch`/`retryPendingSwitchCheck`/`handleSwitchTargetMissing` and their supporting state. The underlying classification logic itself (`classifyRideTransition`) is correctly factored out into `src/ui/riding/rideSessionTransition.ts` as a pure, presumably well-tested function — it is specifically the orchestration _around_ that classification, inside `App.tsx`, that is large, low-coverage, and was the most recently and heavily touched (§14, §6 F-3).

Map style fallback (`FALLBACK_STYLE`, a local, tile-free background style in `MapView.tsx`) is real and is exercised by a genuinely distinct test path (`forceMapStyleFailure`, used by 7 E2E specs) from the normal-ready-state path (`installLocalMapStyle`, used by 35 E2E specs) — both routed through the same intercepted style-request pattern, so neither test category can accidentally reach the real tile host.

The service-worker update prompt is real (F-8): `registerType: "prompt"` at the build-config level plus an application-code path that only ever calls `updateServiceWorker` from an explicit user tap, together giving strong structural assurance that an update can never apply itself mid-ride — but no single test currently exercises that specific combination (a `RideSessionKind`-active fixture plus an attempted forced update) end to end, so the guarantee currently rests on two independently-confirmed facts rather than one integrated regression test.

Item 66 (fresh-Start Follow intermittently remaining at overview) was independently corroborated, not reopened: `RidingScreen.test.tsx` contains a test explicitly documenting the exact same-render-commit race current-status.md already describes, and asserts the system still eventually converges to the correct follow command despite a spurious intermediate overview fit — this is additional evidence supporting the existing "accepted for now, monitored" disposition, not a new finding.

## 13. Test, coverage, browser and device analysis

**Inventory:** 167 production TS/TSX files, 31,598 lines, under `src/` (excluding tests and `e2e/`). 146 unit/component test files (63,708 lines) plus 43 E2E spec files (20,552 lines) — 189 test files and 84,260 lines total, roughly 2.7× production code by line count. Playwright is configured with exactly two projects, both Chromium-based: `chromium` (desktop) and `android-chrome` (Pixel 7 emulation, `androidGpxImportExport.spec.ts`-style specs only) — **no WebKit project exists.**

**Coverage baseline, attempted and completed:** `@vitest/coverage-v8` is an installed devDependency with no wired `npm run coverage` script. This audit ran the broad, whole-project coverage baseline directly (`npx vitest run --coverage`) and it **completed successfully in ~51 seconds with all 2,992 tests passing under instrumentation** — the previously-reported instrumentation-overhead issue in `parseAcnExtension.test.ts`'s intentional >10,000-manoeuvre boundary test **did not reproduce on this run**; no timeout was raised and no test was skipped to achieve this. This is reported as a non-reproduction under current conditions, not as proof the earlier observation was wrong — coverage instrumentation overhead is plausibly sensitive to machine load, and this run's environment differs from whatever produced the earlier one. Overall project figures: **93.53% statements, 88.78% branches, 94.81% functions, 95.73% lines** (5,971/6,384 statements). `src/gpx/` itself sits at 99.33% statements/91.12% branches — `parseAcnExtension.ts` specifically at 100% statements/92.52% branches — so the module carrying the most untrusted-input parsing responsibility is very thoroughly exercised.

The two lowest-coverage production modules, both consequential: **`src/App.tsx` at 79.78% statements/74.15% branches** (see §12, §14, F-3) — the uncovered statement lines (353–354, 451, 483–484, 496–497, 503, 535, 558, 565, 575, 594, 615–969 in clusters) concentrate heavily inside the route-switch coordinator's own error/retry branches, including the `"clear-failed"` catch path and the free-roam-write failure path discussed in §11; and **`src/map/mapAdapter.ts` at 54.4% statements/65.57% branches** — plausibly because much of its role is constructing real MapLibre marker DOM elements, work that is inherently more naturally exercised through the E2E suite's real browser than through jsdom unit tests, though this audit did not exhaustively confirm equivalent E2E coverage exists for every uncovered branch. Both are folded into item 89's risk-based-floor scope rather than treated as a blanket-threshold problem.

**Test-environment noise, not silenced:** the unit-test run emits repeated jsdom "Not implemented" warnings for `HTMLCanvasElement.getContext()`, `window.scrollTo()`, and one navigation-to-another-document warning. These are genuine, expected jsdom limitations (no real canvas/layout engine, no navigation) rather than a signal of broken application code; stubbing them purely to quiet the log would risk claiming behaviour the test environment cannot actually provide, so item 89 scopes this as a deliberate, honest triage decision (accept vs. targeted-adapt per warning), not a blanket suppression.

**WebKit feasibility:** not implemented, and this audit did not build a WebKit CI image to test it — recorded as a judgement call for item 89 to make explicitly (MapLibre's WebKit support, CI image/cost tradeoffs, and the fact that even a passing WebKit project would still not reproduce installed-iPhone-Home-Screen-PWA lifecycle behaviour) rather than asserting feasibility either way here.

**Physical-device evidence:** unchanged by this audit. Per `current-status.md`, free-roam bicycle-speed behaviour, several recent map-camera/immersive-shell/wake-lock slices, and physical Android verification remain outstanding — this audit neither closes nor duplicates those entries.

## 14. Architecture and maintainability analysis

The domain/gpx/routing/navigation/storage/pwa/map/ui separation CLAUDE.md prescribes is genuinely present in the source layout, and the seams that matter most for correctness are pure, independently testable functions: route projection, off-route classification, completion arming, gradient/climb detection, and GPX parsing/export all live as provider-independent pure logic with their own dedicated test files, separate from the React components that consume them. `rideSessionTransition.ts`'s pure `classifyRideTransition` function being factored out from `App.tsx`'s orchestration around it (§12) is a concrete example of this pattern working as intended even inside the codebase's most complex remaining coordinator.

**Size and churn, re-measured against the audit's own prior-snapshot leads (all confirmed current, one materially updated):** `MapView.tsx` 2,242 lines, `RidingScreen.tsx` 1,997 lines, `PlanningScreen.tsx` 1,976 lines, `index.css` 2,774 lines — all match the snapshot referenced when this audit was commissioned. **`App.tsx` is now 1,102 lines, not the ~800 previously recorded** — real, continued growth since the item-73 follow-up, not a stale figure being repeated.

All-time git churn (commit touch count) for production files: `RidingScreen.tsx` leads by a wide margin (54 touches, 43 of them in the last ~90 commits alone), followed by `MapView.tsx` (39), `PlanningScreen.tsx` (35), `mapAdapter.ts` (21), `db.ts` (20), `mapping.ts` (19), and `App.tsx` (19 all-time — but 15 of those 19, i.e. the large majority, landed in just the last ~90 commits, meaning `App.tsx` has gone from a quiet file to one of the most actively-changing files in the repository very recently). Combined with §13's coverage finding — `App.tsx` is simultaneously the newest hotspot and the lowest-covered production module in the entire codebase, with the coverage gap sitting almost exactly inside the route-switch coordinator's own failure paths — this is the one architecture finding this audit treats as consequential rather than cosmetic (F-3).

Hook-density spot-check across the four largest files supports treating them as structurally different kinds of complexity, not interchangeable candidates for the same fix: `MapView.tsx` (30 `useEffect`, 30 `useRef`, 0 `useMemo`) is dominated by imperative map-instance lifecycle synchronisation, consistent with its documented role; `RidingScreen.tsx` and `PlanningScreen.tsx` (6 effects each, but 20/33 `useState` and 13/20 `useCallback` respectively) are dominated by screen-level state/orchestration rather than effect chains; `App.tsx` (0 `useEffect`, 0 `useCallback`, 0 `useMemo`, but 8 `useState`/7 `useRef`) concentrates its complexity in plain async handler functions and a state machine rather than effects at all — a materially different shape than the other three, and one this audit did not find an existing characterization-test suite proportionate to.

**This audit recommends against refactoring `App.tsx`'s coordinator right now.** Per this project's own change-discipline rule, a refactor is justified only once a cohesive seam is named and its behaviour is characterised first. §13 already shows exactly which branches of that seam are uncovered; item 91 is scoped to close that specific gap (test-only, zero behaviour change) as the necessary precondition — not to perform the extraction itself, which remains an explicitly separate, not-yet-justified future decision.

Both suspected type-only import cycles were confirmed present and are genuinely mechanical, low-risk fixes (folded into item 89): `mapAdapter.ts` imports value functions from `waypointMarkerElement.ts`, which imports `type { MapMarkerSpec }` back from `mapAdapter.ts`; `MainNavigation.tsx` imports the `NavIcon` component, which imports `type { Screen }` back from `MainNavigation.tsx`. Both are type-only back-edges (no runtime circular-value-import risk), most likely resolved by relocating the shared type into a small third module or the more foundational of the two files.

No refactor of `MapView.tsx`, `RidingScreen.tsx`, `PlanningScreen.tsx`, or `index.css` is recommended by this audit. Each is large, but each also carries a correspondingly large, seemingly proportionate test suite (`MapView.test.tsx` 5,678 lines, `PlanningScreen.test.tsx` 4,409 lines, `RidingScreen.test.tsx` 8,080 lines), and this audit found no evidence — via coverage, churn, or direct reading — that any of the three is currently a defect-prone hotspot in the way `App.tsx` now is.

## 17. Release decision

### Continued `0.3.x` private use

**Appropriate to continue.** No release-blocking defect was found: the full automated gate is green both locally (non-equivalent toolchain) and in CI for this exact commit; production dependencies carry zero known advisories; the application's own security- and privacy-relevant code paths were traced and found consistently defensive with tests backing the load-bearing claims. `0.3.x` remains the right version line while behaviour and storage contracts continue evolving and manual acceptance (per `current-status.md`) remains incomplete — that is expected at this stage, not a defect.

### Proposed `0.4.0` gate

Recommended, evidence-based criteria for a deliberate post-audit hardening milestone:

- **Must fix:** item 87 (dev-dependency remediation) completed with a clean full-gate run and a reviewed, minimal lockfile diff.
- **Must decide/document:** item 88 (CI/supply-chain pinning and Dependabot/CodeQL evaluation) — either implemented or explicitly deferred with a stated reason; item 90 (CSP feasibility) — the compatibility-matrix investigation completed and a decision recorded, even if the decision is "not yet, for the following reason," since a decision either way satisfies this gate, not implementation itself.
- **Recommended before `0.4.0`, not a hard blocker:** item 91 (App.tsx characterization tests) — given F-3 is this audit's only Medium finding and sits in the most recently active part of the codebase, closing its coverage gap before further route-switch changes land is prudent, but does not itself block continued `0.3.x` use.
- **Deferrable to a later milestone:** item 89 (verification-baseline polish) and item 92 (storage-health quota signal) — both genuine, low-risk improvements, neither release-blocking.

### Future `1.0.0` gate

`1.0.0` should mean the owner is willing to treat core route planning, saved-route recovery, active Riding, and update/storage compatibility as a stable product contract for supported devices — it does not require every backlog item or every Low/Informational finding above to be resolved. Beyond the `0.4.0` criteria: item 91 completed (not merely recommended); a decision recorded on item 90's CSP investigation, implemented or explicitly and durably deferred; the outstanding bicycle-speed free-roam field test and the remaining recent map-camera/immersive-shell/wake-lock real-device confirmations from `current-status.md` closed with real evidence, since those bear directly on the core Riding contract `1.0.0` would be certifying; and item 60's battery investigation substantively progressed beyond its current single-ride, hypothesis-level observation. Physical Android verification remaining a documented support limitation — rather than a `1.0.0` blocker — is reasonable **provided ACN does not claim full Android support** at that point; if Android support is ever claimed as equivalent to iOS, physical Android acceptance would need to move from "outstanding" to "confirmed" first.
