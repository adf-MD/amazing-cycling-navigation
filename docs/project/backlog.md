## Item 59 — Elevation and recognised-climb discrepancy investigation

_Category: Riding elevation enhancement_

59. **Elevation and recognised-climb discrepancy investigation**
    - Field observation (unverified against ground truth, not yet a confirmed defect): on one ride, ACN's planned figure was approximately 640 m ascent versus approximately 540 m recorded by a Garmin watch and approximately 510 m reported by Google for a comparable route. Some recognised climb sections subjectively felt like they started later than the physical climb on the road.
    - Confirmed current implementation (recorded here as ground truth for any future analysis, not as an admission of a defect): ascent/descent totals (`src/navigation/elevation.ts`) resample raw route-point elevation at `RESAMPLE_STEP_METRES = 20` m (flat-extrapolating), apply a centred moving-average smoothing window of `SMOOTHING_WINDOW_SAMPLES = 5` samples (~100 m at that spacing), and accumulate with a `MIN_ASCENT_DELTA_METRES = 1` m reversal threshold — this pipeline runs independently of, though sharing constants/helpers with, the gradient/climb-detection pipeline below. Local gradient and climb/descent detection (`src/navigation/gradient.ts`, `src/navigation/routeFeatures.ts`) share the same 20 m resample step and reuse the elevation module's smoothing window; local gradient is fitted by least-squares regression over a `GRADE_BASELINE_WINDOW_METRES = 100` m centred window (minimum usable window `MIN_GRADE_WINDOW_METRES = 40` m near a run's edges), with runs split apart by gaps over `MAX_ELEVATION_GAP_METRES = 500` m and short (`MIN_SEGMENT_LENGTH_METRES = 80` m) classification flicker suppressed. Climb recognition requires length ≥ `MIN_FEATURE_LENGTH_METRES = 500` m, average gradient ≥ `MIN_CLIMB_AVERAGE_GRADIENT_PERCENT = 3` %, and Garmin's own published `climbScore ≥ MIN_CLIMB_SCORE = 1500`; a boundary only confirms once a reversal exceeds `REVERSAL_BRIDGE_ELEVATION_METRES = 10` m or persists past `REVERSAL_BRIDGE_DISTANCE_METRES = 200` m of distance since the tracked extremum (a flat lead-in/plateau within `FLAT_EPSILON_METRES = 0.01` m of the current extremum is treated as neither extending nor reversing). None of the above trusts a provider-supplied ascent/descent summary — ACN always recomputes from route-point elevation itself, per this project's long-standing "do not sum raw positive elevation noise" GPX rule.
    - Treat this strictly as an evidence-gathering investigation, not a confirmed provider-data defect, and not a request to retune any constant above yet.
    - Required investigation before any tuning proposal: compare the exact ACN-exported planned GPX for the ride in question against the corresponding Garmin-recorded GPX/FIT activity, aligned by distance and geography — ask the user to supply both files explicitly for a dedicated future analysis task; keep them local, never commit or retain them, and allow the user to trim privacy-sensitive sections first, per this project's "never commit personal GPX files" rule. Report, from that comparison: route-point spacing in each file, ACN's raw-vs-smoothed elevation profile, ACN's cumulative ascent under the current algorithm above, and exactly where recognised climb boundaries differ from where the rider judged the physical climb to start/end. Treat Garmin and Google's own figures as comparison data points, not ground truth — they may use different elevation sources (barometric vs. digital-elevation-model), their own smoothing, and their own ascent thresholds, none of which ACN can inspect. Get the user to clarify, with a concrete reproducible case, what "later" means for the climb-boundary complaint: the coloured map boundary (`routeFeatureLayer.ts`), the highlighted elevation-chart section, or the automatic active-Climb view's own entry point (`climbElevationView.ts`) — three distinct presentation layers over the same underlying boundary that could diverge from each other even if the boundary itself is correct.
    - Only after that analysis should a separate, later-numbered implementation slice propose any change to smoothing, the reversal threshold, climb-boundary hysteresis, or elevation-source handling — any such proposal must quantify its effect across several representative routes (not just the one ride that prompted this), and add deterministic regression fixtures rather than tuning purely to match one ride's Garmin/Google numbers.

## Item 60 — Battery consumption investigation and possible battery-saving mode

_Category: Battery and performance investigation_

60. **Battery consumption investigation and possible battery-saving mode**
    - Field observation (hypothesis-level, not a confirmed cause): an approximately two-hour installed iPhone PWA route ride saw battery fall from roughly 90% to below 20%. A separate, approximately ten-minute walking free-roam test (already recorded under item 42's own manual-acceptance entry) showed no obvious heat or battery drain, but was too short to validate representative endurance.
    - Record contributing factors as hypotheses only, not conclusions: high screen brightness/keeping the display awake; the app's current light presentation, particularly on an OLED device; continuous high-accuracy `watchPosition` use; MapLibre rendering and camera-update/easing frequency; cellular tile downloads, weak signal, or other device/environmental conditions; device model, battery health, and ambient temperature. A PWA cannot directly control hardware screen brightness; browser geolocation has no dependable application-controlled update interval; and the project must not trade away navigation reliability merely to claim better battery life.
    - Stage the work, and do not conflate the stages:
      1. **Measurement and diagnosis:** define a repeatable 60–120 minute real-device test procedure recording phone model, iOS version, battery health, system appearance, approximate brightness, wake-lock use, active screen, signal conditions, start/end battery percentage, perceived heat, and route/free-roam mode. Any opt-in developer diagnostics added for this must not retain location/speed history and must not become analytics/telemetry, per this project's explicit non-goals.
      2. **Low-risk rendering audit:** inspect for unnecessary React rerenders, MapLibre repaint/camera-easing frequency, hidden/off-screen chart or map work, and network tile churn. Require a measured, reproducible issue before changing anything found here.
      3. **Possible battery-saving presentation, gated on evidence from stages 1–2:** consider a manually selectable dark/OLED-friendly active-Riding theme and a compatible dark/dim map style, preserving outdoor contrast, route/warning colours, attribution/licensing requirements, and accessibility. A dark UI alone does not address GPS/rendering cost or a bright map style, and must not be described as a proven fix by itself.
      4. **Higher-risk power changes, gated on comparative field evidence only:** do not lower GPS accuracy, weaken manoeuvre timing, degrade Follow reliability, or silently disable wake lock. Any such option must be explicit, reversible, off by default, and tested against navigation accuracy as well as battery use before being offered.
    - Keep the investigation (stages 1–2) and any eventual feature (stages 3–4) as clearly separate future slices, each with its own acceptance evidence — do not implement stage 3/4 work on the strength of the single two-hour ride reported here.

## Item 61 — Android GPX share-sheet import feasibility

_Category: Platform compatibility_

61. **Android GPX share-sheet import feasibility**
    - Field observation: on Android, opening a GPX file received through WhatsApp currently offers only `Open with` choices (no ability to save to Files first), and the installed ACN PWA is not offered as an option there.
    - Platform distinction (re-verify against current official documentation before acting on it, since browser capability support changes over time): the web File Handling API (which can register a PWA as a file's default handler for an `Open with` chooser) is documented by Chrome as desktop-only today — it is not expected to make an installed Android PWA appear in an `Open with .gpx` chooser. The Web Share Target API is a distinct mechanism that can let an installed Android PWA appear as a target in a genuine Android Share/Send sheet — this depends on WhatsApp/Android actually exposing a Share/Send action for the received file, which is unconfirmed for this exact flow. A static GitHub Pages PWA can potentially implement a Web Share Target through its manifest plus service-worker/Workbox request handling, without an application server — this remains to be prototyped, not assumed to already work. This cannot make ACN appear in an `Open with`-only chooser under any of the above; it only helps if a genuine Share/Send path exists for this file. Useful, but not yet re-verified, official starting points: <https://developer.chrome.com/docs/capabilities/web-apis/file-handling>, <https://web.dev/web-share-target>, <https://web.dev/articles/workbox-share-targets> — check current status before relying on any detail from them.
    - Confirmed repository state: no Web Share Target, File Handling API, `share_target`/`file_handlers` manifest field, or related service-worker route exists anywhere in the current codebase (confirmed by an exhaustive case-insensitive grep). This is a fresh feasibility item, not a partially-built feature.
    - Stage the work, gated at each step:
      1. **Real-device flow capture and feasibility:** obtain screenshots or a screen recording of the exact WhatsApp menu/chooser on the user's real Android device, plus Android/Chrome/WhatsApp version numbers, to determine whether a genuine Share/Send path exists at all. Record the result as real-device evidence, distinct from any later Chromium-emulated Playwright coverage.
      2. **Static prototype, only if step 1 finds a Share path:** prove an installed Android PWA can register as a file share target under the project's current Vite PWA/Workbox configuration and GitHub Pages base-path deployment, covering both app-closed and app-already-open invocation.
      3. **Local GPX import integration, only if step 2 succeeds:** accept `.gpx` and realistic MIME types via the share target, validate through the existing file-size/XML/coordinate/import pipeline unchanged, never upload the file anywhere, and show a clear foreground review/confirmation or error state. Any service-worker handoff buffering the shared file must be short-lived and must not retain personal GPX data indefinitely.
      4. **Conflict and recovery coverage:** an inbound share must respect the existing unfinished route/free-roam conflict guard (item 42's fail-closed `checkFreeRoamConflict`-style pattern) and must never silently replace an active session or Planning draft; it must work after a fresh install/relaunch. Add Playwright coverage where meaningful, then require real Android Chrome acceptance — Chromium/Playwright emulation cannot prove real OS share-sheet registration, matching this project's existing, repeatedly-stated distinction between the `android-chrome` Playwright project and genuine physical-device verification (item 25).
    - If step 1 finds only an `Open with` path and no Share/Send path, document that conclusively and record that no pure static-PWA solution is currently available for this exact flow — do not propose a native wrapper, Trusted Web Activity, APK, or other Android-specific packaging as a workaround; that would be a major architecture departure and is explicitly not approved by this backlog item.
    - Requires the "## Explicit non-goals" edit recorded above (item 61's own cross-reference) — that section stays in the root `CLAUDE.md` and already carries this cross-reference.

## Item 100 — Reusable route tags and tag-based organisation

_Category: Route Library organisation_

100. **Reusable route tags and tag-based organisation**
     - Confirmed current state: no tag or folder concept exists anywhere in the codebase (`src/domain`, `src/storage`, `src/ui`) — this is genuinely new work, not an extension of a partially-built feature.
     - Use user-facing **tags**, not exclusive folders. A saved route may naturally belong to several concepts, such as `commute`, `gravel` and `weekend`.
     - When editing a route's tags, offer existing tags as suggestions and allow a new tag to be created without leaving the editor.
     - Specify deterministic normalisation for whitespace, empty values, duplicates and case. Preserve one stable display spelling while preventing accidental case-only duplicates.
     - Existing routes migrate safely to an empty tag collection. No route becomes hidden or inaccessible after the migration.
     - Initial tags are local ACN library metadata. Do not silently alter GPX import/export or place tags inside the geometry-digest-bound `<acn:navigation>` GPX extension without a separately reviewed format/version decision.
     - This is approved staged implementation work, not a feasibility study — stage the delivery so each slice ships independently, rather than an unreviewable vertical expansion in one commit. Later stages depend on the tag foundation earlier stages build, not on a feasibility gate:
       1. **Data model and storage:** inspect migration implications and the compact phone editor's interaction pattern, then add the backward-compatible storage schema/migration for an empty-by-default tag collection per route.
       2. **Tag editing:** add reusable-tag suggestions and new-tag creation in the route editor, built on stage 1's storage.
       3. **Filtering and organisation:** add tag filtering and a useful organisation view without duplicating a multi-tag route confusingly across many sections, built on stage 2's tag data.
       4. **Full lifecycle and acceptance:** add tag editing, deletion/rename and empty-state coverage plus real-device acceptance for the complete feature.
     - Prefer filtering and tag chips before inventing nested folders. If a later grouped presentation is proposed, mock up how multi-tag routes appear before implementation.
     - Preserve search, pinning, sorting (including item 99's new fields once delivered), import/export privacy, storage migrations and route-switch behaviour. Adding a third-party taxonomy or cloud synchronisation is out of scope.
     - **Stage 1 progress (8 September 2026): data model and storage foundation shipped, no UI.** Added `tags?: string[]` to `PlannedRoute` (`src/domain/types.ts`), plus a new `LibraryRoute` type requiring it, which `storage/routesRepository.ts`'s `getRoute()`/`listRoutes()` now return — so a route read through the Route Library repository never needs a defensive `route.tags ?? []`. A new pure module, `src/domain/routeTags.ts`'s `normalizeRouteTags()`, is the single normalisation authority: non-array input and non-string entries are discarded; each surviving tag is Unicode-NFC-normalised, trimmed, with internal whitespace runs collapsed to one ordinary space; empty/whitespace-only results are discarded; two tags are the same identity when equal after NFC normalisation, the whitespace handling above, and plain ECMAScript `toLowerCase()` (deliberately not `.toLocaleLowerCase()`, for cross-machine/CI determinism) — documented explicitly as **not** full Unicode case folding (e.g. a German eszett spelling and its double-s expansion stay distinct tags) and **not** diacritic folding (an accented and unaccented spelling likewise stay distinct); the first spelling seen per identity is kept, in first-occurrence order. `routesRepository.ts` canonicalises tags on both save and read, and gains a narrow `updateRouteTags(id, tags)` primitive for stage 2 to build on — not called by anything in this stage. No Dexie version bump was needed: `routes`' `id, name, createdAt` index is unchanged since v1, and `tags` was added as a plain non-indexed field, the same precedent already established for `pinnedAt`/`manoeuvreProvenance`/`planningProvenance`/`surfaceSummary`.
       - **Fail-first, in explicit order.** Before any production file changed, one test using only pre-existing exports (`saveRoute`, `getRoute`, no new module or type) asserted a freshly saved, untagged route's `tags` equalled `[]` through `getRoute()` — confirmed failing on the unmodified tree with `expected undefined to deeply equal []`, a genuine runtime assertion failure rather than a compilation error. Only then were `domain/routeTags.ts`, the `LibraryRoute` type and the rest of the test suite added together.
       - **Legacy/corrupt-row and new-save-default behaviour.** A raw legacy v4 `routes` row with no `tags` field at all, and a row with a malformed `tags` value (non-array, or an array mixing valid and invalid entries), both load as a canonical `[]`/sanitised array via `getRoute()` and `listRoutes()` — proven with raw `db.routes.put()` rows bypassing the repository's own write path, and with a dedicated Dexie-schema test (`routes tags field (no schema version bump)`) confirming `db.verno` stays `4`. A route saved with the `tags` key omitted entirely defaults to `[]`.
       - **Both real production ingress paths, not a synthetic object alone.** The existing Planning save test (`PlanningScreen.test.tsx`, "saving clears the draft...") now additionally asserts the saved route's `tags` equal `[]`, exercising the real `PlanningScreen.tsx` save flow end-to-end. A new test in `gpx/importGpx.test.ts` drives the exact `importGpxFile()` → `saveRoute()` sequence `ui/library/ImportGpxButton.tsx` performs and asserts the same.
       - **GPX/privacy proof.** A distinctive probe tag is proven absent from exported XML; a route exported then reimported has no tags on the raw import result; and — closing the loop through the actual Route Library boundary rather than stopping at that raw result — saving and re-reading the reimported route produces a canonical `[]`. A second test confirms tags never change `<acn:navigation>`'s `geometrySha256` or add any new element/attribute, with the geometry-digest-bound extension itself untouched.
       - **Negative controls, two of which did not initially discriminate — reported honestly rather than dropped.** Disabling write-time canonicalisation in `saveRoute()` and separately in `updateRouteTags()` produced no test failure at first, because `getRoute()`'s own read-time normalisation silently compensated — a redundant-mechanism gap, not a sound design. Fixed by adding two further assertions that read the raw Dexie row directly (bypassing the repository's read-side normalisation) to prove the persisted data itself, not merely what is returned on read, is canonical; both controls then failed as expected. The remaining five controls (read-time normalisation, case-insensitive dedup, first-spelling-wins, whitespace collapsing, and a simulated GPX leak into a `<desc>` element) all discriminated correctly on the first attempt.
       - **Stage-2 design note (not implemented).** `ui/library/RouteListItem.tsx` already has a one-at-a-time, mutually-exclusive inline-state pattern (rename/pin/delete-confirm/switch-prompt) lifted to `RouteLibrary.tsx`; a future tag editor would add one more such state and an `onTagsSave` callback wired to `updateRouteTags`, the same way `onRename` wires to `renameRoute` today. A reusable-tag suggestion corpus would most naturally be a `useMemo` over the `LibraryRoute[]` that `listRoutes()`'s live query already returns, mirroring how item 99's `selectRouteLibraryGroups` is computed. Neither needs any stage-1 code to change.
       - Stages 2–4 (tag editing/suggestions, filtering/organisation, full lifecycle and physical acceptance) remain undone. Shipped as `0.4.15`; this is an invisible storage-layer change with no UI and no physical-device acceptance claim.
     - **Stage 2 progress (8 September 2026): compact tag editor and reusable suggestions shipped, browser-tested, not yet physically accepted.** `ui/library/RouteListItem.tsx`'s card body is now a three-way ternary (`isRenaming` / `isEditingTags` / the ordinary card), mutually exclusive by construction — the button that opens each mode only exists in the ordinary-card branch. Assigned tags render as a non-interactive `<ul aria-label="Tags">` chip list; a new "Add tags"/"Edit tags" action sits between Rename and Export. The tag editor is a `<div className="tag-editor">` showing the route's name/meta for context, a small inner `<form>` (label "Add a tag" + input + "Add tag" button, so Enter never submits the whole editor) and a single deterministically-sorted toggle-button grid — `sortTagsForDisplay(normalizeRouteTags([...tagSuggestions, ...tagDraft]))` — that handles selecting a suggestion, removing a currently-assigned tag and keeping a freshly-typed tag visible/removable pre-save, all as one mechanism. `RouteLibrary.tsx` derives `tagSuggestions` via `useMemo(() => collectTagSuggestions(routes ?? []), [routes])` from the full, unfiltered live-query result (never `viewRoutes`), and wires a thin `handleTagsSave` wrapper to the already-built `updateRouteTags`.
       - **Identity, never display-string equality.** Five small `domain/routeTags.ts` additions: `tagIdentityKey(tag)` extracts `normalizeRouteTags`'s own dedup-key computation into a reusable, exported function (a behaviour-preserving refactor — `normalizeRouteTags`'s existing test suite passes unmodified); `tagsEqualByIdentity(a, b)` is order-independent, count-aware set equality; `sortTagsForDisplay(tags)` is a fresh, domain-local `Intl.Collator("en-GB", { sensitivity: "base", numeric: true })` sort (not imported from `ui/library/routeLibraryView.ts` — domain must not depend on ui); `resolveTagSpelling(candidate, knownTags)` returns `null` for a whitespace-only candidate, otherwise the candidate's own normalised spelling unless an identity-equivalent tag already exists in `knownTags`, in which case that established spelling is returned instead; `collectTagSuggestions(routes)` is `sortTagsForDisplay(normalizeRouteTags(routes.flatMap(r => r.tags)))`, reusing `normalizeRouteTags` over the flattened cross-route corpus for cross-route dedup and first-occurrence-spelling-wins with no new dedup logic. Every draft-membership, pressed-state, toggle and duplicate check in `RouteListItem.tsx` compares via `tagIdentityKey`, never raw `.toLowerCase()` or `===` — proven directly: a route whose own stored tag is `"gravel"` while another route has established `"Gravel"` renders **one** merged, pressed entry labelled `"Gravel"`; toggling it off removes `"gravel"` by identity despite the differing display spelling; saving _without_ touching it preserves the original `"gravel"` spelling unchanged (canonicalisation happens only on an explicit type/toggle interaction, never silently).
       - **The editor never closes onto stale chips.** `onTagsSave`'s promise resolves as soon as the underlying write settles — a separate, later step from `useLiveQuery`'s `listRoutes()` subscription actually re-firing and this card's `route` prop reflecting the new tags. Closing on promise-resolution alone risked a render where the editor was closed but the chips still showed the pre-save tags. Fixed with a `savedTagsAwaitingSyncRef`, set once the write settles, consumed by a `useEffect` keyed on `route.tags` that only closes the editor once `tagsEqualByIdentity(route.tags, savedTagsAwaitingSyncRef.current)` is true — mirroring `RouteLibrary.tsx`'s own `lastRenamedIdRef`/`lastRenamedNameRef` "wait until the live query demonstrably reflects an async write" precedent. Proved through the real repository/live-query pipeline, not a manually rerendered prop: an integration test spies on `routesRepository.listRoutes` (the function the live query actually calls) to inject a real, undelayed-write/delayed-read artificial gap, then samples repeatedly across the whole widened window — never checking once — confirming the editor is never observed closed while the chips still show the pre-save tags.
       - **Save/Cancel/Escape are guarded synchronously, independent of React's render timing.** The load-bearing guard for `handleSaveTags`/`handleCancelTags`/Escape is a `useRef<boolean>` (`isSavingTagsRef`), checked and set immediately — a `useState` value alone is not reliably synchronous against two invocations landing before React has processed the first one's update. Proved with two techniques: the project's existing two-synchronous-`fireEvent.click()` convention, and a strengthened test invoking the Save handler twice inside one `act()` call with zero intervening re-render. The strengthened test is the one that actually matters here — see the negative control below.
       - **Fail-first.** One test against the unmodified `0.4.15` tree rendered `RouteListItem` with `tags: ["Gravel"]` and asserted an "Edit tags" button plus visible "Gravel" text — confirmed failing with a genuine `TestingLibraryElementError` (element not found), not a compile error.
       - **Automated evidence.** 30 domain tests (`routeTags.test.ts`, 17 new), 80 `RouteListItem.test.tsx` tests (25 new, covering every hand-off-required case plus the identity/sync/guard mechanics above), 72 `RouteLibrary.test.tsx` tests (7 new, real fake-indexeddb integration — cross-route suggestion reuse and spelling adoption, suggestion availability despite an active search filter, name-only search preserved, all four sort modes plus pin priority unaffected by a tag save, persistence across unmount/remount, a rejected write retaining the draft with retry, and the delayed-`listRoutes` stale-chips proof). Two new Playwright specs: `routeLibraryTags.spec.ts` (chromium; the full journey — add/reuse/dedupe/remove/reload — plus 390×844, 200%-text and 844×390-landscape geometry/44×44 evidence) and `androidRouteLibraryTags.spec.ts` (android-chrome; no existing Route Library spec ran on this project before, so this is a new file, deliberately narrower, following the established `android*.spec.ts` convention).
       - **Negative controls, two of which needed strengthening or were reported honestly rather than silently dropped.** Calling `onTagsSave` from the suggestion-toggle handler instead of only `handleSaveTags` did not initially fail the "Cancel discards the draft" test, because that test only exercised typing a tag, never toggling a suggestion — the test was strengthened to cover both mutation paths, after which the control correctly failed. Reverting the `isSavingTagsRef`-based guard to read the `isSavingTags` _state_ value instead did **not** fail the project's own standard two-`fireEvent.click()` test (React's `act()` happens to flush state between the two calls in that harness) but **did** fail the strengthened single-`act()`-double-invocation test — reported honestly rather than treated as a pass, and the reason the strengthened technique was added at all. The remaining six controls (suggestions from `viewRoutes` instead of `routes`; bypassing `resolveTagSpelling`; closing the editor unconditionally on any settled promise, which discriminated both the rejected-write and the stale-chips tests at once; removing `aria-pressed` and removing the decorative check-mark independently; including tags in the name-search predicate) all discriminated correctly on the first attempt.

CI's "Verify and build" job passed, but "End-to-end tests" failed at the same boundary in both the `chromium` and `android-chrome` Playwright projects during run 226, so Deploy was skipped and `0.4.16` never reached the live site. That failure cannot be dismissed as a contention-only test flake: CI exposed a genuine production ordering race in both browser projects during run 226. (One CI run reproducing the same failure in two projects is strong evidence of a real bug, not proof the race resolves the same way on every run — CPU scheduling could still influence which side of the race wins on a given run — so this is stated as a genuine race CI exposed, not as deterministic on every run or as something contention plays no part in.)
       - **Root cause.** `RouteListItem.tsx`'s tag editor closes only once two independent async facts are both true: the save write has settled, and `route.tags` (via `RouteLibrary`'s live query) reflects the saved tags by identity. The write-settled fact was held in a plain `useRef` (`savedTagsAwaitingSyncRef`), set inside the write promise's `.then()`. A ref mutation never triggers a re-render or effect re-run. The closing effect depended only on `route.tags`. This worked whenever the write settled _before_ `route.tags` updated — but broke whenever `route.tags` updated _first_: the effect ran once, found the ref not yet set, no-opped; when the write later settled and the ref was finally set, nothing caused the effect to run again, and the editor stayed on "Saving…" forever. The same failure mode also affected a successful no-op save (re-saving already-canonical tags), where `route.tags` might never change again at all.
       - **Fix: a genuine two-signal handshake, in `useState`, not a ref.** `savedTagsAwaitingSyncRef` became `pendingSyncTags`, a `useState<string[] | null>` — so setting it in the write's `.then()` is itself a state update that causes React to reconsider the closing condition, keyed on both `route.tags` and `pendingSyncTags`, wherever the two-signal handshake sits in the component (moved from an effect to a during-render adjustment — see below). No ref-only signal, no microtask delay, no `setTimeout`, and no increased Playwright timeout is part of the fix itself.
       - **A second lint-driven correction along the way.** The straightforward `useEffect` version of the new two-state-dependency closing check tripped this project's `react-hooks/set-state-in-effect` rule, which only exempts a ref-gated "consume once" shape — not this one, since `pendingSyncTags` is deliberately state. Following the exact convention already established in `RouteLibrary.tsx` (`pendingRouteSwitch`/`previousPendingRouteSwitch`) and `RidingScreen.tsx`, the closing check was moved to React's own documented "adjust state during render" pattern instead of an effect; it is self-terminating with no extra "previous value" mirror needed, because clearing `pendingSyncTags` is itself one of the condition's own inputs. `isSavingTagsRef`'s own reset on this success path can't happen during render either (`react-hooks/refs`), so it was split into a small separate effect keyed on `isSavingTags`.
       - **New fail-first evidence for the exact ordering CI hit, plus the orderings it didn't.** `RouteListItem.test.tsx` gained an explicit "Ordering A" test (write settles first — already worked, kept as a regression guard, replacing the previous less explicit version), a new "Ordering B" test (`route.tags` arrives first — the load-bearing fail-first case, confirmed failing against the unmodified `39e45fe` code with a genuine `findByRole` timeout, confirmed passing after the fix), and a new no-op-save test (route already canonical, no further `route.tags` change ever required to close — also confirmed failing pre-fix). `RouteLibrary.test.tsx` gained a real-repository/live-query integration test for ordering B: it performs the real `updateRouteTags` write immediately (so the live query can react to it for real) while holding the write's own caller-visible promise on a manually-released deferred, _proves_ the live query has already propagated — before ever releasing that deferred — by checking the new tag now appears as a reusable suggestion on a second, different route's editor, then confirms the first route's card is still open, releases the write, and confirms it then closes; this test was independently confirmed to fail against the unmodified `39e45fe` code (the same real-device symptom: the card stuck open) and to pass after the fix. Counts: `routeTags.test.ts` stays 30; `RouteListItem.test.tsx` 80 → 82; `RouteLibrary.test.tsx` 72 → 73.
       - **The 25-second timeout padding is removed.** `SAVE_ROUND_TRIP_TIMEOUT` and its explanatory comment are deleted from both `routeLibraryTags.spec.ts` and `androidRouteLibraryTags.spec.ts`; the affected assertions are back to Playwright's own default timeout. With the real fix in place, five repeats of each spec on both `chromium` and `android-chrome`, plus two full-suite runs, all passed in well under a second per assertion — the timeout padding was never the correct fix and is not needed.
