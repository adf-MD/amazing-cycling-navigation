_Category: Immersive active-Riding redesign_

56. **Fixed route Map/Profile views — done**

Presentation only: no change to route-matching, progress, off-route classification, manoeuvre selection (beyond consuming item 47's fix), elevation/gradient/climb calculation, completion-arming, or persistence logic.
    - **Wake-lock/header ordering fix (corrects item 55's own post-deployment finding above [docs/project/history/items-49-55.md]).** `RidingWakeLockControl`'s render call moved to directly after the header block (after `RidingImmersiveHeader` and its `pauseError`/`.ride-end-ride-confirm-row` siblings) in both `RidingScreen.tsx` and `FreeRoamScreen.tsx`, with its own existing render condition (`isWakeLockSupported() && geolocationStatus !== "idle"` for Riding; unconditional-while-mounted for free roam) completely unchanged. No CSS changes were needed for this specific fix alone — `.riding-immersive-header`'s own padding/`:has()` safe-area handling was always correct regardless of what followed it; the bug was purely about what preceded it. For route Riding, the wake-lock control additionally becomes the first of the new "shared" status stack described below (visible from either Map or Profile), which the reorder already achieves for free.
    - **Architecture — why `<MapView>` and `GradientColoursDisclosure` never remount across idle↔active or Map↔Profile.** React only preserves a component instance across renders when its JSX expression sits in a stable, unconditional textual slot in the source — the same "stable outer wrapper, conditional only on the inside" pattern this file's own Milestone-4 sixth-slice entry [now in `docs/project/history/delivery-milestones.md`] already established for `GradientColoursDisclosure`'s uncontrolled `<details>` state. Concretely: writing `{cond ? <div><MapView/></div> : <div><Other/><MapView/></div>}` **does** remount `MapView` (different children arrays at the same slot, confirmed directly by reasoning through React's keyless-children reconciliation, not assumed); writing `<div>{cond ? <Other/> : null}<MapView/></div>` **does not** (MapView's own JSX expression is textually fixed; only what precedes it toggles between `null` and content). This dictated the whole design: `.ride-map-container` (containing `<MapView>`) and the Profile pane's own wrapper (containing `GradientColoursDisclosure`) are each a **single, always-rendered** element — present with the same shape in both idle and active, and both `.ride-content-area`-child slots the same on every render regardless of `activeView` — with idle/active and Map/Profile differences expressed entirely via conditional `className`/inline `style`/`aria-hidden` on that same stable element, never via branching that wraps either of them differently. `RidingScreen.tsx`'s idle branch is otherwise byte-for-byte unchanged from before this slice; only its map-preview div and `.ride-profile-panel` div now sit as the two children of the same unconditionally-present `.ride-content-area` wrapper (base, non-`--immersive` variant during idle — a plain flex column reproducing the exact 16px gap those two elements already had as ordinary flex siblings of `.screen`, a pure relocation with no idle-state visual change).
    - **State.** One new local `useState<"map" | "profile">("map")` in `RidingScreen.tsx` (`activeView`), reset to `"map"` only inside the **existing** idle-only branch of `handleStart` (the same branch that already resets `explicitFeatureSelection`/`selectedGradientSegment`) — defaults to Map on a genuinely fresh Start and on an explicit Resume-riding tap, but deliberately not on the mid-ride "Try again" retry path (the same handler's `else` branch, untouched) — a rider mid-GPS-error on Profile is not yanked back to Map. A Pause→relaunch→Resume cycle gets a fresh `"map"` default for free, since this whole screen unmounts on Pause. Not persisted to storage, per the item's own scope (presentation-only local state).
    - **Both panes (Map, Profile) stay permanently mounted; toggling is CSS-only (inline `visibility`/`pointerEvents`, plus `aria-hidden`), never conditional unmount.** Each pane is `position: absolute; inset: 0` inside a shared `position: relative` content area (`.ride-content-area--immersive`), so both panes always occupy the identical, constant-size box regardless of which is active — the map's rendered pixel size never changes on toggle, so there is no `<MapView>` resize risk to reason about at all (not even relying on `ResizeObserver` spec behaviour for a 0→nonzero transition, since the box is never zero). The toggle uses **inline `style`, not a CSS class**, for the visibility/pointer-events pair: `vite.config.ts`'s test config sets `test: { css: false }`, so component tests never load `index.css` — a class-driven visual state (as this file already documents happening once, for `GradientColourSwatch`) would be invisible to jsdom assertions, whereas inline style is always readable via `getComputedStyle`/`toHaveStyle`, and `@testing-library`'s `getByRole` correctly excludes `visibility: hidden` subtrees from queries, giving real, testable proof that inactive-pane controls become unreachable. `aria-hidden` is added defensively alongside it.
    - **A genuine DOM-duplication bug found and fixed during test-writing, not merely theorised.** The first design gated the compact manoeuvre cue (see below) purely on urgency (`!idle && nextManoeuvre !== null && urgency !== "normal"`), reasoning that mounting it unconditionally inside the always-present, merely-`aria-hidden`-toggled Profile pane was harmless. Fixed by additionally gating the compact cue's render on `activeView === "profile"` (unlike the panes themselves, the cue is stateless with no `GradientColoursDisclosure`-style continuity requirement, so conditionally mounting/unmounting it is completely safe and costs nothing) — eliminating the duplication outright rather than just working around it in tests.

When it isn't — i.e. `classifyManoeuvreUrgency` (an existing exported pure function from `navigation/nextManoeuvre.ts`, unchanged, moved nowhere) classifies the _same_ already-computed `nextManoeuvre.remainingDistanceMetres` RidingScreen already passes to the full panel as `"near"` or `"imminent"` — a small new `RidingCompactManoeuvreCue` component (`src/ui/riding/RidingCompactManoeuvreCue.tsx`, new) renders at the top of the Profile pane's `.ride-elevation-section`: a direction icon (reusing the existing `ManoeuvreIcon`), a CSS-ellipsis-truncated ("shortened") one-line instruction, and the distance. `genericManoeuvreLabel` (the per-type fallback instruction text) was extracted out of `RidingNextManoeuvrePanel.tsx` into a new shared `src/ui/riding/manoeuvreLabels.ts` — not merely exported from the panel file — because exporting a non-component function alongside a component trips `react-refresh/only-export-components`, a warning this slice chose to eliminate rather than tolerate; `formatManoeuvreDistance` (already exported from `routeSummary.ts`) is imported directly, no new formatting logic. `RidingCompactManoeuvreCue` never switches the view to Map and never forces document scroll (it sits inside the Profile pane's own bounded content, ahead of `elevationSectionBody`). Because `showCompactManoeuvreCue` is a plain boolean recomputed every render from the live `nextManoeuvre`/urgency (not a one-shot decision), it disappears automatically the instant the manoeuvre's urgency returns to `"normal"` or the selection advances past it — no explicit "hide" logic is needed. `RidingStatusStrip` and `RidingRouteCompletionPanel` render unconditionally (as before this slice, gated only on their own existing conditions, never on `activeView`) so they're visible from either view — directly satisfying the requirement that completion must "remain readily discoverable... without an automatic view switch." ## Item 57 — Non-disruptive climb cue and Profile integration — done

_Category: Immersive active-Riding redesign_

57. **Non-disruptive climb cue and Profile integration — done**
    - Depends on items 55 and 56. On the Map view, entering a recognised climb no longer leaves the rider with no indication at all — a small, non-disruptive cue appears, and Map stays selected throughout; a `View climb` action switches to Profile with `Climb` already selected, in one tap.
    - **Zero new state, zero new persisted fields, zero new navigation/domain logic.** The cue's visibility is a pure derivation from values `RidingScreen.tsx` already computes every render for the existing Profile-pane Climb-chart branch: `activeClimb` (progress-driven, via `findFeatureAtDistance`), `climbProgressMetrics` (via the existing, unmodified `computeClimbProgressMetrics`), and `effectiveElevationView` (via the existing, unmodified `selectEffectiveElevationView`, `climbElevationView.ts`, item 13). `effectiveElevationView.kind === "climb"` already means exactly "there is an active climb, not manually dismissed for this climb" — precisely the condition under which the cue should show — so the cue's gate is `nav.geolocationStatus !== "idle" && activeView === "map" && effectiveElevationView.kind === "climb" && activeClimb !== null && climbProgressMetrics !== null`, mirroring the Profile branch's own three-part guard (plus the two defensive checks already established elsewhere: the `geolocationStatus` gate, mirroring `RidingNextManoeuvrePanel`'s identical precedent, matters because `.ride-map-container--immersive` is unconditionally mounted including for the idle pre-ride preview, so a resumable session with stale climb state must not show the cue before Resume riding is pressed; and `activeView === "map"`, the existing Map/Profile switcher state from items 55–56). `View climb`'s `onViewClimb` is a single `setActiveView("profile")` — since the cue is only ever visible while `effectiveElevationView.kind === "climb"` is already true, switching to Profile alone is sufficient; no separate dismissal-clearing call is needed and the two presentations cannot desync, since both read the same `effectiveElevationView` value. Nothing in this item ever calls `setActiveView` automatically, so "must never automatically switch away from Map" holds by construction, not by a guard. ### Unnumbered reliability follow-up — stabilised the `RidingScreen` active-state error test

Not a numbered backlog item; recorded here as a test-only reliability correction from the same era as item 68, immediately after it, rather than in `backlog.md` or as a new monitored entry in `current-status.md`.

- **Incident.** Documentation-only commit `c57dd17` (unrelated to item 68) triggered a GitHub Actions failure in `src/ui/riding/RidingScreen.test.tsx`, suite `onRidingActiveChange`, test `keeps reporting true through a transient GPS error mid-ride`: `expect(onRidingActiveChange).toHaveBeenLastCalledWith(true)` received `undefined`. The test passed 12/12 in isolation on the same commit, indicating a full-suite-load-only race rather than a permanent break — consistent with item 68's own recorded 2670/2670 unit total, which this exact test contributed to.
- **Confirmed root cause (source-verified, not the earlier commit assumed).** Re-read against current, post-item-68 source: the production effect (`RidingScreen.tsx`, `onRidingActiveChange?.(nav.geolocationStatus !== "idle")` plus its cleanup) is untouched since `c57dd17` — `git diff c57dd17 9908176 -- src/ui/riding/RidingScreen.tsx src/ui/riding/RidingScreen.test.tsx` shows item 68 only renamed wake-lock label text elsewhere in the same test file, nowhere near the `onRidingActiveChange` describe block. The test's own `stub.emitError(...)` call invokes the geolocation stub's listener directly — a bare synchronous call, not routed through `fireEvent`/`userEvent`, so it gets none of React Testing Library's automatic `act()` flushing. React commits the resulting DOM change (the alert) and flushes the passive effect that calls `onRidingActiveChange` as two separately scheduled things. `await screen.findByRole("alert")` only guarantees the former (it polls via DOM mutation, satisfied the moment the alert commits) — it is not causally ordered after the latter. Under ordinary load the effect happens to flush first; under full-suite contention the assertion could still run before it, observing the freshly-cleared mock's `undefined`.
- **Why the alert wasn't a sufficient synchronisation point.** The alert element and the `onRidingActiveChange` call are both downstream of the same `nav.geolocationStatus` state transition, but on different React scheduling paths (commit vs. passive-effect flush) once the triggering call sits outside any `act()` boundary. Waiting for one does not wait for the other.
- **Minimal correction.** Test-only, in `src/ui/riding/RidingScreen.test.tsx`:
  1. Added an explicit `expect(onRidingActiveChange).toHaveBeenLastCalledWith(true)` immediately after the `Start riding` click, before `mockClear()` — mirroring the already-reliable sibling test earlier in the same `describe` block, so the error-transition phase can no longer inherit an unobserved Start transition.
  2. Kept `stub.emitError(...)` and `await screen.findByRole("alert")` exactly as they were (still proving the error surfaces).
  3. Replaced the final synchronous assertion with `await waitFor(() => { expect(onRidingActiveChange).toHaveBeenLastCalledWith(true); })` — synchronising on the exact postcondition the test claims to prove, rather than on the incidentally-timed alert. This is this file's own established idiom for exactly this shape of assertion (a callback/spy driven by an effect that follows a stub emission): the same `await waitFor(() => expect(spy).toHaveBeenCalledWith(...))` pattern already appears roughly a dozen times in this file for `map.setCameraSpy` assertions after `stub.emitFix(...)`.
