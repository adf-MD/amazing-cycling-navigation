## Item 81 — Preserve Riding zoom through stale-GPS and imagery-retry recovery — done

_Category: Riding camera reliability investigation_

81. **Preserve Riding zoom through stale-GPS and imagery-retry recovery — done**
    - Field evidence: during an active route ride (the PWA remained active throughout — never paused, backgrounded or suspended), the camera intermittently ended at approximately whole-world zoom after a combination believed to involve stale GPS and pressing `Retry map imagery`. Follow was already active; pressing Follow again did not restore a normal zoom, which is correct, since Follow preserves the rider's selected zoom rather than resetting it. Pressing North-up also did not change zoom, which is likewise correct, since North-up only changes bearing/pitch. Manual pinch/`+` zoom restored a normal useful view. Kept separate from item 66 (an unreproduced, accepted-for-now-monitored route-Riding fresh-Start overview-zoom symptom) and item 74 (a confirmed and shipped fix for a _different_ free-roam fresh-Start zoom-corruption bug, via the `hasAppliedCameraCommand` settle-provenance latch) — this item's evidence is mid-ride, tied specifically to a stale-GPS-plus-imagery-retry combination, not a fresh Start.
    - **Confirmed root cause, source-verified before any change, then proven with a failing test against unmodified code.** `src/map/MapView.tsx`'s `appliedCameraCommandGenerationRef` (item 74's own settle-provenance latch) answers only "has _any_ real `cameraTarget` command ever been applied on this map instance's current generation" — set once, synchronously, immediately after the `cameraTarget` effect calls `setCamera`, and never reset except by a full map recreation. `onCameraSettled`'s `hasAppliedCameraCommand` payload field was computed purely as `appliedCameraCommandGenerationRef.current === generation` — a coarse per-_generation_ latch, not a per-_settle-event_ correlation. Once true for a generation, **every subsequent settle on that instance — regardless of what actually produced it — was reported `hasAppliedCameraCommand: true`**, indistinguishable from a genuine settle of the tracked command. `src/ui/riding/rideCamera.ts`'s `"follow-zoom-settled"` reducer case trusts this boolean completely: if a settle carrying a value that does not correspond to the rider's real command reaches it while `mode === "following"`, `awaitingFreshFix === false` and the latch is already true, `followZoomLevel` is unconditionally overwritten. That field is read directly by `useRideCamera.ts`'s `persistableCameraState` and by every subsequent `followCommand(...)` call, so the corruption is persisted on the very next accepted GPS fix (unrelated to the corrupting settle) and does **not** self-correct on a later fresh fix, since `"fresh-fix"` explicitly preserves `state.followZoomLevel` rather than re-deriving it — matching the field report's every detail: Follow's own re-press faithfully (and correctly, per its own contract) reproduces the corrupted value rather than resetting it; manual zoom "fixes" it only because `"follow-zoom-changed"` steps _away from_ the corrupted value additively rather than re-deriving it from a trustworthy source; and the corruption survives a subsequent fresh fix rather than self-correcting, since only genuine reducer-state corruption (not a transient display glitch) explains that persistence.
    - **A previously-ruled-out hypothesis, not re-proposed.** Item 66's own investigation (`docs/project/current-status.md#item-66`) had already directly read the installed MapLibre 6.0.0 source and confirmed `Map.resize()` does not independently fire its own corrupting settle at a stale transform — it only updates cached container dimensions and leaves an in-flight ease running. This investigation did not reopen that finding.
    - **Two other hypotheses traced and closed, not merely assumed safe.** A "Follow re-pressed while GPS is stale, after an earlier manual gesture" path was traced in full: a genuine gesture drops `rideCameraReducer`'s `mode` to `"free"`, which also nulls `cameraTarget`; re-requesting Follow with a stale (`freshCoordinate: null`) fix produces `NO_COMMAND` and keeps `cameraTarget` at `null`, so the `cameraTarget` effect never runs and `appliedCameraCommandGenerationRef` correctly stays stale for that generation — this path is not reachable as a corruption source. An "overview-fit effect re-firing mid-ride" hypothesis was closed by inspecting `hasActionableCameraTarget` (`useRideCamera.ts`): a sticky, monotonic latch, explicitly documented as existing to prevent exactly this ("un-latching then would make MapView's overview-fit effect re-run and incorrectly re-fit the whole route mid-ride"), which stays true for the rest of a route-open session once Follow has engaged once, regardless of later staleness or mode churn.
    - **Fail-first evidence, exercising the real causal path, not a fabricated reducer event.** A new `MapView.test.tsx` test (`describe("recoverable errors, staged readiness, and retry", ...)`) drives the real, unmodified `cameraTarget` effect and `onCameraSettled` handler via the file's existing mock map factory: a genuinely non-default zoom (18, never `NAVIGATION_ZOOM` or the corrupting settle's own 0) settles and is correctly reported `hasAppliedCameraCommand: true`; a tile/style failure and manual `retry-map-imagery-button` click trigger a real map-instance recreation (a new attach generation); the new generation's own `cameraTarget` effect genuinely re-applies the same real command once style becomes ready (`setCameraSpy` called twice, correctly); then `mock.triggerCameraSettled({coordinate:[0,0], zoom:0, ...})` — MapLibre's own confirmed pre-style-ready settle at its raw default transform, delivered _after_ the real command rather than before it, which nothing in production code bounds to arrive first — is fired on the same generation. **Pre-fix, this settle was reported `hasAppliedCameraCommand: true`** (confirmed by running the test against the unmodified tree, `git stash`ed away from the fix, before writing any production change), passing all four of the reducer's guard conditions and, per the second test below, genuinely corrupting `followZoomLevel`. A companion `RidingScreen.test.tsx` integration test reproduces the complete field sequence end to end — Start, a fresh fix, two real `Zoom in` presses to `NAVIGATION_ZOOM + 2`, a genuine `stub.emitError(...)` (retained-stale-fix, no Follow re-press, no manual gesture), a genuine tile error, a manual `Retry map imagery` click, the new generation's correct real reapplication, the same unrelated late settle, then a fresh stationary fix followed by a fresh moved fix. **Pre-fix, the moved fix's resulting `setCamera` call carried `zoom: 0`** — the field-reported "approximately whole-world zoom" — instead of the rider's real `18`, confirmed deterministic across repeated runs before any production change. (The stationary-fix step in this same test is a legitimate but weaker check: a genuinely unmoved fix does not reissue any command at all under `rideCamera.ts`'s existing "stationary fixes don't jitter the camera" no-op guard, so it cannot itself distinguish a corrupted from an uncorrupted `followZoomLevel` — the moved fix is what carries the pre-fix failure.) Two genuine test-level races were found and fixed while constructing this evidence, neither a production defect: `map.triggerTileError()`/`map.triggerCameraSettled(...)` are raw synchronous calls bypassing React Testing Library's automatic `act()` flushing (mirroring this file's own already-documented `emitError` gotcha), requiring `await screen.findByTestId(...)` rather than a synchronous query; and the post-retry `waitFor` assertion needed an explicit `setCameraSpy.mockClear()` beforehand, since without it the assertion could trivially pass against a stale pre-retry call that happened to already match by coincidence, racing ahead of the real generation-2 reapplication.
    - **The fix: a coordinate-provenance correlation, not a zoom clamp or a broader gate.** `MapView.tsx` gained `settleMatchesLastAppliedCommand(settleCoordinate, lastApplied)`, comparing the settle's own coordinate against `lastAppliedCameraTargetRef.current` — the exact target the most recently applied command actually specified — within a `1e-6`-degree tolerance (mirroring `e2e/ridingCamera.spec.ts`'s own `CAMERA_VALUE_TOLERANCE`, for negligible floating-point read-back noise on a genuinely-caused settle, far tighter than any real distinguishable coordinate difference). `hasAppliedCameraCommand` becomes `appliedCameraCommandGenerationRef.current === generation && settleMatchesLastAppliedCommand(camera.coordinate, lastAppliedCameraTargetRef.current)`. Deliberately **coordinate-only, not zoom/bearing/pitch**: MapLibre's own min/max zoom clamping can legitimately shift a genuinely-caused settle's zoom away from the exact commanded value (`rideCamera.test.ts`'s own clamped-zoom reconciliation coverage proves this is a real, intended case), so correlating on zoom would risk exactly the false negative this project's own "do not globally clamp deliberate zoom" requirement forbids; a raw/default MapLibre transform, by contrast, is never the rider's real route/GPS coordinate, so coordinate alone fully and safely discriminates the untrustworthy case. A command with a null coordinate (north-up-only, via `rideCamera.ts`'s `"north-up-requested"`) always drops `rideCameraReducer`'s own mode to `"free"` — `"follow-zoom-settled"`'s own mode guard already excludes that settle regardless of this function's result, confirmed by direct source reading before relying on it, so falling back to `true` (generation-only) when no coordinate was ever commanded needed no special-casing.
    - **Deliberately not done, per the fail-first evidence's own scope.** No `cameraRestorePendingGenerationRef` skip-once guard was added to the `cameraTarget` effect (mirroring the sibling overview-fit/warning-selection-fit effects): traced and found structurally unreachable for `useRideCamera.ts`, since a genuine gesture always nulls `cameraTarget` before any diverged-and-still-following state could exist. `lastAppliedCameraTargetRef`'s reset was left unconditional (not made divergence-aware like its four sibling one-shot dedup refs), since making it conditional risks regressing the already-tested "retry preserves and re-applies a live cameraTarget" guarantee and the fail-first evidence gave no reason to touch it. `rideCameraReducer`'s `"follow-zoom-settled"` guard itself was left completely unchanged — it already correctly trusts an accurate boolean; the defect was entirely in what produced that boolean.
    - **Free roam: no production changes needed, confirmed by tracing, not merely assumed.** `useFreeRoamCamera.ts` consumes the exact same shared `rideCameraReducer` and forwards `MapView.tsx`'s `hasAppliedCameraCommand` verbatim into the same `"follow-zoom-settled"` event, via the same `onCameraSettled` payload MapView produces — since the fix lives entirely inside `MapView.tsx`'s shared handler, free roam inherits the correction automatically. The complete existing `useFreeRoamCamera.test.ts` and `e2e/freeRoam.spec.ts` suites were re-run unmodified and pass, confirming the shared fix introduces no free-roam regression; no new free-roam-specific test was added, since no free-roam-only production code changed and this item's own scope explicitly authorises extending only if a shared defect is proven — here the shared fix is already the smallest safe correction.
    - **Real-browser regression.** A new `e2e/mapImageryRecovery.spec.ts` test combines this file's own manual-retry mechanism with `ridingCamera.spec.ts`'s Zoom-in-to-a-non-default-zoom technique and `ridingStatusCardRecovery.spec.ts`'s genuine `context.clearPermissions()` stale-fix mechanism: establishes a genuinely non-default zoom, induces a real mid-ride tile failure and clicks the real `Retry map imagery` button, induces a real `PERMISSION_DENIED` geolocation error, then recovers both (re-granting permission and pressing the real "Try again", and letting the tile retry's own success clear the imagery banner), asserting `data-camera-zoom` equals the rider's exact pre-failure selected zoom for both a stationary and a subsequently moved fresh fix, and that `Follow my location` stays pressed throughout. A genuine test-level settle-timing race was found and fixed while writing this: `triggerFreshTileFailure`'s own success signal (a new tile request failing) is an independent async completion from the camera's own ease settling at the new zoom, so the "selected zoom" reference value must be captured only after an explicit poll confirms the camera has itself genuinely changed, not merely immediately after the tile-failure helper resolves. This e2e test is real-MapLibre regression/non-regression coverage for the fix, not the prove-first evidence itself — the exact out-of-order-settle race the fix closes is proven deterministically at the component/integration level, where settle ordering is under full test control; a real browser gives no reliable way to force that same internal ordering without manufacturing an artificial, unrepresentative race, and this item's own instructions explicitly warn against doing so.
    - **Files changed.** Production: `src/map/MapView.tsx` (`settleMatchesLastAppliedCommand`, `CAMERA_PROVENANCE_TOLERANCE_DEGREES`, and `onCameraSettled`'s `hasAppliedCameraCommand` computation — the entire production diff). Test: `src/map/MapView.test.tsx` (one new test), `src/ui/riding/RidingScreen.test.tsx` (one new test), `e2e/mapImageryRecovery.spec.ts` (one new test). `package.json`, `package-lock.json`.
