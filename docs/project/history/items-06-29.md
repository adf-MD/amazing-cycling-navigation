## Item 7 — Inline route-deletion confirmation — done

_Category: Navigation and library interface_

7. **Inline route-deletion confirmation — done**
   - Pressing a route's Delete button now opens a non-modal, per-row confirmation (`role="alertdialog"`, no `aria-modal`) rendered inside that route's own `<li>`, directly beneath its Rename/Export/Delete row, replacing the previous screen-detached `ConfirmDialog`. `RouteLibrary` keeps single-source-of-truth ownership of `pendingDeleteId`/`isDeleting`/`deleteError` and the actual `deleteRoute` call; `RouteListItem` only ever renders its own row's confirmation, so at most one is open at a time and opening a second row's replaces the first.
   - Opening the confirmation moves focus to Cancel; Cancel and Escape-within-the-confirmation both close it without touching storage and return focus to that row's own Delete button — both actions are disabled while a deletion is in flight so Cancel can never appear to undo a delete that storage is still carrying out. Clicking Rename while a delete confirmation is open on the same row cancels the pending delete first, rather than leaving it silently orphaned.
   - On success the reactive `useLiveQuery`-backed list removes the row automatically; a small pure helper (`routeDeleteFocus.ts`) then moves focus to the next, else previous, else (empty library) the Routes heading — with no global selectors or route-name matching, since route names aren't guaranteed unique. A failed deletion keeps the route, shows an inline error, and leaves the confirmation open for cancel or retry; the destructive button reads "Deleting…" while in flight, to prevent double submission.
   - `ConfirmDialog.tsx` itself is unchanged and still backs Settings' "Delete OpenRouteService key" confirmation — only `RouteLibrary`'s own usage of it was removed.
   - Renaming a route (the "Rename" button) is likewise an in-card edit state: `RouteListItem` renders exactly one `<li className="route-card stack">` per route across its normal, renaming and delete-pending states — entering rename mode no longer swaps in a separate, unstyled `<li>` above the list. Distance/ascent stay visible while renaming; Export/Delete (and any open delete confirmation) are fully unrendered, not merely disabled, while renaming; the input autofocuses with its existing name selected; Save and Cancel both return focus to the row's own Rename button, and Escape performs the same discard-and-restore as Cancel, mirroring the delete confirmation's own Cancel/Escape-returns-focus precedent above.

## Item 18 — Ride screen opens from the top; library scroll position remembered for the session — done

_Category: Navigation and library interface_

18. **Ride screen opens from the top; library scroll position remembered for the session — done**
    - Opening a route from Routes, or saving a newly planned route from Planning, previously kept whatever document scroll offset Routes (or Planning) happened to be at, so a route opened from far down a long library — or saved after scrolling deep into a long Planning form — could land on Riding already scrolled away from its own heading. A new hook, `useResetScrollForNewRideContent` (`src/ui/shared/`), scrolls the document to `(0, 0)` with `behavior: "auto"` (never animated) the instant `App.tsx`'s `screen` becomes `"riding"` and a token it owns internally has advanced past whatever it last actually applied, bumped only by `handleOpenRoute` and `handleRouteSaved` — App's only two genuine "a new route is now the selected ride" call sites. It never fires on a plain nav-tab click back to an already-open ride: `RidingScreen` always fully unmounts/remounts on every screen switch (no `key` anywhere in `App.tsx`'s conditional screen rendering), so only `App` itself — which never unmounts — can tell "genuinely new" apart from "already open."
    - `RouteLibrary` gained one new optional prop, `restoreScrollYRef` (a plain `RefObject<number | null>`, never a dereferenced value — reading a ref's `.current` during render would both trip this project's `react-hooks/refs` lint rule and not actually work, since a ref mutation alone never triggers the re-render needed to pick up a changed prop). `App.tsx`'s `handleOpenRoute` captures `window.scrollY` into this ref synchronously, as the very first statement of the click handler, strictly before any state setter — the only point guaranteed to run before React unmounts the library's tall content (a browser's own scroll clamping only ever bounds `scrollY` to the new, shorter document's max, never zeroes it, so an explicit reset is required regardless). `RouteLibrary` restores it, via `window.scrollTo`, inside a `useLayoutEffect` gated on real route cards having rendered (never the "Loading routes…" placeholder), applies it at most once per mount, and always nulls the ref out afterwards, so neither a later reactive `useLiveQuery` update from the same mount (rename/delete) nor an unrelated later remount (e.g. Routes → Diagnostics → Routes with no intervening route-open) ever reapplies a stale offset. Both refs live only in `App`'s own in-memory state — nothing is persisted to IndexedDB or any storage, so a full reload always starts Routes at the top, and this has no effect on the restored-ride map camera contract, GPS state, progress restoration, or the Resume-riding route framing.
    - Automated coverage: `App.test.tsx`, `src/ui/library/RouteLibrary.test.tsx`, a new `src/ui/shared/useResetScrollForNewRideContent.test.ts` (needed because `App.test.tsx` cannot mount a real `PlanningScreen` in jsdom — see that file's own "Deliberately excludes 'Plan'" comment — so the Planning-save leg of this contract is proven at the unit level), plus a new `e2e/routeLibraryScroll.spec.ts` and one new assertion added to `e2e/planning.spec.ts`'s existing save-and-reopen test. `App` also gained a new optional `mapFactory` prop, forwarded only to `RidingScreen`, purely so these tests can inject a stub map and avoid mounting a real, unmocked MapView in jsdom — production's `main.tsx` passes no props and is unaffected. Manually verified on the deployed iPhone PWA (see "Manual acceptance status" above, now in `docs/project/current-status.md`).

## Item 19 — Route library search and sort — done

_Category: Navigation and library interface_

19. **Route library search and sort — done**
    - `RouteLibrary` gained a session-only name search (a labelled `<input type="search">`, "Search routes") and a persistent sort control (a labelled `<select>`, "Sort by": `Most recent`/`Name A–Z`). Search matches a trimmed, case- and diacritic-insensitive substring anywhere in a route's name only — never fuzzy, never tags/folders/route-content — via Unicode NFD normalisation (e.g. a query of "hutte" matches "Hütte"). Both are computed by a new pure `src/ui/library/routeLibraryView.ts` (`normalizeSearchText`/`filterRoutesByName`/`sortRoutesForLibrary`/`selectRouteLibraryView`), applied to whatever `listRoutes()`'s own liveQuery returns, never assumed to already match — the pipeline is always normalise query → filter → sort → render, and neither function mutates its input array. `Most recent` preserves `PlannedRoute.createdAt` descending exactly as before (opening/exporting/renaming a route never makes it "recent"; no `updatedAt`/last-opened field was added); `Name A–Z` uses a module-level `Intl.Collator("en-GB", { sensitivity: "base", numeric: true })` (a pinned locale, matching `providerKeyStatus.ts`'s existing `DATE_TIME_FORMATTER` convention, so ordering is deterministic across machines) so e.g. "Route 2" sorts before "Route 10". Both orders are tie-broken deterministically by route id.
    - Sort choice is the first Route-library-specific durable preference: a new singleton `routeLibraryPreferences` table (`id: "route-library"`, schema `version(4)`, purely additive like v1→v2→v3, no `.upgrade()` needed) holds a plain `sortOrder` string; `src/storage/mapping.ts`'s `RouteLibrarySortOrder`/`isRouteLibrarySortOrder`/`fromStoredRouteLibraryPreferences` guard-validate it on read (mirroring `fromStoredPlanningDraft`'s profile guard, not `fromStoredPlanningPreferences`'s bare `??`, since this is a closed enum) and default an absent or corrupt value to `most-recent`. `src/storage/routeLibraryPreferencesRepository.ts` mirrors `planningPreferencesRepository.ts` exactly. `RouteLibrary` waits for both the routes liveQuery and this preference to resolve before rendering any list or the toolbar, avoiding a "Most recent, then jump to Name A–Z" flash; the `<select>`'s value is always bound directly to the live-query-resolved preference, never optimistic local state, so a failed or in-flight save can never look like it succeeded — on failure it keeps showing the last-persisted value alongside a `role="alert"` message, with a `role="status"` "Saving…" note only while a write is genuinely in flight.
    - The search query is deliberately not persisted to IndexedDB — it's transient view state that may clear on a full reload/relaunch. Within the current app session it survives navigating away from Routes to any other screen and back, via a new `routesSearchQueryRef` owned by `App.tsx` (a `RefObject<string>`, continuously synced on every keystroke rather than captured once like `restoreScrollYRef`, since — unlike the Riding-open path — there is no single "about to navigate away from Routes" call site covering every destination; `MainNavigation`'s `onNavigate` goes straight to `setScreen`). `RouteLibrary` hydrates its local `searchQuery` state from this ref exactly once per mount via a `useLayoutEffect` with an empty-ish dependency array (never a lazy `useState` initializer, for the same `react-hooks/refs` reason `restoreScrollYRef` documents), and never nulls the ref afterwards.
    - The existing scroll-restoration effect and `computeFocusRouteIdAfterDelete` (`src/ui/library/routeDeleteFocus.ts`, itself unchanged — it was already order-agnostic) now both operate on the filtered/sorted array actually on screen rather than the raw liveQuery result. Deleting the last visible route under an active filter focuses the search field rather than the Routes heading. A rename that causes the renamed route to drop out of the active filtered view (and so unmount its own row, stranding any focus inside it) is handled by a small, explicitly-scoped effect — tracking the just-renamed id and comparing the previous rendered view to the new one — rather than a generic "was focus just here" check, since by the time any effect can observe a removed row the browser has already moved focus to `<body>`, making rename-caused and delete-caused disappearance indistinguishable at that point; a `stillExists` guard defers to the delete flow's own focus handling if the same route was deleted before the rename's write round-tripped. Reordering under `Name A–Z` needs no equivalent code: `RouteListItem` stays keyed by `route.id`, so React's key-based reconciliation moves the existing DOM node (and any focus within it) rather than unmounting it.
    - No fuzzy search, tags, folders, route-content search, remote search, analytics or new dependency; `Intl.Collator`/Unicode `normalize("NFD")` are Web-platform-native. No change to import, export, inline rename/delete, route selection or GPX/Riding behaviour. Automated tests (storage mapping/repository/migration, pure view-logic unit tests, `RouteLibrary`/`App` component tests, and a phone-viewport `e2e/routeLibrarySearchSort.spec.ts`) pass; real-device iPhone verification of search, reload persistence, narrow-viewport layout and returning from a searched/sorted route is still outstanding — do not treat this item as manually verified until that check has actually been done.

## Item 20 — Route pinning — done

_Category: Navigation and library interface_

20. **Route pinning — done**
    - Persistent Route Library pinning, exactly as recorded for continuity above: pinned routes form one group, `Pinned`, always shown above unpinned routes; within `Pinned` the most recently pinned route is always first, ordered purely by pin recency; the existing persisted `Most recent`/`Name A–Z` preference applies only within the unpinned group (`Other routes`) and never reorders `Pinned`. `PlannedRoute` gained one new optional field, `pinnedAt?: string | null` (`src/domain/types.ts`) — an ISO timestamp when pinned, `null`/absent when not, documented as local Route Library metadata rather than route geometry or provenance, never read by `gpx/`, `routing/` or `navigation/`. Because it is optional and never indexed, it needed no Dexie schema version bump — the exact same precedent already established for `manoeuvreProvenance`/`surfaceSummary` on `PlannedRoute` and the camera/wake-lock fields on `StoredRideState`: Dexie's `version().stores()` only lists indexes, so a plain new field on an existing row is handled entirely by explicit defaulting in application code, not a schema migration.
    - `src/storage/routesRepository.ts` gained `pinRoute(id, clock: Clock = systemClock)` (writes `pinnedAt: new Date(clock.now()).toISOString()`) and `unpinRoute(id)` (writes `pinnedAt: null`, not `undefined`, the correct member of the `string | null` union for Dexie's `update()`), mirroring `renameRoute`'s own `db.routes.update(id, {...})` shape and `src/gpx/importGpx.ts`'s existing `(file, clock: Clock = systemClock)` convention so pin timestamps are testable without `vi.setSystemTime`. Deleting a route naturally deletes its pin metadata with it — there is no separate pin table to leave an orphan row in. GPX export/import were confirmed structurally incapable of touching `pinnedAt` (`exportGpx.ts`/`normalizeGpx.ts` both name every field explicitly, with no `{...route}` spread anywhere in either file) and needed no code change, only regression tests: a pinned route exports with no pin metadata in the GPX, and any reimported route — including a re-export/reimport of a previously pinned one — is unpinned. Pin state is specific to this device's local library, exactly like sort order and search.
    - `src/ui/library/routeLibraryView.ts` gained `isPinnedRoute` (a route counts as pinned only when `pinnedAt` is a string that parses to a finite timestamp — missing, `null`, or malformed local data is treated as unpinned rather than destabilising ordering) and `selectRouteLibraryGroups(routes, query, sortOrder): { pinned, unpinned }`, superseding the previous flat `selectRouteLibraryView`: normalise the query → filter by name (the existing, unchanged `filterRoutesByName`) → partition into pinned/unpinned by `isPinnedRoute` → sort pinned by `pinnedAt` descending (id-tiebroken, never consulting `sortOrder` at all, so a sort-order change can never touch `Pinned` even in principle) → sort unpinned via the existing, unchanged `sortRoutesForLibrary`. The partition is exhaustive and disjoint by construction (a plain filter/predicate split), proven directly by a dedicated unit test rather than left implicit.
    - `RouteLibrary.tsx` derives `groups = selectRouteLibraryGroups(...)` and a flattened `viewRoutes = [...groups.pinned, ...groups.unpinned]` kept feeding exactly what it already fed before this slice — `computeFocusRouteIdAfterDelete`, the rename-orphan-focus effect, and scroll-restoration gating — so deletion focus continues to use the full displayed pinned-then-unpinned order with no change to `routeDeleteFocus.ts` itself. Rendering splits into up to two `<h2>`-headed `<ul className="route-list">` groups — `Pinned` shown only when non-empty, `Other routes` shown only when both groups are non-empty — so with zero pinned routes the DOM is byte-for-byte identical to before this slice. A new optional `clock?: Clock` prop (default `systemClock`), mirroring `PlanningScreen`'s own existing convention, lets tests assert deterministic newest-pinned-first ordering without depending on real clicks landing in different milliseconds.
    - Pin/unpin writes are never optimistic: because `routes` is a Dexie live query, a card only ever visually moves once the write has actually committed and the query re-fires, so "never move a card before the write succeeds" and "keep the previous group/order on a failed write" both fall out of the existing architecture with no extra bookkeeping — a rejected write simply never touches `routes`. A per-route `pinPendingIds` set disables that route's own toggle and blocks a duplicate submission while its write is in flight; a per-route `pinErrors` map shows a concise `role="alert"` message on failure. Because pinned and unpinned render as two separate `.map()`-produced arrays under two separate `<ul>` parents, a route moving between them is an unmount-then-mount pair even though its `key` is unchanged — React does not carry a component's DOM identity, and therefore focus, across that move the way it would for a plain reorder within one array. A `pendingPinFocusIdRef` set on a successful write, consumed by an effect keyed on `groups`, explicitly refocuses the route's own toggle at its new position (an accepted, narrow race — pinning a second route before the first one's effect has fired overwrites the pending target — documented the same way as the pre-existing `lastRenamedIdRef` rename-orphan-focus race, and equally sub-perceptible in practice).
    - `RouteListItem.tsx` gained one compact, icon-only pin toggle in the title row's upper-right, via a new `.route-card-title-row` (`display: grid; grid-template-columns: minmax(0, 1fr) auto`, plus `min-width: 0` added to the existing `.route-card-title` rule) so a long/wrapping route name never collides with or displaces the fixed-size toggle. A new project-owned, dependency-free `src/ui/library/PinIcon.tsx` (mirroring `ManoeuvreIcon.tsx`'s exact convention — `aria-hidden`, all styling inline since Vitest's `test: { css: false }` never loads `index.css`) renders an outline pushpin when unpinned and a filled one when pinned, never rotated; `.route-pin-toggle`/`.route-pin-toggle.is-pinned` add only the real CSS deltas on top of the global `button` rule's own inherited 44px touch target, mirroring `.waypoint-row-icon-button`'s override-only-the-delta convention — the pinned state additionally gets a pale `--colour-accent-soft` surface and a stronger accent ring, mirroring `.main-nav-button[aria-current="page"]`'s soft-surface-plus-ring convention, so pinned state is never colour alone. `aria-pressed`/a full route-scoped accessible label (`Pin Evening loop`/`Unpin Evening loop`) carry the state explicitly; no `Pin`/`Unpin` text is ever shown inside the button itself. The toggle is deliberately **not** disabled merely because that row's delete confirmation is open (only while a pin write is genuinely in flight, or while deleting) — clicking it while a confirmation is open cancels that confirmation first via a local `handlePinClick`, mirroring exactly where the equivalent Rename-cancels-delete logic already lived in this same file (`openRename`), rather than lifting that per-row concern into `RouteLibrary`. The toggle is unavailable during inline rename with no extra logic at all, since it lives inside the same "not renaming" fragment as the rest of the card's normal-state markup.
