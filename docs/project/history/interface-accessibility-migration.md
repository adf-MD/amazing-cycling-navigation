# Interface and accessibility — full visual-migration narrative

This is the complete, byte-preserved seven-slice UI visual-migration narrative that used to live inline under root `CLAUDE.md`'s "Interface and accessibility" section. The root file keeps the durable design-token/button/layout facts (reproduced below for this file's own self-containedness) and a short summary of the outcome, with a pointer here for the full slice-by-slice detail — including a real CI-driven MapLibre gesture-bug fix discovered during the fifth slice. See [README.md](README.md) for the documentation map.

## Design foundation (also present, unchanged, in root `CLAUDE.md`)

- Optimise Riding mode for a small phone mounted on a bicycle, bright daylight, gloves, vibration, and brief glances.
- Assume road-bike speeds: prioritise advance visibility, low interaction and rapid comprehension over dense information.
- Use large touch targets, high contrast, restrained motion, and few controls.
- Do not rely on colour alone for route or warning status.
- Use metric units throughout.
- Use British spelling in user-facing text and documentation.
- Make empty, loading, stale, offline, permission-denied, and provider-failure states explicit.

## The seven-slice migration narrative

- `src/index.css` carries a small shared visual foundation: spacing (`--space-4` through `--space-32`), two radius tokens and one restrained shadow token, and colour roles including a new `--colour-info`/`--colour-info-soft` for informational/location cues, independent of any map colour (map/route/gradient/warning colours are unchanged). A small button vocabulary (`.btn-primary`/`.btn-secondary`/`.btn-danger`, the latter deliberately quiet/outlined rather than a large solid red) and layout classes (`.screen`, `.stack`, `.row`) sit on top. Routes (`RouteLibrary`/`RouteListItem`) is the first screen migrated to this foundation, presented as route cards rather than a bullet list; other screens keep their existing internal layout for now and are expected to migrate incrementally in later slices, per this file's own smallest-coherent-vertical-slice discipline. A second slice migrates Settings to this same foundation and completes Future-backlog item 15 (Avoid ferries by default). Settings is restructured beneath its single `<h1>` into two `.panel` sections — a new **Route planning** panel and the existing **OpenRouteService** panel (both `h2`, unchanged heading level) — plus a native, collapsed-by-default `<details className="settings-disclosure">` ("How the key and route data are used") inside the OpenRouteService panel, holding the two longer explanatory paragraphs (the HeiGIT data-flow sentence, and the "not encrypted"/clearing-site-data sentence); the sign-up sentence and link, the verification-status line, the offline notice, and any rejected/quota-limited/unavailable status all stay outside it, always visible, never concealed inside a closed disclosure. The Route planning panel's only control is a new **Avoid ferries by default** setting: a real `<input type="checkbox">` (`.setting-row`, wrapped in a `<label>` so the whole row activates it, 44×44 px minimum via `--touch-target-min`, with an explicit `aria-label` so its announced name stays just the concise title rather than the row's hint sentence too) whose checked state is bound directly to a live-query-derived persisted value from a new `getPlanningPreferences()` — never a separate optimistic local flag — so a save in flight, or one that fails, can never make the control appear to have already succeeded; on failure the checkbox simply keeps showing the last-persisted value (nothing was ever changed locally) alongside a small `role="alert"` message, and a `role="status"` "Saving…" note mounts only while a write is genuinely in flight. Backing storage is a new singleton `planningPreferences` table (schema `version(3)`, id `"planning"`, purely additive like v1→v2, no `.upgrade()` needed): `src/storage/mapping.ts`'s `fromStoredPlanningPreferences` defaults a missing row's `avoidFerriesByDefault` to `true`, and `src/storage/planningPreferencesRepository.ts` exposes `getPlanningPreferences()`/`savePlanningPreferences(...)`. `PlanningScreen.tsx`'s existing one-time draft-hydration effect is unchanged for a restored draft (one or more waypoints already present); along its existing "genuinely fresh" branch only (no draft row at all, or a draft row with zero waypoints — the same boundary the debounced autosave effect already used), it now additionally fetches this default and seeds `avoidFerries` from it exactly once. From a draft's first autosave onward it is fully self-contained: changing the Settings default afterwards never rewrites it, never recalculates its route, and never touches an already-open draft or a saved route. Planning's previous directly editable "Avoid ferries" checkbox is removed and replaced with concise read-only text ("Ferries: avoided for this plan" / "Ferries: allowed for this plan") plus a "Change default in Settings" button reusing the existing `onNavigateToSettings` prop — no new navigation plumbing. New shared classes: `.panel` (a neutral bordered/elevated surface, mirroring `.route-card`), `.status-row`/`.status-row--info` (the latter the first real use of `--colour-info`/`--colour-info-soft`, applied only to the offline notice), `.setting-row`/`.setting-row-checkbox`/`.setting-row-text`/`.setting-row-title`, `.field-hint`/`.field-error` (also reused by Planning's read-only ferry-policy text), and `.settings-disclosure`; `ConfirmDialog.tsx` (still Settings' only consumer) picks up the existing `.route-delete-confirm`/`.route-delete-confirm-actions`/`.btn-secondary`/`.btn-danger` classes rather than new ones, since its visual need is identical to the existing route-deletion confirmation. A third slice ("Active Riding glance hierarchy") migrates `RidingScreen` itself onto the shared foundation (`.screen`/`.screen-title`, the latter gaining `overflow-wrap: anywhere` so a long route name always wraps rather than overflowing) and restyles only its active-riding states (watching, error, stale, off-route, active-climb) — the pre-ride/idle prompt, the offline banner, and `RidingClimbSelector` are deliberately left untouched, matching this slice's presentation-only scope. `RidingWakeLockControl` keeps its existing DOM-order-before-the-title/non-pushing-popover behaviour and just gains a small, muted `.ride-wake-lock-control` treatment. A route's distance/ascent moves out of a standalone paragraph into a compact `.route-card-meta`-styled line directly under `<h1 className="screen-title">`, deliberately reusing Route Library's own meta-line class rather than a near-duplicate. The "On route"/GPS-accuracy/"Remaining" paragraphs combine into one new `src/ui/riding/RidingStatusStrip.tsx` — status, then remaining distance, then GPS accuracy/staleness (a genuine reorder from before) — a small presentational component receiving only the already-derived `offRouteLevel`/`distanceRemainingMetres`/`accuracyMetres`/`isStale`/`fixAgeMs`, never touching off-route/stale computation; "Off route" keeps `role="alert"`, "On route"/"Possibly off route" stay `role="status"`, and the latter two additionally get a non-exclusive `--colour-warning`/`--colour-danger` text-colour cue (the app's first real use of `--colour-warning`) — the unchanged wording alone still carries the distinction. The waiting-for-fix message and the geolocation-error block (same retry button) stay inline in `RidingScreen.tsx`, gaining `.status-row` and a new `.ride-alert-panel` class respectively, rather than folding into `RidingStatusStrip`, since neither carries the same already-derived-value shape. `RidingNextManoeuvrePanel` moves from fully inline styling to `.ride-manoeuvre-card`/`.ride-manoeuvre-icon`/`.ride-manoeuvre-text`/`.ride-manoeuvre-instruction` classes, while its urgency-driven distance paragraph deliberately keeps font-size/font-weight as inline style (same `URGENCY_FONT_SIZE_REM`/`URGENCY_FONT_WEIGHT` values as before) since Vitest's `css:false` test environment cannot verify a class-driven computed style; its urgency-escalation test now locates that paragraph via a new `.ride-manoeuvre-distance` class instead of a fragile `querySelectorAll("p")[1]` index — a selector-only test change, its "never `role=alert`" and "role=status text stays byte-identical across same-urgency rerenders" behaviour is unchanged. Its two "unavailable" messages gain `.status-row` rather than becoming an empty card. The map's previous inline `{height:320, position:"relative"}` wrapper becomes `.ride-map-container` (still exactly 320px pre-ride) plus a `.ride-map-container--active` modifier applied whenever `geolocationStatus !== "idle"`; `MapView`'s existing `ResizeObserver` picks this class-driven height change up with no logic change, proven by a new `e2e/layout.spec.ts` test comparing the map container's and its canvas's bounding boxes before and after Start riding. Real-browser investigation during this slice found that a raw `clamp(280px, 46dvh, 420px)` — the originally intended rule — reproducibly breaks the Follow-location repeat-press-after-a-manual-gesture regression test: certain resulting container heights (unrelated to whether the value is fractional; a whole-pixel 331px was just as broken as 331.1875px) leave MapLibre's own drag-rotate/drag-pitch handler permanently "active" for this route/camera combination, so it never emits `moveend`/`rotateend` and the camera visibly never finishes rotating even though its internal bearing/pitch did change — a genuine MapLibre/CSS interaction, not a test artefact, since the same fixed-pixel drag gesture a rider could plausibly make is what triggers it. The shipped rule therefore snaps to a coarse 20px grid instead of a continuous value — `@supports (height: round(nearest, 46dvh, 20px)) { .ride-map-container--active { height: clamp(280px, round(nearest, 46dvh, 20px), 420px); } }`, behind the plain-`dvh` `@supports` fallback (`clamp(280px, 46dvh, 420px)`) which itself sits behind a flat `340px` fallback, mirroring `.app-shell`'s own documented minifier-safe pattern of separate `@supports`-gated rules — verified directly, via the real drag gesture, against both the default desktop e2e viewport (1280×720 → 340px) and the project's 390×844 mobile viewport (→ 380px); no test currently pins the exact height value itself, only that it differs from the pre-ride height and that the canvas reflows to match it. The North-up/Follow-location buttons move from large inline style objects to `.ride-map-control`/`.ride-map-control--north-up`/`.ride-map-control--follow`/`.is-pressed`, mirroring (not reusing) `.planning-map-control`'s shape/pressed-swap at Riding's own bottom-right position, keeping the same aria-labels/aria-pressed wiring, the same literal `#ffffff` pressed-state text colour, and the Follow button's pre-existing unbolded weight. `RidingClimbProgressPanel`'s long-orphan `className="riding-climb-progress"` finally gets matching CSS (a `.panel`-like bordered card) with no JSX change at all, and now renders immediately before its own detailed chart rather than after it — a presentation-only reorder with no test dependency either way. The Full/2km/5km/10km/Climb buttons keep their exact DOM order and `aria-pressed` source of truth but gain a real `.elevation-window-button` class plus an explicit `.is-selected` toggle (mirroring `.cycling-profile-button.is-selected`/`.route-warning-button.is-selected`, never an `[aria-pressed="true"]` attribute selector), and `.elevation-window-group` gains `display:flex;flex-wrap:wrap` so five buttons never force horizontal scroll on a narrow phone. The chart, climb-progress panel, `GradientColoursDisclosure`, `RouteFeatureDetailsPanel` and `GradientSegmentDetailsPanel` are grouped, together with the elevation-window-group, inside one new unlabelled `.ride-elevation-section` wrapper — outer spacing only, no internal prop/markup changes to any of them. A fourth slice ("Planning workflow organisation") migrates `PlanningScreen` onto the same foundation (`className="screen planning-screen"`), the last of the four screens to move — no routing, map, waypoint, draft, warning, elevation or Save/Export _behaviour_ changed anywhere in this slice, only markup/classes around it. The previous inline `{height:320, position:"relative"}` map wrapper becomes `.planning-map-container`: a flat 340px fallback, then `@supports (height: 44dvh) { height: clamp(280px, 44dvh, 460px) }`, deliberately without a second `--active` modifier — unlike Riding, Planning's map is one continuous workspace with no idle/active transition to key a second height off. Real drag-rotate/drag-pitch gesture verification at this height range, mirroring the third slice's own method, did not reproduce the stuck-gesture MapLibre bug that motivated Riding's `round()`-snapped 20px-grid tier at the time, so that extra tier was not shipped in this slice — see the fifth slice below, where a subsequent CI run proved that omission wrong. The three locate-failed/warning-selected/route-feature-selected blocking messages, previously flow-positioned inside the fixed-height wrapper (where they could overflow below the visible map, the same class of bug `.map-attribution`'s own comment already guards against), move into a new absolutely-positioned `.planning-map-status-overlay`/`.planning-map-status-message`, with byte-identical conditional logic and `role="status"` text. Undo/Redo/Return to start/Add to end become one `.row` toolbar; Return to start alone gains `.btn-secondary` as its sole visual distinction from the other three (never `.btn-danger`, which stays reserved for genuinely destructive actions). `WaypointList` migrates from a per-button inline `TOUCH_TARGET_STYLE` object to real classes (`.waypoint-list`/`.waypoint-row`+`.is-selected`/`.waypoint-row-select`/`-ordinal`/`-label`/`-reorder`/`-icon-button`/`-relocate`, `.waypoint-relocate-button.is-pending`); a row's selected state uses `.main-nav-button[aria-current="page"]`'s richer inset-ring-plus-accent-text treatment rather than the plainer neutral-fill pattern, deliberately distinct from Move/Insert-after's own pending state (the plain neutral variant, matching `.cycling-profile-button.is-selected`) so the two never look identical. Each row gains a purely decorative, `aria-hidden` numbered ordinal badge; the select button's accessible name stays exactly the pre-existing "Start"/"Waypoint N" text, so no query semantics changed. DOM order within a row changes deliberately (select → reorder → delete → conditional Move/Insert-after sub-row, was select → conditional group → reorder → delete) to match the section's own prose ordering; Move/Insert-after stay in their own `role="group"`, continuing the file's original relocate-vs-reorder separation rationale. The empty state changes from "No waypoints placed yet." to "No waypoints yet. Tap the map or use the crosshair button below to add one." Road bike/General cycling becomes an equal-width segmented selector (`.cycling-profile-group` gains `display:flex`, a new base `.cycling-profile-button{flex:1 1 0}` rule added alongside the existing `.is-selected` modifier) inside a new **Route options** `.panel`, alongside the unchanged 0.3.1 read-only ferry-policy readout and a **Calculate route** section restyled as `.btn-primary` with its key-status/error/stale messages gaining `.status-row`/`.field-error` and its own "calculated in sections" explanation moved into a `<details className="settings-disclosure">How recalculation works</details>` — the provider-key status, provider error and stale-result message all stay outside that disclosure, always visible, per this file's own "never hide the current provider error or stale-result message" rule. `RouteSummaryPanel` gains a visible `<h2>Route overview</h2>` and a `.panel`-styled root, while its `aria-label="Route summary"` landmark is deliberately left unchanged — a landmark name and a visible heading serve different navigation purposes, and roughly twenty existing tests query the landmark by that name. Distance/ascent/descent/waypoint-count move into a `.route-summary-metrics` row; the elevation chart, `GradientColoursDisclosure`, `RouteFeatureDetailsPanel` and `GradientSegmentDetailsPanel` are grouped inside a new `.route-overview-elevation-section` wrapper, mirroring `.ride-elevation-section`'s own identical rationale but kept as a separate class, continuing this codebase's convention of not sharing Planning/Riding presentational classes for similar concepts; the surface breakdown becomes a `.surface-summary-grid` (all four categories, including zero/unknown, still always shown); the warnings list gains a conditional `<h3>Route warnings</h3>` (only when `warnings.length > 0`) at the same heading depth as the two shared detail panels' own existing `<h3>`s. None of the warning-selection, map-tap-reveal-and-scroll, `aria-expanded`/`aria-controls`, or surface-detail logic changed. Route name/Save route/Export GPX become a **Save or export** `.panel`, the input gains `.field-input`, and Save/Export gain `.btn-primary`/`.btn-secondary` — `canSaveOrExportPlan`'s gate itself is untouched. `NoApiKeyNotice` gains `.status-row status-row--info` (the second real use of `--colour-info`/`--colour-info-soft`, after Settings' offline notice) and a `.btn-secondary` Open Settings action. A new `.planning-section` class (`max-width: 720px` centred via auto inline margins, gated behind a `min-width: 900px` media query) constrains every non-map section's text measure on a wide desktop browser while the map itself stays full width — a single well-spaced column, not a two-column grid, per this slice's own explicit design-decision record. A fifth, corrective slice reinstates the `round()`-snapped 20px-grid tier the fourth slice's own real-browser verification had concluded was unnecessary: a subsequent GitHub Actions CI run of `e2e/planning.spec.ts`'s "pressing Northwards twice" test failed exactly the way Riding's own investigation predicted — a genuine right-button drag left `data-camera-bearing` stuck at `"0"` because MapLibre's drag-rotate handler never fired `moveend` — at the unsnapped `44dvh` height (≈316.8px on the project's default 1280×720 e2e viewport). Extensive local reproduction attempts (10 unthrottled repeats and 15 repeats under 3× CDP CPU throttling, at the exact CI-matching measured height) did not reproduce the stuck gesture, consistent with the repository's own existing account of this MapLibre behaviour as narrow, environment-sensitive and not reliably reproducible from height alone — so this fix is applied on the strength of the CI evidence and Riding's own already-proven mitigation, not a repeated local reproduction. `.planning-map-container` now mirrors `.ride-map-container--active`'s exact three-`@supports`-tier structure, keeping Planning's own `44dvh`/`460px` numbers. `e2e/planning.spec.ts`'s "pressing Northwards twice" test gains a phone-viewport (390×844) counterpart proving the same manual-drag-then-Northwards contract plus no horizontal overflow and contained map controls at that width, without duplicating the desktop test's full setup. A sixth slice ("Pre-ride route briefing") migrates `RidingScreen`'s idle state onto the same foundation — the one pre-ride path the third slice's own scope note explicitly left untouched. The Start/Resume prompt becomes a `.panel`/`.stack`-based `.ride-start-panel` with a `.btn-primary` `Start riding`/`Resume riding` button; `.stack`'s own default `align-items: stretch` already makes it full width on a narrow phone for free, so the only new CSS is a `.ride-start-panel-button` cap (`align-self: flex-start`, `min-width: 220px`/`max-width: 320px`) gated behind `.planning-section`'s own existing `min-width: 900px` desktop threshold rather than a second breakpoint; `handleStart` itself, its idle-only clear-on-start guard, and the button's accessible text are untouched. The pre-ride map gains a `.ride-map-container--overview` modifier (applied instead of `--active` while idle, never combined with it), a restrained 1px border/`--radius-md`/`--shadow-sm` mirroring `.panel`, deliberately without `overflow: hidden` since `.map-attribution` and any status/alert banner sit absolutely positioned inside the same container; the border's own ~2px content-box shrinkage (global `* { box-sizing: border-box }`) is negligible against the unchanged 320px pre-ride height and leaves `e2e/layout.spec.ts`'s pre-vs-active height comparison unaffected, since `--active` itself gains no border. `RidingClimbSelector` moves onto `.panel`/`.stack` and its own heading moves from `h3` to `h2` — same `id`/`aria-labelledby` wiring, same wording/order/default-to-"All route" behaviour — now that it is one of two top-level pre-ride sections beneath the route's own sole `h1`, per Future-backlog item 6's still-holding "exactly one `<h1>`" invariant; `.recognised-climb-select` gains an explicit `width: 100%` it never previously needed outside a flex/stack ancestor. A new `.ride-profile-panel` wraps the existing, byte-identical `.ride-elevation-section` (chart, `GradientColoursDisclosure`, `RouteFeatureDetailsPanel`, `GradientSegmentDetailsPanel`) beneath a visible `<h2>Route profile</h2>`, but only while idle — implemented as an always-present outer `<div>` whose class and heading child alone are conditional, rather than a ternary between a wrapped and a bare render of the section: the latter would change the rendered tree's depth at the exact moment riding starts, and React's own unkeyed positional reconciliation would then remount the whole chart/legend/detail-panel subtree, silently resetting `GradientColoursDisclosure`'s own uncontrolled `<details>` open state. The stable wrapper keeps `.ride-elevation-section` and everything inside it mounted in place across the Start-riding transition, at the cost of one always-present, unstyled, class-less `<div>` remaining once active — invisible to any class- or role-based query, and not observable in the rendered layout, proven by a new test asserting the section's own DOM node reference is unchanged across Start riding. No geolocation, camera, map-layer, or elevation-analysis behaviour changed anywhere in this slice. A seventh, final slice ("Diagnostics screen readability") migrates `DiagnosticsScreen` onto the same foundation, the last screen to move and completing this visual-foundation migration series — presentation-only, with no diagnostic-capture, redaction, storage-schema, or connection-test logic changed anywhere in this slice. Its System status `<dl>` becomes a new `.diagnostics-definition-grid` (each `dt`/`dd` pair wrapped in its own child `<div className="diagnostics-definition-item">` — valid `<dl>` content per the HTML spec's own div-grouped-terms model, and still adjacent siblings so the existing `nextElementSibling`-based test lookup is unaffected), one column on a phone and two columns behind a new `.diagnostics-section`'s `min-width: 900px` breakpoint — reusing `.planning-section`'s own threshold value but as its own class, since `.planning-section` is documented as Planning-specific and this codebase keeps separate class families per screen for the same visual idea. Build and Active route are the only two values given a restrained `.diagnostics-value--mono` monospace treatment, being the only build-ID/route-UUID-shaped values on the screen. The four top-level sections (System status, Recent errors, Routing diagnostics, Recent map imagery attempts) each become their own `<h2>`-headed `.panel stack diagnostics-section`, mirroring `SettingsScreen.tsx`'s own `aria-labelledby`-per-panel pattern. Recent errors/routing attempts/map attempts move from bare `<ul>` bullet lists to a new `.diagnostics-log-list`/`.diagnostics-log-row` treatment — hairline-separated rows in one bordered/elevated container, mirroring `.waypoint-list`/`.waypoint-row`'s own rationale (a continuous chronological log, not independent items) rather than `.route-list`/`.route-card`'s. The previously bare CORS/502-ambiguity paragraph moves into a collapsed-by-default `<details className="settings-disclosure">Why a fetch can fail before an HTTP response</details>` inside Routing diagnostics, reusing Settings' own disclosure class verbatim; the connection-test result keeps one nested `.diagnostics-definition-grid` (never split into per-value cards), its own and Copy diagnostic report's buttons both gain `.btn-secondary`, and the copy-failure fallback `<textarea>` gains a new `.diagnostics-report-textarea` (composed with `.field-input`; `resize: vertical` and `overflow-wrap: anywhere` only, so it can never be dragged or forced wider than the viewport) plus the app's first monospace font stack. A restrained system-status colour cue was considered and deliberately not shipped: every affected value's own wording ("Offline", "Unavailable", "Denied") already fully carries the distinction, mirroring `.status-row`'s own existing rationale, so this slice adds no new colour role and computes no new health classification.
