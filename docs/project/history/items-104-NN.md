## Item 104 — Preserve route progress through exactly overlapping out-and-back turnarounds — done

_Category: Ride navigation reliability_

104. **Preserve route progress through exactly overlapping out-and-back turnarounds — done** - **Real iPhone field symptom (pre-fix evidence).** On an out-and-back route whose route-before and route-after the turnaround overlap exactly, the app never caught that the rider had reached the turnaround. Continuing physically beyond it in the original direction only ever showed the "Possibly off route" message; turning around and riding home along the coincident return leg instead made the app "go back in time" — displayed progress moved backward instead of continuing forward. This report identifies the pre-fix defect only; it is not evidence that the correction below works on a real device — see the outstanding real-device checklist in `docs/project/current-status.md`. - **Deliberately reprioritised ahead of item 98.** Item 98 (direction-aware active-Riding route-segment layering) is a map-presentation slice whose own contract requires deriving its current/near-ahead overlay from matched canonical route progress, not GPS bearing alone. Building that overlay on top of progress that can run backwards would just make it faithfully highlight the wrong leg. Item 104 is confined to route projection/matching; it adds, reorders or restyles no map layer, and item 98 remains selected next, unimplemented in this slice, and now has a corrected progress input to consume without reopening the matcher (see `docs/project/backlog.md`'s own item 98 cross-reference). - **Fail-first reproduction, measured against unmodified `main`.** A new fixture, `src/test/fixtures/outAndBackCoincidentRoute.ts` (`OUT_AND_BACK_COINCIDENT_ROUTE_POINTS`, ~14 m spacing, ~2099 m per leg, plus a second, deliberately sparse/irregular `OUT_AND_BACK_COINCIDENT_SPARSE_ROUTE_POINTS`, ~320–670 m segments ending in a ~50 m final approach), was built with an EXACT coordinate-for-coordinate retrace of the outbound leg on the return leg — unlike the pre-existing `outAndBackRoute.ts`, whose return leg is deliberately offset ~11 m in latitude (confirmed by direct arithmetic, `0.0001° × 111,320 m/° ≈ 11.13 m`) so its two legs are never tied, which is exactly why it never caught this bug. Two of the required traces genuinely failed against unmodified `src/navigation/projection.ts`, deterministically seeded via a directly-constructed `ProjectionMatch` rather than a fresh reacquire (a fresh whole-route reacquire on this fixture is itself subject to the same ambiguity the fix addresses, since every point on the coincident stretch has a tied mirror somewhere in the array — see the fixture's own module comment):
     - **Trace A** (exact fix at the turnaround, then a fix 20 m onto the return leg): `firstReturnFix.distanceFromStartMetres` measured `2079.32`, required to be greater than `atTurnaround.distanceFromStartMetres` (`2099.32`) — it decreased instead of advancing.
     - **Trace B** (a near-turn fix 8 m short of the turnaround, then a sequence of fixes progressively further along the return leg with no exact apex fix): the first sequence step measured `2074.32`, required to be `>=` the previous step's `2091.32` — it regressed.
     - A third, deliberately constructed "normal forward approach" test (`lastMatch = T − 30`, next fix `T − 20`, both comfortably before the turnaround) did **not** fail against unmodified code — recorded honestly rather than invented, since the pre-fix defect is specifically about resolving the turnaround/return-leg tie, not about ordinary approach. - **Confirmed root cause — with a correction to the original hypothesis.** `src/navigation/projection.ts`'s windowed branch (`projectFixOntoRoute` → `nearestWithinRange`) makes exactly one Turf `nearestPointOnLine` call over the whole ±`WINDOW_RADIUS_METRES` (400 m) window, trusting its single winning candidate unconditionally. Near a turnaround, that window spans both the outbound approach and the return departure (both fall within `[lastMatch.distance − 400, lastMatch.distance + 400]` in cumulative-distance terms, even though they are the same physical line traversed in opposite directions). The installed `@turf/nearest-point-on-line` (v7.4.0, confirmed in `node_modules`) resolves an exact geometric tie via a **strict** `<` comparison (`dist/esm/index.js:80`) — the first-encountered (lowest array index, i.e. outbound) candidate wins on a true tie, and any later exact tie is silently discarded. The original hypothesis was that this would **always** resolve to the outbound occurrence. Direct measurement (see `LATERAL_TIE_TOLERANCE_METRES` calibration below) showed this is not quite right: because the outbound and return coordinates are computed via independently-evaluated floating-point expressions (`0.03 × (i/150)` versus `0.03 − 0.03 × (j/150)`), they are not bit-identical, so which candidate has the marginally smaller computed lateral distance — and therefore wins — is effectively erratic rather than deterministically "always outbound". This is a more precise, and arguably more concerning, characterisation of the field defect than the original hypothesis: the pre-fix behaviour near a turnaround is not simply biased backward, it is unpredictable. - **Why a single split point cannot work — worked counter-example.** Two intermediate designs (splitting the window into two sub-ranges at `lastMatch.pointIndex`, then at the array index nearest to `lastMatch.distanceFromStartMetres`) were tried and rejected before implementation, following review. A single pivot can only separate two tied occurrences into different sub-ranges when it falls _between_ them — but the two tied occurrences near a turnaround are symmetric around the turnaround itself, not around `lastMatch`. Worked example: turnaround `T = 2100 m`, a vertex at `2050 m` (one 50 m segment leading into the turnaround), `lastMatch.distanceFromStartMetres = 2070` (closer to the earlier vertex than to `T`). A fix at the coordinate shared by outbound-`2060` and return-`2140` splits at the nearest-vertex pivot `2050` — **before both tied occurrences** — so both land in the same ("leading") sub-range; that sub-range's own internal Turf call resolves the tie by array order and returns `2060` only, discarding `2140` before any comparison logic runs. The result depends on where `lastMatch` happens to fall relative to nearby vertices, not on the actual route geometry. - **Why gap-size alone cannot justify forward preference — worked counter-example.** An initial decision rule (prefer whichever tied candidate is forward of `lastMatch` whenever the two candidates' route-distance gaps from `lastMatch` differ by no more than a margin) was also rejected. Counter-example: `lastMatch = T − 30` (still 30 m short of the turnaround, ordinary forward approach), next ordinary fix at `T − 20` — tied on this exactly-coincident geometry with its own not-yet-reached return mirror at `T + 20`. `gapTrailing = |(−30) − (−20)| = 10`; `gapLeading = |(−30) − 20| = 50`; difference `= 40`, comfortably within a tens-of-metres margin — wrongly jumping the rider onto the return leg while still on the way out. The root error: `gapLeading − gapTrailing = 2·min(a, b)` (where `a` is how close `lastMatch` was to the crossover and `b` is how close the _new_ fix is) is symmetric in `a` and `b` — small either because `lastMatch` was close, or merely because the new fix happens to be, which does not on its own prove the turnaround was reached. - **The exact correction, in two parts.** `src/navigation/projection.ts`'s windowed branch now, after computing `primary` exactly as before:
     1. `findTiedOccurrences` scans every individual segment in the window (a lightweight two-point `nearestPointOnLine` call each, reusing Turf's own per-segment projection — no new geometry maths), collecting every segment whose own lateral distance is within `LATERAL_TIE_TOLERANCE_METRES` of `primary`'s, and clusters them into distinct **occurrences**. A qualifying segment joins the previous cluster only when it is BOTH array-index-adjacent AND its own matched route-distance is within `OCCURRENCE_SEPARATION_METRES` of the previous one's — array adjacency alone is insufficient, since the last outbound segment and first return segment always share the turnaround vertex and so are always array-adjacent even when they represent two occurrences many metres apart (this specific gap was found and fixed during implementation via a direct debug probe: with adjacency-only clustering, a fix 10.1 m past the turnaround still returned only ONE occurrence, silently discarding the genuinely tied return candidate). If exactly one occurrence survives, `primary` is returned unchanged — ordinary, non-tied fixes are unaffected.
     2. When more than one occurrence survives, `selectAmongOccurrences` picks the occurrence closest in route-distance to `lastMatch` ("continuity-nearest") by default. It only overrides that default when the continuity-nearest occurrence is a **genuine regression** — more than `PROGRESS_EPSILON_METRES` below `lastMatch`'s own distance, not merely equal to or infinitesimally below it — **and** some other occurrence is a **genuine advance** (more than `PROGRESS_EPSILON_METRES` above) whose own gap from `lastMatch` is within `CONTINUITY_PREFERENCE_METRES` of the continuity-nearest occurrence's own gap.

     `findWindowRange`, `isClippedAtEdge`, `nearestWithinRange` itself, and the whole-route reacquire fallback are all byte-for-byte unchanged — this fix is confined to the one call site inside `projectFixOntoRoute`'s windowed branch. - **Three new named constants, each measured, not guessed:**
     - `LATERAL_TIE_TOLERANCE_METRES = 0.01` (1 cm). Calibrated by direct measurement (a dedicated calibration probe, not assumption): across an on-line fix, a mid-segment-interior projection, a fix laterally offset 5 m from the line, and an endpoint-clamped case at the turnaround vertex, plus a sweep over 140 outbound/return mirror pairs, the largest observed lateral-distance delta between two genuinely coincident candidates was `5.7 × 10⁻⁸` m (57 nanometres) — floating-point noise. 1 cm sits roughly five orders of magnitude above that measured floor, and comfortably below `outAndBackRoute.ts`'s own ~11 m offset, which must stay distinguishable, not absorbed into a tie. Handling nearly-parallel-but-physically-distinct geometry (separate carriageways, an adjacent cycleway) is explicitly out of this item's scope and was not, and must not be, smuggled in via a loose tolerance.
     - `CONTINUITY_PREFERENCE_METRES = 30` m. Pinned by TDD against the required traces (Trace B's realistic-sampling sequence, and the "normal forward approach" tests) — related to realistic fix-to-fix route-distance movement at road-bike speeds with ordinary GPS sampling gaps, not GPS accuracy directly. A dedicated boundary test constructs `gapDifference` exactly `±0.1 m` either side of `30` (derived from the constant's own exported value, not a hardcoded literal) and confirms the override fires just under and does not just over — real measurement showed the true boundary is slightly less crisp than the idealised arithmetic suggests (interpolation noise in test-fixture coordinate construction), which is itself informative: even the textbook Trace-A case (`gapDifference = 0` exactly, in principle) measurably fails once `CONTINUITY_PREFERENCE_METRES` is forced to `0` in the negative-control run below, not just Trace B — confirming the constant is more broadly load-bearing than the idealised derivation alone implied.
     - `PROGRESS_EPSILON_METRES = 5` m. Scaled to realistic GPS/coordinate jitter at a stationary or near-stationary fix, deliberately smaller than `CONTINUITY_PREFERENCE_METRES`. A dedicated boundary test constructs a regression magnitude exactly `±0.1 m` either side of `5` and confirms the override fires just over and does not just under.
     - `OCCURRENCE_SEPARATION_METRES = 1` m (a fourth, implementation-level constant, not part of the plan's original three, found necessary during implementation — see the clustering gap above). Kept well under `PROGRESS_EPSILON_METRES`, since a genuine single-occurrence discrepancy between adjacent segment framings is expected to be at most a small fraction of a metre. - **Rejected shortcuts**, per the hand-off's own explicit list, none implemented: a global `Math.max(previous, next)` progress clamp (would leave the matcher stuck forever at the turnaround and corrupt genuine backtracking/reacquisition); always selecting the geographically tied candidate with the largest route distance; always selecting the candidate ahead of `lastMatch` without directional evidence (the rejected gap-size-alone rule, above); GPS bearing as sole authority; suppressing or weakening the `Possibly off route`/`Off route` thresholds; enlarging `WINDOW_RADIUS_METRES` until a fixture happened to pass; source-kind, route-feature-kind or elevation-based special cases; a UI-only correction papering over a wrong navigation core; a production-only testing hook or fixture-specific coordinate exception. - **Accepted, honestly-documented residual ambiguity.** Backtracking that begins very close to the crossover, where the regressing candidate's own gap also happens to fall inside `CONTINUITY_PREFERENCE_METRES`, remains irreducible from route-distance evidence alone — this design deliberately resolves that narrow zone forward, to avoid the strictly worse "goes back in time" symptom. Documented directly in `selectAmongOccurrences`'s own doc comment and exercised (not asserted to a specific winner, since the correct resolution is legitimately boundary-dependent on the pinned constants) by a dedicated "return-vs-backtracking ambiguity characterisation" test on the sparse fixture (`T ≈ 2098`, `lastMatch = T − 27`, tied candidates at `T − 37`/`T + 37`): with the constants above, `gapDifference = 54 > 30`, so the continuity-nearest (regressing) candidate wins — read as "still approaching, wobbled backward" rather than "already turned around", the correct, conservative reading given no other evidence. - **A real, distinct interaction found via the E2E layer, outside item 104's own windowed-branch scope.** While building the required real-browser evidence on a deliberately sparse (100 m-spaced) GPX, a large single fix-to-fix jump (from 600 m to 300 m physical, a 300 m cumulative jump) reproduced the field-class symptom again — but for an unrelated, pre-existing reason: the correct windowed candidate sat at `range.endIndex − 1`, tripping `isClippedAtEdge`'s existing, unmodified "genuinely clipped edge" rejection (item 46's own mechanism, deliberately left untouched by this item), falling through to the whole-route reacquire fallback — which is, by design, still subject to the same Turf tie-break ambiguity this item does not touch.     - **Follow-up (2026-09-04): the first physical acceptance failed, and why.** The correction above shipped as `0.4.8` on automated evidence alone. The user then walked a real, short out-and-back on the installed iPhone PWA and it failed in the field: after turning onto the exactly retraced return leg, committed progress ran **backwards**. Two screenshots one minute apart, both reading `On route` at `GPS ±14 m · Live`, showed the remaining/status line move `0.1 km` → `0.2 km` and the trusted finish cue move **150 m → 180 m**. The route's non-identifying structure: **eight track points, 374.519 m total**, an approach at 0/30.877/38.182/113.689/114.808 m, a **turnaround at 225.313 m**, and a **110.505 m mirrored leg traversed exactly in reverse** (its two shared endpoints byte-identical) before a 38.7 m finish exit. Because the finish manoeuvre sits at 374.519 m, the two cue readings pin committed progress to ≈ `T − 0.8 m` and then ≈ `T − 30.8 m` — i.e. the regression began with the anchor essentially **at** the turnaround, which is precisely where the correction above was expected to work.

    - **Diagnosis was gated on reproduction, not hypothesis.** No production file was edited until the private GPX had been run through the **production** importer (`importGpxFile`) and instrumented traces replayed through the **production** `processFix`/`projectFixOntoRoute`/`classifyFix`. A verbatim JS mirror of `projection.ts`'s private internals was used only to observe occurrences and vary the selection policy, and was validated fix-for-fix against production output first (**0 mismatches** across every trace). Production import confirmed the structure exactly, accepted the geometry digest, and confirmed the route as trusted with six manoeuvres.

    - **Confirmed root cause: rolling-anchor epsilon erosion.** `selectAmongOccurrences` returns the continuity-nearest occurrence immediately unless it is a regression **strictly greater than** `PROGRESS_EPSILON_METRES` (5 m) relative to `lastMatch`; below that the forward override is never even evaluated. That is correct for a single projection, but every accepted match becomes the next fix's own anchor, so the epsilon is applied **per fix and never cumulatively**. At walking cadence each backwards step is roughly 0.5–1.4 m of route distance, so `isGenuineRegression` is never true and the match walks smoothly down the outbound mirror for as long as the rider walks home. The replay reproduced the field numbers directly: from a sampled apex, committed progress and the cue read 150.6 m one fix later and **180.0 m at 30.8 m along the return** — the screenshots' own pair, at ≈ 0.5 m/s. The defect is therefore **cadence-dependent, not short-route-specific**: it reproduces on this project's own dense item-104 fixture at 1.4 m steps and disappears entirely at 7 m steps. Every test written for item 104 above steps 8, 25, 42, 45, 65 or 100 m at a time, which is exactly why none of them could reach this state.

    - **Two competing hypotheses refuted by measurement, not by precedent.** (a) *Tie not detected on diagonal geometry.* `LATERAL_TIE_TOLERANCE_METRES` had only ever been calibrated against constant-latitude fixtures, so it was plausible that two genuinely mirrored candidates on a real diagonal segment might differ by more than 1 cm. Measured on the real route at lateral offsets of 0/1/3/8/14/25 m and at 5/20/55/100 m from the apex, the two occurrences' lateral distances are **bit-identical** (delta exactly `0.000e+0`). Refuted. (b) *Clipped window / whole-route reacquire.* On a 374.5 m route, `WINDOW_RADIUS_METRES` (400 m) always spans the whole route, and `isClippedAtEdge` is structurally false at both edges. Confirmed by direct measurement rather than assumed from item 104's own earlier E2E observation. Refuted.

    - **The correction: an explicit disposition, and a hold in the navigation core.** `ProjectionResult` gains a required `disposition: ProjectionDisposition` (`"resolved" | "tied-sub-epsilon-regression"`, `src/navigation/types.ts`). `projectFixOntoRoute` does not change **what it returns** — the projection remains the honest current geometry, with its own `matchedCoordinate`, `lateralDistanceMetres` and the genuinely selected occurrence's own route distance; nothing is ever recombined from an earlier fix. ## Item 107 — Investigate navigation recovery around overlapping route geometry after suspension — done

_Category: Ride navigation correctness_

107. **Investigate navigation recovery around overlapping route geometry after suspension — done**
     - Origin: the installed-iPhone field test of 10 September 2026 — see [`current-status.md`](../current-status.md) for the dated report. During a route ride, after ACN had been suspended and connectivity had been absent for a substantial period, the resumed position appeared to be matched to the wrong part of overlapping or closely adjacent route geometry.
     - **What is deliberately not claimed, and must not become claimed by implication anywhere downstream of this entry.** ACN is **not** claimed to have failed to recover: the rider may subsequently have seen automatic recovery, or may have pressed the existing retry control, and which of those actually happened was not recorded at the time. The prolonged absence of connectivity is **not** classified as a defect — riding through it is exactly what this application is built to do, and a saved route's line, position, progress and elevation are all designed to work without the network. No root cause is claimed, and nothing recorded below is a diagnosis. What **is** recorded is the incorrect or ambiguous progress match itself, as a correctness observation requiring investigation.
     - Confirmed current implementation, recorded here as ground truth this investigation must reconcile with rather than extend past — and, as with item 59, recorded as fact rather than as an admission of a defect or a request to retune any constant:
       - `src/navigation/projection.ts`'s `projectFixOntoRoute(fixCoordinate, points, lastMatch)` searches a `±WINDOW_RADIUS_METRES` (400 m) window measured in **route-distance** space around the previous accepted match, not in geographic space — that choice is precisely what stops a self-intersection or an out-and-back from snapping to the wrong pass.
       - Within that window it recovers additional near-exact geometric ties (`LATERAL_TIE_TOLERANCE_METRES` = 0.01 m, with `OCCURRENCE_SEPARATION_METRES` = 1 m separating array-adjacent qualifying segments into distinct occurrences) and resolves them in `selectAmongOccurrences`: the continuity-nearest occurrence by `|candidate − lastMatch|` wins by default, and a forward override engages **only** when the continuity-nearest is a genuine regression beyond `PROGRESS_EPSILON_METRES` (5 m), and then only when the advancing candidate sits no more than `CONTINUITY_PREFERENCE_METRES` (30 m) farther than the nearest.
       - The windowed result is **discarded** — falling through to a whole-route search with no continuity protection at all, reported as `reacquired: true` — when the match's lateral distance exceeds `MAX_ACCEPTABLE_LATERAL_METRES` (300 m) or the window is clipped at a genuinely truncated edge.
       - `src/navigation/rideNavigationCore.ts`'s `processFix` anchors every fix on the previous accepted `lastMatch`, and on a `tied-sub-epsilon-regression` disposition holds **both** `lastMatch` and the presentation-only `lastReliableMatch` at their previous values; that hold is bounded by cumulative regression exceeding `PROGRESS_EPSILON_METRES`, not by elapsed time or fix count.
     - Confirmed current restoration path, likewise recorded as ground truth: `src/storage/mapping.ts`'s `fromStoredRideState` rebuilds the projection anchor from the persisted `lastMatchedPointIndex` and `matchedDistanceFromStartMetres` — but **only when `stored.lastFix` is non-null**; otherwise `lastMatch` is `null`, and the first fix after resume therefore takes the whole-route branch rather than the windowed one. The same is true when no stored row matches the open route at all, or when the restoration read throws. `src/ui/riding/useRideNavigation.ts` owns the surrounding lifecycle: the mount/retry restoration effect, the persistence effect that upserts after every accepted fix, and `resumeIfWatching`, which on `visibilitychange`/`pageshow` marks the fix stale and restarts the watch only when the status was already `watching`.
     - The investigation should inspect **how ride progress is restored** and **how candidate positions are selected when route geometry overlaps or revisits the same area**, treating those as two questions that may or may not share an answer. It must preserve valid progress continuity, must avoid an implausible jump to another occurrence of the same geometry, and must add discriminating automated evidence **before** any matching behaviour is changed — a test that passes equally with and without the change proves nothing, per this project's repeated negative-control discipline.
     - If the original failure cannot be reproduced, record that limit honestly and derive tests from the confirmed state transitions above rather than inventing certainty. A closure of the "investigated, not reproduced" kind is an acceptable outcome for this item, exactly as it was for item 66; a speculative fix on unreproduced evidence is not.
     - Cross-references, none of which is reopened or weakened by this item: item 104 ([`items-104-NN.md#item-104`](items-104-NN.md#item-104)) fixed a genuinely confirmed exact-overlap turnaround defect and carries the most directly relevant precedent — including its central lesson that the defect was **cadence-dependent, not short-route-specific**, and that two plausible competing hypotheses were refuted by direct measurement rather than by precedent. Item 66 ([`../current-status.md#item-66`](../current-status.md#item-66)) is the standing example of a camera-correctness field symptom that closed without reproduction.      - **Implementation (10 September 2026, `0.4.24`).**

       - **The observation reproduced, and the mechanism is a boundary item 104 had already documented and deliberately left — not a new discovery.** No production code was touched until a deterministic reproduction existed. `src/navigation/projection.ts`'s windowed branch is thoroughly protected against exactly this ambiguity, because item 104 gave it `findTiedOccurrences` + `selectAmongOccurrences`. Its **whole-route reacquire fallback was not**: `lastMatch` was in scope, still perfectly good evidence, and simply discarded, leaving a single Turf `nearestPointOnLine` call to resolve any geometric tie by its own internal strict-`<` comparison — i.e. by **array order**. Item 104's own entry above records this twice, as scope it did not take: a probe reproducing `reacquired: true` "resolved to the wrong, `299.66`-distance occurrence", and its Limitations' "a single whole-route reacquire … still moves committed progress for that one fix … observed in the probe as a one-fix jump of about 187 m". The 10 September field observation is that boundary reached by an ordinary suspension.
       - **How a suspension reaches it.** Suspension stops fixes; `useRideNavigation`'s `resumeIfWatching` marks the fix stale and restarts the watch, and a genuine reload restores the anchor through `fromStoredRideState` and waits for an explicit Resume. Either way the rider has kept riding, so the first fresh fix can land far outside the ±`WINDOW_RADIUS_METRES` (400 m) route-distance window. The windowed match is then rejected on lateral distance (measured at **461.85 m**, against `MAX_ACCEPTABLE_LATERAL_METRES` = 300 m) and the whole-route search runs with no continuity at all. Because `classifyFix` returns `"untrusted"` for any reacquire, `nextOffRouteState` leaves the level untouched and `processFix` adopts the match into **both** `lastMatch` and `lastReliableMatch` — so remaining distance, remaining ascent and the trusted finish cue all move together, in one fix. The wrong anchor is then self-sustaining: every following windowed match tracks the wrong leg.
       - **Confirmed, before any edit, on this repository's own fixtures.** On `OUT_AND_BACK_COINCIDENT_ROUTE_POINTS` with an anchor 2500 m in on the exactly retraced return leg and a fresh fix genuinely ~859 m further along that same leg, unmodified `e63dc82` returned **839.728 m** instead of **3358.912 m** — progress **2519.18 m backwards**, onto the outbound mirror. On `CLOSED_LOOP_ROUTE_POINTS`, an anchor 2500 m round a 3623.3 m loop with a fix exactly at the shared start/finish returned **+0** — progress collapsing to the start line at the moment of finishing. That last case is precisely the risk `isClippedAtEdge`'s own doc comment names ("a whole-route reacquire that can snap onto the geographically coincident start instead") and had no test.

- **Why stacking alone was not enough.** With `z-index: 3` and nothing else, a marker centred on the button's top border still protrudes 13px and butts directly against it — the "badge attached to the control" appearance the field report actually described. `box-shadow: 0 0 0 var(--space-4) var(--colour-bg)` adds a 4px opaque band in the control's own background colour. It is part of the button's own box decoration, so it paints at the same z-index with no extra element, no wrapper and no layout change; and because a box-shadow is never hit-testable, the map stays reachable immediately outside the button instead of gaining an invisible blocking layer. Both halves are separately load-bearing — negative controls 1 and 2b below break exactly one each.

- **No `max-width` was added, because measurement said none was needed.** An absolutely positioned shrink-to-fit box with `left: 50%` and no `right` can never grow past the remaining half of its containing block, so the longest label `describeCrosshairAction` can produce (`Insert after waypoint N`) wraps instead of overflowing. Measured at 390x844: 179px wide at ordinary text, 180.3px at 200% browser text with `scrollWidth === clientWidth` (178 = 178, no clipping) and the control's right edge at 285px against a 390px viewport. The conditional `max-width` the plan allowed for was therefore dropped rather than added speculatively.
