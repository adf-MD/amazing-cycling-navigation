## Item 30 — Planning's draft-autosave can race a just-completed Save, briefly resurrecting a cleared draft — done

_Category: Ride lifecycle_

30. **Planning's draft-autosave can race a just-completed Save, briefly resurrecting a cleared draft — done**
    - Found while hardening `e2e/editRouteAsPlanningCopy.spec.ts`'s own coverage (item 26 above [docs/project/history/items-06-29.md]): `PlanningScreen.tsx`'s debounced draft-autosave effect (900ms, rescheduled on every waypoint/routeName/avoidFerries/profile/editCopyMeta change) and `handleSave`'s own `saveRoute()` → `clearDraft()` → waypoint-reset promise chain both wrote to the same singleton `planningDrafts` row independently, with no explicit cancellation between them beyond the effect's ordinary dependency-array cleanup. If an autosave timer already pending from an earlier edit (e.g. typing the route name just before pressing Save) had not yet fired by the time `handleSave` ran, and it fired after `clearDraft()` resolved but before the post-save waypoint-reset re-render had caused React to run the effect's own cleanup, the stale timer's callback could write the pre-save waypoints back into the just-cleared draft row. Observed directly under heavy parallel e2e load — rare, never reproduced in an ordinary interactive session — and previously worked around, not fixed, by an explicit `page.waitForTimeout(1_200)` in `e2e/editRouteAsPlanningCopy.spec.ts` before every Save. Distinct from item 31 below, which this slice leaves entirely unmodified: item 31 protects autosave against a still-loading/failed hydration read; this item coordinates autosave against a concurrent explicit Save.
    - Fixed by four small coordination primitives added to `PlanningScreen.tsx`, declared together immediately before the autosave effect: `saveTimeoutRef` (`useRef<number | undefined>`, mirroring `usePlanningRoute.ts`'s own `debounceTimeoutRef` shape) is the one synchronously-reachable handle for whichever autosave timer is currently scheduled, written by the effect and read/cleared by `handleSave`; `saveGenerationRef` (`useRef(0)`, mirroring `hydrationGenerationRef`'s existing idiom) is bumped at the start of every `handleSave` attempt and in a new unmount-only cleanup effect, and is checked by both the autosave timer callback and `handleSave`'s own `.then`/`.catch` continuations before they touch any state; `isSavingRef` (`useRef(false)`) is a synchronous re-entrancy guard checked+set as the first lines of `handleSave`, mirroring this same file's existing `isLocatingRef` rationale that a React state check alone isn't synchronous enough to block a rapid second click; `isSaving` (`useState(false)`) is the user-visible counterpart, added to the autosave effect's own gate and dependency array (`if (hydrationStatus !== "ready" || isSaving) return;`) and used to disable/relabel the Save button.
    - `handleSave` now synchronously cancels the pending timer (`window.clearTimeout(saveTimeoutRef.current)`) and bumps+captures the generation before any `await`/`.then` begins — closing the race entirely rather than narrowing it, since the only timer that could ever race a Save is the one that existed at the exact moment Save was clicked (the autosave effect's own dependencies provably don't change during the async gap, and effects only run at commit time). On failure — either `saveRoute` or the explicit `clearDraft` rejects, a single shared `.catch()` covering both and preserving existing partial-failure semantics with no cross-store rollback attempted — nothing was reset, so `isSaving` flipping back to `false` re-arms the autosave effect against current, live render state with no snapshotting. On success, the post-reset render re-arms the effect with `state.present = []`, so any further "autosave" is a harmless, idempotent `clearDraft()` call, never a resurrection. The Save button gained `disabled={!canSaveOrExport || isSaving}` and an in-flight `"Saving…"` label, matching this codebase's existing "Saving…"/"Deleting…" button vocabulary (`RouteLibrary.tsx`, `SettingsScreen.tsx`, `RouteListItem.tsx`).
    - Automated coverage: a new, dedicated `src/ui/planning/PlanningScreen.saveAutosaveRace.test.tsx` (mirroring `PlanningScreen.draftHydration.test.tsx`'s own fake-timer/controlled-promise conventions, plus a new mock of `routesRepository.ts`'s `saveRoute`) proves, deterministically: a pending autosave timer is cancelled before it can fire when Save is clicked just ahead of it; no autosave write occurs for the whole successful in-flight window and the draft is never resurrected afterward; a rapid double Save click issues exactly one `saveRoute`/`clearDraft` pair; the button shows `"Saving…"` and disables while in flight; a rejected `saveRoute` resumes autosave with the current (unreset) in-memory plan; a rejected explicit `clearDraft` (with `saveRoute` resolved) does the same, documented as accepted partial-failure semantics; a Save attempt's continuation discards itself if it resolves after unmount; a pending autosave timer never fires after unmount; ordinary post-hydration autosave is unchanged; and item 31's failed-hydration no-write invariant still holds. `PlanningScreen.test.tsx`'s two existing real-Dexie Save-click tests (`"saving clears the draft…"` and `"clears the edit-copy notice once the copy is saved"`) were extended with an edit-the-route-name-then-immediately-click-Save sequence followed by a real 1,100ms wait, re-asserting `getDraft()` is still `undefined` after the wait — an integration-level proof alongside the mocked unit-level one.
    - `e2e/editRouteAsPlanningCopy.spec.ts`'s `planAndSaveTwoWaypointRoute()` no longer waits 1,200ms before Save; it clicks Save immediately after filling the route name and asserts, via a new `readPlanningDraftRow` export added to `e2e/support/rideStateDb.ts` (mirroring `readActiveRideStateRow` exactly, extended for a third store per this file's own established precedent — see item 25), that the singleton draft row stays `null` after saving. Passed 15/15 under `--repeat-each=3` against the same heavy-parallel-load conditions that originally surfaced the race. The unrelated second `page.waitForTimeout(1_200)` in that same spec file (protecting an intentionally-unsaved, unrelated draft before navigating away to test the replace-draft confirmation dialog) was deliberately left untouched.
    - Version bumped to 0.3.22 (`package.json` and `package-lock.json`'s two matching `version` fields, hand-patched, following the established precedent). Real-device iPhone verification of the new `"Saving…"` button state is still outstanding — do not treat it as manually verified until that check has actually been done.
    - A follow-up, test-only slice removes the four `1_200`ms pre-Save workaround waits `e2e/reverseRoute.spec.ts` had carried since before this fix (in `planAndSaveTwoWaypointRoute`/`planAndSaveClosedLoopRoute` and the two direct Save clicks on a reversed draft), superseding the "left untouched, out of this slice's scope" note above. Each site now clicks Save immediately and awaits a new shared `assertPlanningDraftStaysCleared(page)` helper. This is deliberately stronger than `editRouteAsPlanningCopy.spec.ts`'s own `expect.poll(() => readPlanningDraftRow(page), {...}).toBeNull()` proof: inspection found that pattern's poll runs after an assertion that the "route saved" heading is visible, and `handleSave`'s own promise chain resolves `clearDraft()` strictly before the callback that makes that heading visible fires — so that poll's first check already observes `null` and succeeds immediately, without ever waiting through the ~900ms window in which a _regressed_ (non-synchronous) timer cancellation would let a stale autosave fire and resurrect the row later. `assertPlanningDraftStaysCleared` therefore polls to `null` once and then keeps re-sampling the real row every 150ms across a 1,200ms margin (900ms debounce + 300ms headroom), so a resurrection landing anywhere in that window is still caught; `editRouteAsPlanningCopy.spec.ts` itself was left unmodified (out of this slice's own scope) and still carries the weaker, first-success-only form. A fifth, differently-purposed wait — before `page.reload()` in the "reloading after creating the reverse draft…" test, confirming the seeded draft's fields are genuinely persisted before reloading — was replaced too, since it was never actually a Save-race guard (no Save button is pressed near it): it now polls the real `planningDrafts` row directly (`expect.poll(() => readPlanningDraftRow(page), {...}).toMatchObject({ routeName: ... })`), a strictly stronger, equally small postcondition than the fixed wait it replaced. The one remaining `1_200`ms wait in `reverseRoute.spec.ts` (protecting an intentionally-unsaved, unrelated draft before navigating away to test the reverse-specific replace-confirmation dialog) is unrelated to the Save race and was left unchanged, mirroring `editRouteAsPlanningCopy.spec.ts`'s own identical, still-untouched wait. No production code changed and no version bump was needed, matching this same entry's own established precedent for test-only hardening.
    - A second follow-up, also test-only, supersedes the "still carries the weaker, first-success-only form" note above: `e2e/editRouteAsPlanningCopy.spec.ts`'s own `planAndSaveTwoWaypointRoute` helper now also awaits a locally-copied `assertPlanningDraftStaysCleared(page)` (identical mechanism to `reverseRoute.spec.ts`'s own — poll to `null`, then re-sample every 150ms across the same 1,200ms margin), so it too samples across the complete danger window rather than stopping at the first successful poll. This file's other two Save clicks — saving an edited three-waypoint copy, and saving a GPX-derived copy — were deliberately left unasserted: direct reading of `PlanningScreen.tsx` confirms `handleSave`'s cancellation sequence never branches on `editCopyMeta`, waypoint count or origin, so the one strengthened site already proves the same generic mechanism these other saves also exercise; duplicating full-window sampling there would add ~1.2s per site for no additional coverage. The unrelated `page.waitForTimeout(1_200)` protecting an intentionally-unsaved draft before the replace-confirmation-dialog test remains untouched, since no Save button is involved there. No production code changed and no version bump was needed, matching this same entry's own established precedent for test-only hardening.

## Item 31 — Planning draft hydration/autosave race — done

_Category: Ride lifecycle_

31. **Planning draft hydration/autosave race — done**
    - A dedicated reliability slice, distinct from item 30 above. Evidence-backed root cause, confirmed by direct reading of the pre-fix `PlanningScreen.tsx`: the hydration effect's `getDraft().then(...).catch((error) => { logError(...); setIsDraftHydrated(true); })` set the single boolean coordination signal `isDraftHydrated` to `true` on a **rejected** read — without ever having applied anything, `state.present` was still the pristine empty array. The debounced autosave effect, gated only on `isDraftHydrated`, then saw "hydration complete, zero waypoints" and after 900ms called `clearDraft()` — silently deleting whatever real draft row existed in storage, which had never actually been read. Particularly dangerous immediately after item 26/27's "Edit copy in Planning"/"Reverse route" flows seed that same singleton row before navigating in. Separately confirmed safe and unchanged: `RidingScreen.tsx`'s `performCopyOperation` already `await`s `saveDraft(...)` before calling `onNavigateToPlanning?.()`, and `App.tsx` never mounts `PlanningScreen` before that navigation, so the _seeding_ write itself was never part of the race — the bug was entirely inside `PlanningScreen.tsx`'s own hydration/autosave coordination.
    - New invariant: _Planning must not autosave until the initial draft read has completed successfully and the resolved draft, or the deliberate fresh-plan defaults when no draft exists, has been applied as the authoritative in-memory state._ Implemented as an explicit `PlanningDraftHydrationStatus = "loading" | "ready" | "failed"` state machine (extending this file's own existing `locateStatus` tri-state convention, rather than importing a cross-file pattern) plus a numeric `hydrationGenerationRef` (mirroring `useRideNavigation.ts`'s `watchGenerationRef` idiom) as the sole authority on whether a given `getDraft()`/`getPlanningPreferences()` attempt is still relevant — replacing the old per-effect `cancelled` closure boolean entirely, including the _nested_ fresh-session `getPlanningPreferences()` continuation, not just the outer `getDraft()` one. Both the debounced autosave effect and the existing fresh-session location-framing effect now gate on `hydrationStatus === "ready"` instead of the removed `isDraftHydrated` boolean. A rejected `getDraft()` now sets `hydrationStatus` to `"failed"`, never `"ready"` — nothing was read or applied, so autosave stays genuinely blocked, and no `clearDraft()`/`saveDraft()` call can ever fire from that state. The restore batch (waypoints, route name, avoid-ferries, profile, and — set together, never separately — edit-copy/reversal provenance) is still applied as one atomic React state flush inside a single `.then()` callback, exactly as before; only the completion condition changed.
    - Obsolete/superseded results: the generation ref is bumped both at the top of every effect run (initial mount and every retry, via a `hydrationRetryToken` state bumped by the Retry button) and in the effect's own cleanup, so a result from a prior attempt can never apply after unmount, a retry, or React StrictMode's mount→cleanup→mount double-invocation (`getDraft()` is a read, so a harmless duplicate call; only the winning generation's result is ever applied).
    - "Which state wins" while hydration is loading or has failed: rather than blocking Planning's controls before hydration completes (the map and every interactive control already render unconditionally today, and gating them behind a loading screen would have needed a much larger change, breaking a large fraction of the pre-existing, non-async-aware `PlanningScreen.test.tsx` in the process, for no additional data-integrity benefit over the approach below), a new `hasUserModifiedDraftFieldsRef` — set by a new `noteHydrationOverriddenByUserEdit()` helper called at the top of `dispatchWaypointAction` (the one wrapper every waypoint mutation already goes through) and at the cycling-profile buttons' `onClick` and the route-name input's `onChange` — tells the hydration effect's _restore_ branch specifically to skip re-applying its fields once the rider has already directly changed one of the three restorable fields (waypoints, route name, profile) themselves, rather than silently overwriting their edit; `hydrationStatus` still transitions to `"ready"` either way, so autosave is unblocked for whichever state — restored or rider-edited — is now authoritative. Separately, the same helper unblocks a permanently `"failed"` status directly (`setHydrationStatus((current) => current === "failed" ? "ready" : current)`), since a rejected read has no pending promise left to ever resolve it any other way, and the rider has now started fresh work that deserves saving.
    - **A real regression found and fixed during this slice's own verification, not merely theorised**: the first implementation made `noteHydrationOverriddenByUserEdit()` unconditionally force `hydrationStatus` to `"ready"` and bump the generation on _any_ pre-ready edit — which broke three genuine, pre-existing tests (`"a genuinely fresh draft (no prior draft row) seeds avoidFerries from the current Settings default"` and its two siblings), all of which place a waypoint via a bare map tap immediately after mount, with no `await` in between, before the fresh-session `getPlanningPreferences()` read has any chance to resolve. The fix: the rider-edit override now only gates the **restore** branch's field-application (which genuinely conflicts with a waypoint/name/profile edit), never the **fresh-session** branch's `getPlanningPreferences()` seeding (which touches only `avoidFerries` and so can never conflict with any of the three fields the override tracks) — the fresh branch is unconditional, exactly as before this slice. This is a stronger, more precise statement of "which state wins" than the slice's own first draft, verified against real, previously-passing product behaviour rather than assumed.
    - Hydration failure shows a concise `.field-error`/`role="alert"` message ("Your saved plan could not be loaded. Nothing in storage has been changed.") plus a `.btn-secondary` "Retry" button (reusing this screen's own existing error/button vocabulary, not Riding's), positioned directly beneath the existing `NoApiKeyNotice`, above the `editCopyMeta` notice. Nothing is ever auto-cleared from storage on failure. The Retry button itself sets `hydrationStatus` back to `"loading"` directly in its own `onClick` before bumping `hydrationRetryToken` — mirroring `handleLocateMe`'s own existing convention of setting status in the triggering event handler rather than inside the effect it kicks off, which also avoids a `react-hooks/set-state-in-effect` lint violation a synchronous `setHydrationStatus("loading")` at the top of the effect body would otherwise trip. A separate, non-blocking `role="status"` "Loading your plan…" message shows only while `hydrationStatus === "loading"` — additive, and in production typically imperceptible, since IndexedDB reads normally resolve in low single-digit milliseconds.
    - Out-of-order autosave writes (this slice's own required audit): two new characterization tests in `planningDraftRepository.test.ts` prove `saveDraft`/`clearDraft` calls issued back-to-back with zero awaited gap between them still commit strictly in call order against this repository's real Dexie/fake-indexeddb stack — same-object-store readwrite transactions are queued and committed in request order by the IndexedDB spec itself. This closes the audit for the mechanism this slice touches (a single debounced timer per mount, cancelled before a new one is scheduled, so only one `saveDraft`/`clearDraft` call is ever in flight from the autosave effect itself) — **not a fix**, positive regression coverage for already-safe behaviour. It does **not** address item 30 above, which remains a separate, open, unfixed race.
    - Automated coverage: a new `src/ui/planning/PlanningScreen.draftHydration.test.tsx` (deliberately separate from the existing, much larger `PlanningScreen.test.tsx`, which never mocks the draft repository and never uses fake timers — this new file mocks `planningDraftRepository.ts`/`planningPreferencesRepository.ts` and uses `vi.useFakeTimers({ toFake: ["setTimeout", "clearTimeout"] })`, deliberately narrowed to avoid interfering with React's own scheduler, plus manually-controlled promises, to hold a draft read open indefinitely and assert no premature write occurs) covers: no write while an existing-draft read is pending, full restoration of every field (including edit-copy/reversal provenance) once it resolves; fresh-session defaults applied once, then normal autosave; an editable-copy and a reversed-copy draft both surviving a delayed read with zero premature writes and (for the reversed case) zero routing-provider requests; hydration failure blocking autosave and showing the accessible failure state, with a successful retry recovering; a hydration result that resolves after unmount doing nothing; a rider edit landing before a slow restore-branch read resolves taking precedence over that read's own content; the Settings avoid-ferries default still applying even when a waypoint edit lands before the fresh-session preferences read resolves (the regression above, now pinned as an explicit test); and a plain post-hydration edit continuing to debounce-save normally. `e2e/planning.spec.ts` gained one new reload-recovery test for a plain, hand-built (non-edit-copy) Planning draft — the one reload-recovery path not already covered; `e2e/reverseRoute.spec.ts`'s existing `"reloading after creating the reverse draft recovers the draft and notice with no automatic routing request"` test (around line 521) already proves the edit-copy/reverse-seeded reload path and needed no changes, and passes unchanged against this slice's rewritten hydration effect.
    - No routing endpoint/headers/payload/profile, leg caching, GPX behaviour, route-reversal semantics, map camera behaviour, gradient/warning/elevation calculation, saved-route data, service-worker caching, or CI workflow changed. Version bumped to 0.3.19 (`package.json` and `package-lock.json`'s two matching `version` fields, hand-patched, following the established 0.3.17→0.3.18 precedent). This is a pure logic/state-integrity fix with a small, additive accessible-status/error UI; real-device iPhone verification of the new loading/failure/retry UI is still outstanding — do not treat it as manually verified until that check has actually been done.

## Item 34 — iPhone navigation chrome opacity and waypoint-row layout correction — done

_Category: Navigation and library interface_

34. **iPhone navigation chrome opacity and waypoint-row layout correction — done**
    - Presentation-only correction, evidenced on the installed iPhone Home Screen PWA in portrait orientation (screenshots reviewed 2026-08-12). Two related but independently testable defects, both now fixed.
    - **Sticky-header safe-area opacity — evidence-backed root cause.** Follow-up to item 24 (Always-sticky compact primary navigation). `index.css`'s `.app-header--sticky` rule pinned itself at `top: env(safe-area-inset-top, 0px)`, so its own opaque `background` began _below_ the status-bar strip, not at it. `.app-shell`'s own `padding-top: env(safe-area-inset-top, 0px)` only reserves that strip once, at the very start of the document flow; once the page is scrolled past that one-time reservation, nothing continued to protect `viewport-y ∈ [0, inset)` — whatever page content had scrolled to that screen position painted there instead, exactly matching the observed "scrolled content visible through the strip" symptom. `.app-shell` itself has no `background` of its own, so there was no ancestor backstop either.
    - **First attempt, tried and empirically disproven — recorded for anyone revisiting this.** The first fix attempted was a negative-margin trick: give `.app-header--sticky` `margin-top: calc(-1 * inset)` to algebraically cancel `.app-shell`'s own padding-top contribution, keeping `top` unchanged. A minimal, framework-free repro (`position: sticky`, first child, ancestor `padding-top: 59px`, `margin-top: -59px`, `top: 59px`) disproved this directly: the rendered box stayed pinned at `y = 59` at every scroll position, never `y = 0` — Chromium does not fold a sticky element's own negative margin into the "flow position" its stickiness offset is computed from, unlike an ordinary static/relative box (confirmed by the identical repro with `position: static`, which correctly rendered at `y = 0`). This is a genuine browser behaviour, not a spec detail this file got wrong — do not reintroduce a negative-margin cancellation for a sticky element without re-testing it directly first.
    - **Shipped fix.** A new project-owned custom property, `--safe-area-inset-top: env(safe-area-inset-top, 0px)` (`:root`), is shared by `.app-shell` and `.app-header--sticky` so the two always agree and the value is independently testable. `.app-shell` gained `.app-shell:has(> .app-header--sticky) { padding-top: 0; }` — removing the ancestor's top padding entirely whenever a sticky header is present (`:has()` is supported since Chrome 105/Safari 15.4, comfortably below this project's target platforms), rather than trying to algebraically cancel it. `.app-header--sticky` folds that same inset directly into its own `padding-top: calc(var(--safe-area-inset-top) + var(--space-8))` and sets `top: 0` — with no ancestor padding left to overcome, the header's natural flow position already sits at the true viewport top, so `top: 0` needs no offsetting trick and is continuous by construction (re-verified with the same minimal-repro method: zero ancestor padding, sticky `top: 0`, the inset folded into the sticky element's own padding-top, stayed pinned at `y = 0` across every scroll position tested, both at rest and once genuinely stuck). `.main-nav`'s own visual position is unchanged (the same total offset as before, `inset + space-8`, just sourced entirely from the header's own box instead of split between the ancestor and header).
