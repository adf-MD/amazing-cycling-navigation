    - **Implementation.** Combined with item 48 into one slice, as permitted above, since both touch the same action-card JSX region and the geometry/placement coverage for each is easiest to write and verify together. `ConfirmDialog.tsx` itself is unmodified — no new prop, no in-place mode added to the shared component — keeping Settings' key-deletion dialog and Riding's End-ride/Edit-copy dialogs (item 50, not started) completely unaffected.     - **Test-anchor strategy**: no new `data-testid` was added. The "same slot" proof anchors on the "Change" `<details>` element itself, found via its visible text (`screen.getByText("Change", {exact:true}).closest("details").parentElement`, i.e. the `.planning-routing-summary` wrapper reached without ever naming that class in the test) and asserts its `nextElementSibling` holds the trigger when closed and _is_ the `alertdialog` element when open (`toBe`, proving nothing else was inserted) — mirroring this codebase's existing `nextElementSibling`-based precedent for an analogous inline confirmation (see item 50's own text) rather than inventing a new selector convention.

    - Real-browser verification (`e2e/clearPlanningDraft.spec.ts`, a new dedicated phone-viewport test alongside the existing touch-target one): a DOM-structural check (`page.evaluate`, mirroring the Vitest `nextElementSibling` proof) confirms the confirmation occupies the trigger's exact slot when open and nothing else was inserted (`getByRole("button", {name:"Clear draft"})` has count 1, and it's the dialog's own confirm button); the rest of the action card (`Waypoint actions` group, `Calculate route` button) stays visible with the dialog open, and the dialog itself sits above the `Waypoints` heading; Cancel restores the trigger in the same slot, focused.
