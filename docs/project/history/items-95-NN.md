## Item 96 — Grace period for the slow map-imagery notice — done

_Category: Map imagery status presentation_

96. **Grace period for the slow map-imagery notice — done**
    - **Outcome.** The "Map imagery is taking longer than usual to load. Your route and position are still shown." notice (`MapView.tsx`, `data-testid="map-imagery-delayed-banner"`) now waits a 2-second presentation grace (`SLOW_IMAGERY_NOTICE_GRACE_MS`) before it may render, instead of appearing the instant `styleStructurallyReady && !ready && !usingFallbackStyle && tileErrorMessage === null` (`slowImageryNoticeEligible`) became true with no delay of its own. `STYLE_READY_TIMEOUT_MS` (15s, a wholly separate style-document-readiness fallback), Diagnostics categories, camera/recovery logic, and item 83's external `onImageryStatusChange` presentation seam are all unchanged.
    - **Confirmed cause.** The banner's JSX condition was exactly `slowImageryNoticeEligible`, checked and rendered synchronously on every render — the existing test suite observed it appear immediately after `style.load` with no elapsed time. Predates the CSP work (item 93) and the `0.4.0` release-preparation slice; not a regression from either.
    - **Mechanism actually shipped.** `slowImageryNoticeEligible` (the pre-existing trigger condition, unchanged) is still recomputed fresh every render. A `useState<number | null>` (`elapsedForRetryToken`) is non-null only once a grace timer has genuinely elapsed for the `retryToken` value stored in it, and is set _exclusively_ from inside a `window.setTimeout` callback — never synchronously in the owning effect's body — because this project's `react-hooks/set-state-in-effect` lint rule flags a direct effect-body `setState` call as risking cascading renders. A second, small piece of state (`lastRenderedEligible`) uses React's own documented "adjust state during render" pattern (not a further Effect) to null out `elapsedForRetryToken` the instant `slowImageryNoticeEligible`'s own value changes, in the same render, before paint — this closes the "an already-elapsed marker instantly redisplays once eligibility resumes with the same `retryToken` (e.g. a tile error interrupting, then clearing, with no retry involved)" gap without a second effect-body `setState` call. `imageryGraceEpisodeRef` (a plain `useRef`, incremented once at the very start of every effect run, and again — if unclaimed by a later run — in that same run's cleanup) is read and written _only_ inside the effect and its timer callback, never during render, because this project's `react-hooks/refs` lint rule flags reading a ref value during render. The timer callback checks `imageryGraceEpisodeRef.current !== episode` before calling `setElapsedForRetryToken`, so a callback that becomes runnable despite an intervening cleanup can never mark a superseded episode elapsed. The effect's dependency array is `[slowImageryNoticeEligible, retryToken]` — including `retryToken` explicitly, not relying on `slowImageryNoticeEligible`'s boolean value alone, closes a `retryToken`-bump race: a retry renders once with the _old_ eligibility state still in place (the map-creation effect's own reset to "ineligible" runs later, as a separate effect body), so a boolean-only dependency could silently miss restarting the timer for a retry whose eligibility value happened not to visibly change across it. The final render condition, `slowImageryNoticeVisible = slowImageryNoticeEligible && elapsedForRetryToken === retryToken`, re-derives live eligibility and requires the elapsed marker to belong to the current retry generation — a timer firing is never sufficient by itself.
    - **Rejected/superseded design, corrected during plan review before implementation.** An initial plan proposed a plain boolean effect keyed only on `[slowImageryNoticeEligible]`, with `window.clearTimeout` alone for cancellation and a stored `{retryToken, episode, elapsed}` object whose `episode` field was compared against the ref _during render_. Plan review identified two problems with this: `clearTimeout` cannot neutralise a callback that has already become runnable before React's own passive-effect cleanup gets scheduled, and the callback's own guard (not `clearTimeout` alone, and not a render-time ref read) needed to be what made a stale callback safe. The revised design added the ref-based episode guard _inside_ the timer callback and — per an explicit follow-up correction — also invalidates the episode in the effect's _cleanup_, not only at the start of the next effect run: at unmount specifically, no later effect run ever exists to mint a fresh episode and thereby make a pending one stale by comparison. Once implemented, this exact shape (a stored `{retryToken, episode, elapsed}` object plus a render-time ref comparison) was itself replaced during implementation, after this project's own `react-hooks/set-state-in-effect` and `react-hooks/refs` ESLint rules flagged the direct effect-body `setState` calls and the render-time ref read described above — the final `elapsedForRetryToken`-plus-render-time-reset shape (described in Mechanism above) is what shipped, preserving every one of plan review's correctness requirements without either lint violation.
    - **Fail-first evidence.** Before any production change, the rewritten/added unit tests were run against the unmodified baseline: `npx vitest run src/map/MapView.test.tsx` — **10 failed, 187 passed** (of 197). The 10 failures were exactly the ones expecting the new grace behaviour (8 new tests in the `backlog item 96` describe block, plus 2 existing tests updated to assert the notice is absent immediately after `style.load` and only appears after a 2000ms fake-timer advance) — all failing because the unmodified banner rendered immediately, with no delay.
    - **Negative controls**, each isolating one specific guard, reverting only it, reconfirming a real failure, then restoring and re-verifying the full suite green:
      - **Callback episode-guard alone removed** (`if (imageryGraceEpisodeRef.current !== episode) return;` deleted from the timer callback, render-time reset left intact): the dedicated "ignores an obsolete grace-timer callback from an earlier episode" test failed — a directly-invoked stale callback revealed the banner. Confirms the callback's own guard is independently load-bearing, not redundant with the render-time reset (the two tests use the _same_ `retryToken` throughout, so the render-time reset alone cannot discriminate this case).

## Item 104 — Preserve route progress through exactly overlapping out-and-back turnarounds — done

_Category: Ride navigation reliability_

104. **Preserve route progress through exactly overlapping out-and-back turnarounds — done** - **Real iPhone field symptom (pre-fix evidence).** On an out-and-back route whose route-before and route-after the turnaround overlap exactly, the app never caught that the rider had reached the turnaround. Continuing physically beyond it in the original direction only ever showed the "Possibly off route" message; turning around and riding home along the coincident return leg instead made the app "go back in time" — displayed progress moved backward instead of continuing forward. This report identifies the pre-fix defect only; it is not evidence that the correction below works on a real device — see the outstanding real-device checklist in `docs/project/current-status.md`. - **Deliberately reprioritised ahead of item 98.** Item 98 (direction-aware active-Riding route-segment layering) is a map-presentation slice whose own contract requires deriving its current/near-ahead overlay from matched canonical route progress, not GPS bearing alone. Building that overlay on top of progress that can run backwards would just make it faithfully highlight the wrong leg. Item 104 is confined to route projection/matching; it adds, reorders or restyles no map layer, and item 98 remains selected next, unimplemented in this slice, and now has a corrected progress input to consume without reopening the matcher (see `docs/project/backlog.md`'s own item 98 cross-reference). - **Fail-first reproduction, measured against unmodified `main`.** A new fixture, `src/test/fixtures/outAndBackCoincidentRoute.ts` (`OUT_AND_BACK_COINCIDENT_ROUTE_POINTS`, ~14 m spacing, ~2099 m per leg, plus a second, deliberately sparse/irregular `OUT_AND_BACK_COINCIDENT_SPARSE_ROUTE_POINTS`, ~320–670 m segments ending in a ~50 m final approach), was built with an EXACT coordinate-for-coordinate retrace of the outbound leg on the return leg — unlike the pre-existing `outAndBackRoute.ts`, whose return leg is deliberately offset ~11 m in latitude (confirmed by direct arithmetic, `0.0001° × 111,320 m/° ≈ 11.13 m`) so its two legs are never tied, which is exactly why it never caught this bug. Two of the required traces genuinely failed against unmodified `src/navigation/projection.ts`, deterministically seeded via a directly-constructed `ProjectionMatch` rather than a fresh reacquire (a fresh whole-route reacquire on this fixture is itself subject to the same ambiguity the fix addresses, since every point on the coincident stretch has a tied mirror somewhere in the array — see the fixture's own module comment):
     - **Trace A** (exact fix at the turnaround, then a fix 20 m onto the return leg): `firstReturnFix.distanceFromStartMetres` measured `2079.32`, required to be greater than `atTurnaround.distanceFromStartMetres` (`2099.32`) — it decreased instead of advancing.
     - **Trace B** (a near-turn fix 8 m short of the turnaround, then a sequence of fixes progressively further along the return leg with no exact apex fix): the first sequence step measured `2074.32`, required to be `>=` the previous step's `2091.32` — it regressed.

Near a turnaround, that window spans both the outbound approach and the return departure (both fall within `[lastMatch.distance − 400, lastMatch.distance + 400]` in cumulative-distance terms, even though they are the same physical line traversed in opposite directions). The installed `@turf/nearest-point-on-line` (v7.4.0, confirmed in `node_modules`) resolves an exact geometric tie via a **strict** `<` comparison (`dist/esm/index.js:80`) — the first-encountered (lowest array index, i.e. outbound) candidate wins on a true tie, and any later exact tie is silently discarded. The original hypothesis was that this would **always** resolve to the outbound occurrence. Direct measurement (see `LATERAL_TIE_TOLERANCE_METRES` calibration below) showed this is not quite right: because the outbound and return coordinates are computed via independently-evaluated floating-point expressions (`0.03 × (i/150)` versus `0.03 − 0.03 × (j/150)`), they are not bit-identical, so which candidate has the marginally smaller computed lateral distance — and therefore wins — is effectively erratic rather than deterministically "always outbound". This is a more precise, and arguably more concerning, characterisation of the field defect than the original hypothesis: the pre-fix behaviour near a turnaround is not simply biased backward, it is unpredictable. - **Why a single split point cannot work — worked counter-example.** Two intermediate designs (splitting the window into two sub-ranges at `lastMatch.pointIndex`, then at the array index nearest to `lastMatch.distanceFromStartMetres`) were tried and rejected before implementation, following review. A single pivot can only separate two tied occurrences into different sub-ranges when it falls _between_ them — but the two tied occurrences near a turnaround are symmetric around the turnaround itself, not around `lastMatch`. Worked example: turnaround `T = 2100 m`, a vertex at `2050 m` (one 50 m segment leading into the turnaround), `lastMatch.distanceFromStartMetres = 2070` (closer to the earlier vertex than to `T`). A fix at the coordinate shared by outbound-`2060` and return-`2140` splits at the nearest-vertex pivot `2050` — **before both tied occurrences** — so both land in the same ("leading") sub-range; that sub-range's own internal Turf call resolves the tie by array order and returns `2060` only, discarding `2140` before any comparison logic runs. The result depends on where `lastMatch` happens to fall relative to nearby vertices, not on the actual route geometry. - **Why gap-size alone cannot justify forward preference — worked counter-example.** An initial decision rule (prefer whichever tied candidate is forward of `lastMatch` whenever the two candidates' route-distance gaps from `lastMatch` differ by no more than a margin) was also rejected. Counter-example: `lastMatch = T − 30` (still 30 m short of the turnaround, ordinary forward approach), next ordinary fix at `T − 20` — tied on this exactly-coincident geometry with its own not-yet-reached return mirror at `T + 20`. `gapTrailing = |(−30) − (−20)| = 10`; `gapLeading = |(−30) − 20| = 50`; difference `= 40`, comfortably within a tens-of-metres margin — wrongly jumping the rider onto the return leg while still on the way out. The root error: `gapLeading − gapTrailing = 2·min(a, b)` (where `a` is how close `lastMatch` was to the crossover and `b` is how close the _new_ fix is) is symmetric in `a` and `b` — small either because `lastMatch` was close, or merely because the new fix happens to be, which does not on its own prove the turnaround was reached. - **The exact correction, in two parts.** `src/navigation/projection.ts`'s windowed branch now, after computing `primary` exactly as before:
     1. `findTiedOccurrences` scans every individual segment in the window (a lightweight two-point `nearestPointOnLine` call each, reusing Turf's own per-segment projection — no new geometry maths), collecting every segment whose own lateral distance is within `LATERAL_TIE_TOLERANCE_METRES` of `primary`'s, and clusters them into distinct **occurrences**. A qualifying segment joins the previous cluster only when it is BOTH array-index-adjacent AND its own matched route-distance is within `OCCURRENCE_SEPARATION_METRES` of the previous one's — array adjacency alone is insufficient, since the last outbound segment and first return segment always share the turnaround vertex and so are always array-adjacent even when they represent two occurrences many metres apart (this specific gap was found and fixed during implementation via a direct debug probe: with adjacency-only clustering, a fix 10.1 m past the turnaround still returned only ONE occurrence, silently discarding the genuinely tied return candidate). If exactly one occurrence survives, `primary` is returned unchanged — ordinary, non-tied fixes are unaffected.
     2. When more than one occurrence survives, `selectAmongOccurrences` picks the occurrence closest in route-distance to `lastMatch` ("continuity-nearest") by default. It only overrides that default when the continuity-nearest occurrence is a **genuine regression** — more than `PROGRESS_EPSILON_METRES` below `lastMatch`'s own distance, not merely equal to or infinitesimally below it — **and** some other occurrence is a **genuine advance** (more than `PROGRESS_EPSILON_METRES` above) whose own gap from `lastMatch` is within `CONTINUITY_PREFERENCE_METRES` of the continuity-nearest occurrence's own gap.

     `findWindowRange`, `isClippedAtEdge`, `nearestWithinRange` itself, and the whole-route reacquire fallback are all byte-for-byte unchanged — this fix is confined to the one call site inside `projectFixOntoRoute`'s windowed branch. - **Three new named constants, each measured, not guessed:**
