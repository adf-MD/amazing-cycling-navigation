## Item 95 — Route-switch prompt visibility and action hierarchy — done

_Category: Route Library interaction reliability_

95. **Route-switch prompt visibility and action hierarchy — done**
    - **Outcome.** A confirmed, fail-first-proven presentation defect fixed: the inline route-switch guard prompt (item 73/73-follow-up) now scrolls the complete chosen route card into view — accounting for the sticky top navigation and the visible viewport's bottom/safe area — instead of only the nested prompt sub-panel. The action order and styling were also corrected to the approved hierarchy: `End and switch`/`Discard and continue` first, `Return to paused ride` styled as the positive primary action second, `Cancel` last but still the default keyboard focus. Item 73's state machine, item 91's coordinator characterisation, and `App.tsx`'s conflict/retry/return semantics are unchanged.
    - **Baseline.** `9a215f8` (the item 94 iPhone-acceptance documentation commit, itself on top of `7fe8471` / `0.4.3`), clean, in sync with `origin/main`.
    - **Confirmed root cause.** `RouteListItem.tsx`'s switch-prompt effect held a ref (`switchPanelRef`) only on the nested `<div class="route-delete-confirm" role="alertdialog">` panel — the last child inside the card — and called `scrollIntoView({ block: "nearest" })` on it alone whenever the prompt's message changed. `block: "nearest"` has no awareness of the separate `position: sticky; top: 0` header (`App.tsx`'s `<header class="app-header--sticky">`, z-index 10): nothing in the codebase used `scroll-margin-top`/`scroll-padding` to compensate for its visual overlay (confirmed by a repository-wide grep returning zero matches), and the header's own rendered height is not a fixed CSS constant (`padding-top: calc(var(--safe-area-inset-top) + var(--space-8))` plus the nav row's own content height plus a 1px border), so nothing could reliably offset for it as a static value either. There was also no visibility check at all — the effect scrolled unconditionally on every message change, regardless of whether the card was already fully visible.
    - **Fail-first evidence, run against unmodified baseline before any production change.**
      - **Component-level (deterministic, source-confirmed defect).** A rewritten `describe("scroll-into-view target (backlog item 95)")` block in `RouteListItem.test.tsx`, run via `npx vitest run src/ui/library/RouteListItem.test.tsx -t "backlog item 95"` against unmodified `RouteListItem.tsx`: **3 failed, 2 passed**. The failures proved, deterministically: the scroll call targeted the nested panel (`switchPanelRef`'s element), not the outer `[data-route-id]` card, with `{ block: "nearest" }` rather than `{ block: "end" }`; there was no skip-when-already-visible branch (a card whose fabricated `getBoundingClientRect()` was comfortably within a headerless, un-cushioned viewport still triggered a scroll call); and the reduced-motion assertion inherited the wrong `block` value alongside the correct `behavior`.
      - **Real-browser (Chromium/Playwright), treated as a hypothesis until measured, not assumed.** `e2e/rideSessionSwitchGuard.spec.ts` was extended with header-clearance and card-bottom-visibility assertions (using `window.visualViewport`'s `offsetTop`/`height`, falling back to `window.innerHeight`) across its existing lower-route, portrait, short-landscape and 200%-enlarged-text tests, plus a new "already fully visible, no unnecessary jump" test and a DOM-order assertion. Run via `npx playwright test e2e/rideSessionSwitchGuard.spec.ts --project=chromium` against the unmodified baseline build (`npx vite build`, bypassing the locally-blocked `tsc -b` step — see Verification below): **9 passed, 3 failed**. The three failures, all genuine and distinct, confirm the hypothesis empirically rather than by assumption: the lower-route/portrait test failed only on button order (its geometry passed cleanly at that viewport/list-length combination — the sticky-header occlusion did not manifest there); the 844×390 short-landscape test failed on real header occlusion (`dialogBox.y` measured `43`, 22px above the header's own measured bottom of `65`); and the 200%-enlarged-text test (extended with 8 filler routes to push the card below the fold) failed dramatically, with the card's own bottom edge measured at `861`, 17px below the 844px visible viewport bottom.
    - **Implementation.**
      - `App.tsx`: added a read-only `stickyHeaderRef` (`useRef<HTMLElement>(null)`), attached to the existing `<header className="app-header--sticky">`, and threaded into `<RouteLibrary>` as a new optional prop — mirroring `routesScrollYRef`'s own established "App owns a page-chrome fact a screen component needs" shape (`RouteLibraryProps.restoreScrollYRef`). No other `App.tsx` change: the `PendingRideSwitch` state machine, `checkRideTransition`, `confirmPendingSwitch`, `retryPendingSwitchCheck`, `returnToPausedRide`, `handleSwitchTargetMissing` and the `origin: "route-card" | "global"` distinction are all byte-for-byte unchanged (confirmed via `git diff` before staging).
      - `RouteLibrary.tsx`: added the same optional `stickyHeaderRef` prop, doc-commented like `restoreScrollYRef`, passed straight through unchanged to every `<RouteListItem>` row (one shared ref, not per-row).
      - New `src/ui/library/routeSwitchCardVisibility.ts`: a small pure function, `isCardAlreadyFullyVisible(cardRect, headerBottomPx, bottomCushionPx, visibleTopPx, visibleBottomPx)`, following this directory's existing pure-function-sibling convention (`routeDeleteFocus.ts`, `routeLibraryView.ts`). Its own `routeSwitchCardVisibility.test.ts` covers the fully-visible, header-occluded, viewport-bottom-occluded, cushion-boundary and visible-top-exceeds-header-bottom cases directly with fabricated numbers — the geometry arithmetic is proven independently of any DOM/jsdom limitation.
      - `RouteListItem.tsx`: replaced `switchPanelRef` with `cardRef` (`useRef<HTMLLIElement>(null)`) on the outer `<li className="route-card stack">`, which also gains a conditional `route-card--switch-pending` modifier class whenever `switchPrompt` is non-null. The scroll effect (still gated on `switchPrompt.message` changing, preserving the exact "same message → no extra scroll; changed message → re-check" contract already proven by the pre-existing test) now reads the card's own `getBoundingClientRect()`, `stickyHeaderRef?.current?.getBoundingClientRect().bottom ?? 0`, the card's own computed `scrollMarginBottom` (for the safe-area cushion), and the visible viewport band via `window.visualViewport` (`offsetTop`/`offsetTop + height`, matching the reconciliation between visual- and layout-viewport coordinate spaces that `getBoundingClientRect()` uses) falling back to `[0, window.innerHeight]`. When `isCardAlreadyFullyVisible` reports the card is already within that band, the effect returns without scrolling; otherwise it calls `cardEl.scrollIntoView({ block: "end", behavior: prefersReducedMotion() ? "auto" : "smooth" })` — `block: "end"` was chosen deliberately over `"nearest"` because `"nearest"` is a no-op precisely when an element is larger than the scrollport and already straddles both edges (the exact "card too tall to fit" case this item needs to handle), the opposite of the required behaviour; the explicit visibility skip-check is what restores `"nearest"`-like idempotence for the ordinary, already-visible case.
      - `index.css`: added `scroll-margin-bottom: calc(var(--safe-area-inset-bottom) + var(--space-8))` scoped to the new `.route-card--switch-pending` modifier class only (reusing the exact token pairing `.ride-immersive-switcher` already uses for the same purpose elsewhere in this file) — not the base `.route-card` rule, since an ordinary card (including one showing the unrelated delete-confirmation panel, which has no scroll-into-view behaviour of its own) has nothing to reserve this space for.
      - Action order and styling (`RouteListItem.tsx`'s switch-prompt button block): reordered from Cancel → Return → Confirm to Confirm → Return → Cancel, a plain JSX reorder (confirmed no `order:`/`row-reverse` exists anywhere in `index.css` that would need removing). `Return to paused ride`'s class changed from `btn-secondary` to `btn-primary` (the established positive/accent treatment — `--colour-accent` is green in both light and dark themes); `Cancel` kept its `autoFocus` attribute unchanged, which continues to focus it on mount regardless of its new last DOM position (React's `autoFocus` is position-independent), so the safe, non-destructive action remains the default focus target despite the destructive/proceed action now rendering first. The stale `RouteSwitchPrompt` doc comment ("Cancel and Return are always secondary-styled") was corrected to state Cancel is secondary and Return is primary/positive.

    - **A real, evidence-driven test correction found along the way.** The 200%-enlarged-text scenario (with 8 filler routes added to push the card below the fold, matching the other extended geometry tests) is a genuine instance of the "card too tall to fit between the sticky header and the visible viewport" extreme case the backlog explicitly anticipated: the card measured 1726px tall against only a 766px available band (78–844). Even after the fix, the dialog's own top (containing the heading and message, above the actions) could not be brought fully below the header — mathematically impossible, since the dialog alone (1352px) exceeds the entire available band. Critically, all three actions and the card's own bottom edge were confirmed fully visible and usable (`block: "end"` correctly prioritises them). The test's original single-tier assertion (dialog top must always clear the header) was corrected to a two-tier rule: when the card fits within the available band, the complete prompt (including its top) must be immediately visible, exactly as before; when it genuinely cannot fit, only every action and the card's bottom edge are required to be immediately visible — matching the backlog's own extreme-case fallback wording rather than a stricter, physically-unsatisfiable reading of it.

    - **Follow-up (2026-09-03), v0.4.5 — Return-to-paused-ride scroll carry-over.** The user confirmed item 95's principal result on the installed iPhone Home Screen PWA: the inline prompt appears with the chosen card, the card and actions are brought into view correctly, and the action order/hierarchy work as intended. One intermittent follow-up remained: after tapping `Return to paused ride`, the newly opened paused route's Pre-Ride screen sometimes inherited the Route Library's lower scroll position instead of opening at its normal top.
      - **Mechanism.** Two distinct contributors were examined, held to different evidentiary bars as the diagnosis explicitly required. **Source-confirmed** (a plain fact about the code, not an inference): `RouteListItem.tsx`'s switch-prompt scroll effect keyed only on message text, with no `switchPrompt.busy` guard, even though `busy` was already computed and passed — so tapping Return (which flips status to `"returning"`, changing the message to `"Opening your paused ride…"` while `screen` is still `"library"`) re-triggered a second, wholly avoidable `scrollIntoView` call. **A confirmed structural overlap opportunity, not an empirically observed cause**: nothing synchronises the card's own item-95 scroll animation (started when the prompt first opened, on the `"conflict"` message) with `useResetScrollForNewRideContent`'s single, one-shot `window.scrollTo({top:0})` reset once `openRideTarget` succeeds — so that original animation being still mid-flight when the reset fires is timing-plausible, but this repository's own Chromium e2e harness could not catch it in flight in repeated real runs (see Evidence below); it is reported as an opportunity the fix closes structurally, not as a proven cause of the field symptom.
      - **Fix.** (a) `RouteListItem.tsx`: the scroll effect now returns immediately whenever `switchPrompt.busy` is true, and — critically — does so _before_ recording the message into `lastSwitchMessageRef`, so the ref keeps holding the last actionable text throughout any busy interval and a later genuinely-new actionable message (e.g. a failure) still re-arms and re-checks visibility correctly. (d) `useResetScrollForNewRideContent.ts`: only for a genuinely new token (never a plain nav-tab return), the existing one-shot `scrollTo(0)` is followed by a `requestAnimationFrame` loop that re-flattens `window.scrollY` to within a 1px tolerance until it holds there for 3 consecutive frames — a condition-based completion, not a fixed frame count — backstopped by an elapsed-time (not frame-count) safety cap, and aborted immediately the instant a genuine `touchstart`/`pointerdown`/`wheel` event is observed, so it can never fight a deliberate later scroll. All scheduled frames and the input listener are cancelled via the effect's existing `[screen, token]`-keyed cleanup whenever a newer token supersedes, `screen` leaves `"riding"`, or the component unmounts. This makes correctness independent of exactly which animation is racing the reset, or of any unverifiable assumption about whether an instant `scrollTo` reliably aborts an in-flight smooth one on real iOS Safari — a boundary this sandbox cannot test directly. A third candidate (cancelling at the `openRideTarget` transition boundary) was considered and not used as the primary mechanism for the same reason; (d) does not depend on it.
      - **Fail-first evidence.** `RouteListItem.test.tsx`: a busy `"returning"`-shaped prompt produces no second `scrollIntoView` call, and a later non-busy actionable message still scrolls (fails pre-fix: 2 calls; passes post-fix: gated correctly, then re-arms). `useResetScrollForNewRideContent.test.ts`: a scripted late-drift sequence (a simulated nonzero `scrollY` landing on a later frame) is detected and corrected, then the loop terminates once genuinely stable; a pathological never-stabilising sequence terminates at the elapsed-time cap, not indefinitely; a newer token or unmount cancels the pending frame and listener; each of `touchstart`/`pointerdown`/`wheel` stops the loop immediately; a genuine plain nav-tab return (away from Riding and back with no new token) never starts the loop at all. `App.test.tsx`: extended Return-to-paused-ride and a new End-and-switch characterisation, each with a forced off-screen card-geometry stub (jsdom's default zero-rects otherwise make `isCardAlreadyFullyVisible` trivially true, making a raw call-count assertion vacuous), proving no second `scrollIntoView` call during the real, App-wired busy window, that the reset fires exactly once at the correct transition, and that a simulated Library scroll position is still restored on a later return to Routes.

Across 5+ repeated runs, Pre-Ride reached and held within 1px of the top for the entire post-transition recording every time (`offTopSampleCount=0`). Honestly reported: `motionObservedBeforeReturn` was `false` in every run — this harness's real local IndexedDB reads resolve in roughly 10–80ms total, faster than needed for the item-95 `"conflict"` animation to still be genuinely in flight by the time Return is clicked. This is a reportable data point about this environment's timing, not proof the underlying race cannot occur on slower real hardware, and Chromium's own timing here neither confirms nor refutes anything about real iOS Safari's. A non-race "fully settled" control test and a minimal ordinary-motion End-and-switch analogue (proving the shared `openRideTarget`/busy-gate boundary deliberately, not merely assuming it from code-sharing) were also added, plus a scroll-at-top assertion on the pre-existing reduced-motion test.
