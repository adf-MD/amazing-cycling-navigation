## Item 96 — Grace period for the slow map-imagery notice — done

_Category: Map imagery status presentation_

96. **Grace period for the slow map-imagery notice — done**
    - **Outcome.** The "Map imagery is taking longer than usual to load. Your route and position are still shown." notice (`MapView.tsx`, `data-testid="map-imagery-delayed-banner"`) now waits a 2-second presentation grace (`SLOW_IMAGERY_NOTICE_GRACE_MS`) before it may render, instead of appearing the instant `styleStructurallyReady && !ready && !usingFallbackStyle && tileErrorMessage === null` (`slowImageryNoticeEligible`) became true with no delay of its own. `STYLE_READY_TIMEOUT_MS` (15s, a wholly separate style-document-readiness fallback), Diagnostics categories, camera/recovery logic, and item 83's external `onImageryStatusChange` presentation seam are all unchanged.
    - **Confirmed cause.** The banner's JSX condition was exactly `slowImageryNoticeEligible`, checked and rendered synchronously on every render — the existing test suite observed it appear immediately after `style.load` with no elapsed time. Predates the CSP work (item 93) and the `0.4.0` release-preparation slice; not a regression from either.
    - **Mechanism actually shipped.** `slowImageryNoticeEligible` (the pre-existing trigger condition, unchanged) is still recomputed fresh every render. A `useState<number | null>` (`elapsedForRetryToken`) is non-null only once a grace timer has genuinely elapsed for the `retryToken` value stored in it, and is set _exclusively_ from inside a `window.setTimeout` callback — never synchronously in the owning effect's body — because this project's `react-hooks/set-state-in-effect` lint rule flags a direct effect-body `setState` call as risking cascading renders. A second, small piece of state (`lastRenderedEligible`) uses React's own documented "adjust state during render" pattern (not a further Effect) to null out `elapsedForRetryToken` the instant `slowImageryNoticeEligible`'s own value changes, in the same render, before paint — this closes the "an already-elapsed marker instantly redisplays once eligibility resumes with the same `retryToken` (e.g. a tile error interrupting, then clearing, with no retry involved)" gap without a second effect-body `setState` call. `imageryGraceEpisodeRef` (a plain `useRef`, incremented once at the very start of every effect run, and again — if unclaimed by a later run — in that same run's cleanup) is read and written _only_ inside the effect and its timer callback, never during render, because this project's `react-hooks/refs` lint rule flags reading a ref value during render. The timer callback checks `imageryGraceEpisodeRef.current !== episode` before calling `setElapsedForRetryToken`, so a callback that becomes runnable despite an intervening cleanup can never mark a superseded episode elapsed. The effect's dependency array is `[slowImageryNoticeEligible, retryToken]` — including `retryToken` explicitly, not relying on `slowImageryNoticeEligible`'s boolean value alone, closes a `retryToken`-bump race: a retry renders once with the _old_ eligibility state still in place (the map-creation effect's own reset to "ineligible" runs later, as a separate effect body), so a boolean-only dependency could silently miss restarting the timer for a retry whose eligibility value happened not to visibly change across it. The final render condition, `slowImageryNoticeVisible = slowImageryNoticeEligible && elapsedForRetryToken === retryToken`, re-derives live eligibility and requires the elapsed marker to belong to the current retry generation — a timer firing is never sufficient by itself.
    - **Rejected/superseded design, corrected during plan review before implementation.** An initial plan proposed a plain boolean effect keyed only on `[slowImageryNoticeEligible]`, with `window.clearTimeout` alone for cancellation and a stored `{retryToken, episode, elapsed}` object whose `episode` field was compared against the ref _during render_. Plan review identified two problems with this: `clearTimeout` cannot neutralise a callback that has already become runnable before React's own passive-effect cleanup gets scheduled, and the callback's own guard (not `clearTimeout` alone, and not a render-time ref read) needed to be what made a stale callback safe. The revised design added the ref-based episode guard _inside_ the timer callback and — per an explicit follow-up correction — also invalidates the episode in the effect's _cleanup_, not only at the start of the next effect run: at unmount specifically, no later effect run ever exists to mint a fresh episode and thereby make a pending one stale by comparison. Once implemented, this exact shape (a stored `{retryToken, episode, elapsed}` object plus a render-time ref comparison) was itself replaced during implementation, after this project's own `react-hooks/set-state-in-effect` and `react-hooks/refs` ESLint rules flagged the direct effect-body `setState` calls and the render-time ref read described above — the final `elapsedForRetryToken`-plus-render-time-reset shape (described in Mechanism above) is what shipped, preserving every one of plan review's correctness requirements without either lint violation.
    - **Fail-first evidence.** Before any production change, the rewritten/added unit tests were run against the unmodified baseline: `npx vitest run src/map/MapView.test.tsx` — **10 failed, 187 passed** (of 197). The 10 failures were exactly the ones expecting the new grace behaviour (8 new tests in the `backlog item 96` describe block, plus 2 existing tests updated to assert the notice is absent immediately after `style.load` and only appears after a 2000ms fake-timer advance) — all failing because the unmodified banner rendered immediately, with no delay.
    - **Negative controls**, each isolating one specific guard, reverting only it, reconfirming a real failure, then restoring and re-verifying the full suite green:
      - **Callback episode-guard alone removed** (`if (imageryGraceEpisodeRef.current !== episode) return;` deleted from the timer callback, render-time reset left intact): the dedicated "ignores an obsolete grace-timer callback from an earlier episode" test failed — a directly-invoked stale callback revealed the banner. Confirms the callback's own guard is independently load-bearing, not redundant with the render-time reset (the two tests use the _same_ `retryToken` throughout, so the render-time reset alone cannot discriminate this case).
