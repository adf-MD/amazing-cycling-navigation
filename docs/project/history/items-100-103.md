## Item 100 — Reusable route tags and tag-based organisation — done

_Category: Route Library organisation_

100. **Reusable route tags and tag-based organisation — done**
     - Confirmed current state: no tag or folder concept exists anywhere in the codebase (`src/domain`, `src/storage`, `src/ui`) — this is genuinely new work, not an extension of a partially-built feature.
     - Use user-facing **tags**, not exclusive folders. A saved route may naturally belong to several concepts, such as `commute`, `gravel` and `weekend`.
     - When editing a route's tags, offer existing tags as suggestions and allow a new tag to be created without leaving the editor.
     - Specify deterministic normalisation for whitespace, empty values, duplicates and case. Preserve one stable display spelling while preventing accidental case-only duplicates.
     - Existing routes migrate safely to an empty tag collection. No route becomes hidden or inaccessible after the migration.
     - Initial tags are local ACN library metadata. Do not silently alter GPX import/export or place tags inside the geometry-digest-bound `<acn:navigation>` GPX extension without a separately reviewed format/version decision.
     - This is approved staged implementation work, not a feasibility study — stage the delivery so each slice ships independently, rather than an unreviewable vertical expansion in one commit. Later stages depend on the tag foundation earlier stages build, not on a feasibility gate:
       1. **Data model and storage:** inspect migration implications and the compact phone editor's interaction pattern, then add the backward-compatible storage schema/migration for an empty-by-default tag collection per route.
       2. **Tag editing:** add reusable-tag suggestions and new-tag creation in the route editor, built on stage 1's storage.
       3. **Filtering and organisation:** add tag filtering and a useful organisation view without duplicating a multi-tag route confusingly across many sections, built on stage 2's tag data.
       4. **Full lifecycle and acceptance:** add tag editing, deletion/rename and empty-state coverage plus real-device acceptance for the complete feature.
     - Prefer filtering and tag chips before inventing nested folders. If a later grouped presentation is proposed, mock up how multi-tag routes appear before implementation.
     - Preserve search, pinning, sorting (including item 99's new fields once delivered), import/export privacy, storage migrations and route-switch behaviour. Adding a third-party taxonomy or cloud synchronisation is out of scope.

       - **Root cause.** `RouteListItem.tsx`'s tag editor closes only once two independent async facts are both true: the save write has settled, and `route.tags` (via `RouteLibrary`'s live query) reflects the saved tags by identity. The write-settled fact was held in a plain `useRef` (`savedTagsAwaitingSyncRef`), set inside the write promise's `.then()`. A ref mutation never triggers a re-render or effect re-run. The closing effect depended only on `route.tags`. This worked whenever the write settled _before_ `route.tags` updated — but broke whenever `route.tags` updated _first_: the effect ran once, found the ref not yet set, no-opped; when the write later settled and the ref was finally set, nothing caused the effect to run again, and the editor stayed on "Saving…" forever. The same failure mode also affected a successful no-op save (re-saving already-canonical tags), where `route.tags` might never change again at all.
       - **Fix: a genuine two-signal handshake, in `useState`, not a ref.** `savedTagsAwaitingSyncRef` became `pendingSyncTags`, a `useState<string[] | null>` — so setting it in the write's `.then()` is itself a state update that causes React to reconsider the closing condition, keyed on both `route.tags` and `pendingSyncTags`, wherever the two-signal handshake sits in the component (moved from an effect to a during-render adjustment — see below). No ref-only signal, no microtask delay, no `setTimeout`, and no increased Playwright timeout is part of the fix itself.
       - **A second lint-driven correction along the way.** The straightforward `useEffect` version of the new two-state-dependency closing check tripped this project's `react-hooks/set-state-in-effect` rule, which only exempts a ref-gated "consume once" shape — not this one, since `pendingSyncTags` is deliberately state. Following the exact convention already established in `RouteLibrary.tsx` (`pendingRouteSwitch`/`previousPendingRouteSwitch`) and `RidingScreen.tsx`, the closing check was moved to React's own documented "adjust state during render" pattern instead of an effect; it is self-terminating with no extra "previous value" mirror needed, because clearing `pendingSyncTags` is itself one of the condition's own inputs. `isSavingTagsRef`'s own reset on this success path can't happen during render either (`react-hooks/refs`), so it was split into a small separate effect keyed on `isSavingTags`.

101. **Plain-language HTTP-status guidance in Routing diagnostics — done**
