## Item 69 — Remaining positive ascent in the active route summary — done

_Category: Riding elevation enhancement_

69. **Remaining positive ascent in the active route summary — done**
    - A route-Riding information enhancement, distinct from the layout-only slice immediately above (item 68) because it introduces a new derived navigation metric rather than a presentation change to an existing one.
    - Confirmed (exhaustive grep of `src/navigation/` and `src/ui/riding/`): no "remaining ascent"/whole-route "ascent remaining" metric exists anywhere today. The only ascent-adjacent values that exist are the static, pre-ride `route.ascentMetres` total shown via `formatAscent()` in the idle route header and in `RidingLauncher.tsx` — a total, not live/remaining — and `ClimbProgressMetrics.elevationRemainingMetres` (`climbElevationView.ts`), explicitly scoped, per its own doc comment, to only the currently active climb ("not the same value as elevationGainMetres... not a new cumulative-ascent calculation") and shown only inside `RidingClimbProgressPanel` — never a whole-route figure.
    - Resolved architectural decision (settled in the backlog entry itself, not left to the implementer to choose): use the frozen/reliable `presentationDistanceFromStartMetres`/`lastReliableMatch` progress source for remaining ascent, matching every other presentation value in this app — climb progress, next-manoeuvre selection, the elevation marker, route completion. `RidingStatusStrip.tsx`'s existing "Remaining: X km" figure, previously computed from the live, raw `matchedDistanceFromStartMetres` (`coreState.lastMatch?.distanceFromStartMetres`, per `useRideNavigation.ts`) rather than that frozen/reliable value, was harmonised onto the same frozen/reliable progress source as an explicit, in-scope part of this same slice — not merely matched in wording — so the two figures on the compact status line can never disagree or jump independently under GPS jitter or off-route evidence.
    - Existing whole-route ascent/descent calculation reused, not reimplemented: `src/navigation/elevation.ts`'s `analyzeElevation` pipeline — filter known-elevation points, resample onto a fixed `RESAMPLE_STEP_METRES = 20` m grid, apply a centred `SMOOTHING_WINDOW_SAMPLES = 5`-sample moving average (~100 m window), then `computeAscentDescent`, a running-extremum/reversal-confirmation walk that only banks ascent once the series has reversed by at least `MIN_ASCENT_DELTA_METRES = 1` m from the tracked extremum.
    - Compact presentation shipped, verbatim:
      ```
      On route
      61.5 km · 993 m ascent
      GPS ±9 m · Live
      ```
      Both the distance and the ascent figure on the middle line are remaining values, not route totals. An unambiguous accessible label distinguishes this from the route's original total ascent, since the compact visible wording alone could be misread as a total.
    - Remaining ascent means the total future positive elevation gain from the rider's progress point onward — every future climb's gain summed, not merely the net elevation difference between the rider's position and the finish — with missing/gapped elevation handled honestly (never inventing 0 m when unknown). No ascent metric was added for route-less free roam, which has no route/elevation data at all.
    - **Calculation architecture (`src/navigation/elevation.ts`).** The shared "known points → resample → smooth" steps inside `analyzeElevation` were factored into a new private helper, `buildSmoothedElevationSeries(points)`, returning `{ sampleDistances, smoothed } | null` (`null` exactly when `!hasAnyElevation(points)`); `analyzeElevation` became a thin wrapper over that helper plus the still-private `computeAscentDescent`, with identical output for every existing caller (proven by the pre-existing `elevation.test.ts` suite passing unmodified). A single new exported function, `remainingAscentMetres(points, fromDistanceMetres): number | null`, builds the same series, clamps `fromDistanceMetres` to `[0, totalDistance]`, locates the seam value at that distance by calling the _existing_ `resampleElevations` with a one-element target array (re-expressing the smoothed grid as `KnownElevationPoint[]`, rather than writing a second interpolation routine), builds a tail array `[seamValue, ...smoothed-after-that-point]`, and returns `computeAscentDescent(tail, MIN_ASCENT_DELTA_METRES).ascentMetres`. Because `buildSampleDistances` always starts at exactly `0`, the seam lookup at `fromDistanceMetres = 0` lands on `resampleElevations`'s "at or before the first known point" branch and returns the first smoothed sample verbatim (no interpolation arithmetic at all) — making the tail array element-for-element identical to the whole-route smoothed array `analyzeElevation` itself uses. This gives exact (`toBe`, not approximate) agreement with `analyzeElevation(points).ascentMetres` at progress zero, proven directly by two unit tests. At and beyond the route finish the tail collapses to a single element, so `computeAscentDescent` returns `0` with no special-casing — the same construction that gives progress-zero exactness also gives the "known zero near the finish" behaviour for free. No new public type was introduced; `buildSmoothedElevationSeries`, `computeAscentDescent`, `resampleElevations` and `buildSampleDistances` all stayed module-private.
    - **`useRideNavigation.ts` harmonisation.** `distanceRemainingMetres` now derives from `presentationDistanceFromStartMetres` (previously `matchedDistanceFromStartMetres`); `matchedDistanceFromStartMetres` itself, and every other consumer of it (map position, off-route classification), was left untouched. A new `remainingAscentMetres: number | null` field was added to `RideNavigationState`, computed via `useMemo` keyed on `[route, presentationDistanceFromStartMetres]` — mirroring the file's own pre-existing `elevationDisplayPoints` memoization precedent — so the resample/smooth pass reruns only when the route changes or a new reliable fix genuinely moves progress, not on unrelated renders (`wakeLockDesired`, `elevationViewMode`, `isStale` flips, and so on). Both remaining figures now derive from the exact same `presentationDistanceFromStartMetres` value, so they are `null` together, non-`null` together, and freeze/resume together under off-route evidence, with no separate effect or synchronised state.
