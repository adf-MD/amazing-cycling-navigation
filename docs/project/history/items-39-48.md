## Item 39 — Low-zoom surface-warning width correction — done

_Category: Map zoom-dependent route and waypoint presentation_

39. **Low-zoom surface-warning width correction — done**
    - Direct follow-up to item 23 (Low-zoom route-colour and waypoint-marker legibility), which fixed ascent/descent overlay and neutral-base widths but left warning-layer widths unaddressed. No change to warning detection, categories, colours, dash patterns, selection semantics, details panels, or warning geometry (`src/map/warningLayer.ts` is untouched).
    - **Confirmed root cause**, and one correction to this item's own prior text: `routeWidthPolicy.ts`'s two zoom-recession families resolve identically at close zoom (15) but diverge below it — `recedingWidthStops` (multipliers 0.4 at overview zoom 6, 0.65 at regional zoom 11) recedes markedly faster than `legibleWidthStops` (0.6 at overview, 0.8 at regional). `MapView.tsx` applied `legibleWidthStops` — not `recedingWidthStops` as this item's own pre-implementation note incorrectly claimed — to the neutral base/casing (`acn-route-remaining-line`/`acn-route-completed-line`), the selected route-feature halo, _and_ every warning-related layer (`WARNING_SELECTED_PAINT`, width 13; each `WARNING_CATEGORY_PAINT` entry, widths 8–10). Warnings sharing the neutral base's gentle recession curve, rather than the faster-receding curve item 23 already gave the climb/descent colour overlays, is exactly why warnings remained visually dominant at low zoom in a way ascent/descent overlays no longer were since item 23.
    - **Chosen policy**: a third recession family, `warningWidthStops(closeWidthPx)` (`routeWidthPolicy.ts`), built via the existing `buildStops` helper with `WARNING_MULTIPLIERS = { overview: 0.45, regional: 0.6 }` — a distinct, warning-specific family, not a reuse of either existing one, since a direct swap onto `recedingWidthStops` would have narrowed the selected-warning halo below the selected route-feature halo at overview zoom (`13 × 0.4 = 5.2` vs `9 × 0.6 = 5.4`), inverting item 23's own established nested-ring priority. The chosen multipliers preserve every required inequality at every zoom stop:
      | width (px)                           | overview (×0.45) | regional (×0.6) | close |
      | ------------------------------------ | ---------------- | --------------- | ----- |
      | 8 (unknown-surface)                  | 3.6              | 4.8             | 8     |
      | 9 (other/ferry/questionable-surface) | 4.05             | 5.4             | 9     |
      | 10 (unsuitable-surface/obstacle)     | 4.5              | 6.0             | 10    |
      | 13 (selected warning)                | 5.85             | 7.8             | 13    |
      - Strictly narrower than `legibleWidthStops` at overview/regional, exactly equal at close, for every warning width — a warning now recedes rather than dominating a full-route overview.
      - Every category width stays wider than `recedingWidthStops(5)` (the climb/descent macro/micro overlay centre: 2/3.25/5) at every zoom, even the narrowest category (3.6 > 2, 4.8 > 3.25 at overview/regional) — a warning still visually outranks a climb/descent it overlaps.
      - Every category width stays wider than `legibleWidthStops(5)` (the neutral route base: 3/4/5) at every zoom, even the narrowest category (3.6 > 3, 4.8 > 4, 8 > 5).
      - `warningWidthStops(13)` (selected warning) stays wider than `legibleWidthStops(9)` (selected route-feature halo: 5.4/7.2/9) at every stop (5.85 > 5.4, 7.8 > 7.2, 13 > 9) — a selected warning still outranks a selected climb/descent.
      - `warningWidthStops(13)` stays wider than every warning category width at every stop, and proportional ordering within the warning family is preserved throughout — both hold by construction, since every warning width shares one multiplier applied to a strictly-ordered set of close-widths.
      - Treat these as first-pass, reasoned starting values pending real-device acceptance, mirroring this file's own established humility for `routeWidthPolicy.ts`'s existing constants.
    - **Applied consistently, with no Planning/Riding mode branch**: `WARNING_CATEGORY_PAINT`'s six entries and `WARNING_SELECTED_PAINT` now use `warningWidthStops` instead of `legibleWidthStops`; the neutral base, selected route-feature halo, climb/descent macro/micro overlays and Planning-preview layer are all unchanged. `RidingScreen.tsx` never passes a `warningOverlay` prop to `MapView` — warnings are a Planning-only UI/data feature (see "## Planning behaviour" in the root `CLAUDE.md`); Riding's pre-ride overview and active riding render the warning _layers_ unconditionally (as before) but their GeoJSON sources stay empty there, by existing, correct design, unchanged by this item. "Applied consistently" therefore means the shared paint constants are installed identically for every `MapView` caller by construction, proven directly by a new Planning/Riding parity test covering all six warning category layers.
    - **Files changed**: `src/map/routeWidthPolicy.ts` (new `WARNING_MULTIPLIERS`/`warningWidthStops`, updated doc comments), `src/map/MapView.tsx` (seven `legibleWidthStops` → `warningWidthStops` call sites, updated doc comments including the nested-ring rationale comment inside `addRouteAndPositionLayers`). No change to `src/map/warningLayer.ts`, `src/map/mapAdapter.ts`, or warning detection/normalisation code.
    - **Tests**: `routeWidthPolicy.test.ts` gained a `describe("warningWidthStops", ...)` block (9 tests: close-zoom-unchanged, ascending zoom stops, monotonicity, strictly-narrower-than-legible, wider-than-gradient-centre, wider-than-neutral-base, selected-warning-wider-than-selected-feature, selected-warning-wider-than-every-category, proportional ordering). `MapView.test.tsx`: the existing exhaustive per-layer paint test now expects `warningWidthStops` for the seven warning-related layers; a new test proves the real installed paint hierarchy (warning casings wider than the neutral base and macro overlay at overview/regional; the selected-warning halo wider than the selected route-feature halo at every stop); the Planning/Riding parity test's layer list was extended to all six warning category layers; a new "zoom-invariant warning source data" test (mirroring item 23's own pattern) proves a camera-only zoom change never touches warning GeoJSON source data; the fallback-style test gained assertions that the local fallback style installs the same `warningWidthStops` paints; a new test proves the full `WARNING_CATEGORIES_IN_PAINT_ORDER` add-order sequence, which no prior test covered exhaustively. `e2e/lowZoomLegibility.spec.ts` gained a `MOCK_WARNING_ORS_RESPONSE` fixture (surface codes 8 "Compacted gravel"/`questionable-surface` and 12 "Ground or mud"/`unsuitable-surface`, verified against `src/routing/surfaceCodes.ts`'s real code table) and three new tests: warning count/category/selection/details surviving a Planning zoom round trip; the same route surviving Save → pre-ride overview → Start riding across further zoom round trips (with an inline comment recording the Riding-has-no-warning-UI scope note above); and the warning staying selected and the route staying rendered under the local fallback style across a zoom round trip.

## Item 41 — Ride launcher, explicit session recovery and post-finalisation route clearing — done

_Category: Ride lifecycle_

41. **Ride launcher, explicit session recovery and post-finalisation route clearing — done**
    - Follow-up to item 6 (the existing "Ride, no selected route" empty screen offering `Choose a route`) and item 29 (End/Finish ride). Foundation for item 42 (free roam), which remains unimplemented and unscoped beyond this slice's own storage discriminant.
    - **Confirmed root cause** matched this item's own original description exactly: `App.tsx`'s `screen`/`selectedRoute` were plain, unpersisted `useState`, with no mount-time read of any persisted session state — `getActiveRideState()` was called only inside `useRideNavigation.ts`'s own mount-restore effect (reached only once `RidingScreen` was already mounted with a `selectedRoute`) and read-only in `DiagnosticsScreen.tsx`. A reload always returned to the Routes screen; "Resume riding" only became reachable once the rider manually reopened the _same_ route by name. Nothing cleared `App.tsx`'s own `selectedRoute` after a successful End/Finish ride, so the rider stayed looking at that same route's freshly-reset pre-ride panel rather than a genuinely empty state.
    - **Storage discriminant.** `src/storage/db.ts` gained `export type RideSessionKind = "route"` (a storage-only discriminant, placed and doc-commented alongside the file's existing `StoredElevationViewMode` precedent, not a domain-level type — it has no meaning outside a stored row) and a new optional `StoredRideState.kind?: string` field — deliberately a **plain string, not the narrower `RideSessionKind` union**, at this storage boundary, mirroring `editCopyOperation`/`profile`'s own established "Dexie never validates stored data" convention on `StoredPlanningDraft`, rather than trusting an arbitrary IndexedDB value at the type level. Optional/non-indexed, following every prior field added to this table since v1 — no Dexie `version()` bump. `src/storage/mapping.ts` gained `isRideSessionKind` (mirrors `isEditCopyOperation`'s exact `value === "..."` shape) and exported `resolveStoredRideSessionKind(stored): RideSessionKind | "unsupported"`. `toStoredRideState(...)` now hardcodes `kind: "route"` in its returned object literal — no new parameter, since it remains the sole writer and only ever writes route sessions today; its signature and its one call site (the persistence effect in `useRideNavigation.ts`) are byte-identical.
    - **A deliberate deviation from this file's own usual corrupt-value convention.** Every other closed-string-union field on this table (`editCopyOperation`, `elevationViewMode`'s tag, `sortOrder`) defaults a corrupt or unrecognised value to a concrete fallback via `isX(value) ? value : default`. `resolveStoredRideSessionKind` does not: `undefined` (a legacy row) resolves to `"route"` — the only kind this table has ever held, so this is the correct legacy default — but a **present-but-unrecognised** value (a future kind from a newer app version, or a corrupted row) resolves to a distinct `"unsupported"` outcome, never silently to `"route"`. Reasoning: unlike `editCopyOperation` (a closed, cosmetic, two-value field whose absence has exactly one proven past meaning and never gates a differently-shaped read), `kind` is a discriminant this project already knows it will widen (item 42) to a variant carrying different, route-incompatible fields (no meaningful `routeId`). Defaulting an unrecognised value to `"route"` here would let the launcher confidently call `getRoute(stored.routeId)` on a row whose actual shape it cannot interpret — wrong in a way that actively misleads the rider, not merely cosmetically wrong. The launcher treats `"unsupported"` exactly like a route that no longer resolves: explain that the session can't be recovered by this version of the app, offer only a confirmed discard, never a Resume action.
    - **The launcher.** A new, self-contained `src/ui/riding/RidingLauncher.tsx` replaces the previous inline empty-state `<section>` in `App.tsx` — it imports `getActiveRideState`/`getRoute`/`clearActiveRideState`/`resolveStoredRideSessionKind` directly (no DI props for storage functions, matching every sibling screen's convention; its own tests use real Dexie/fake-indexeddb plus targeted `vi.spyOn` for failure injection, never `vi.mock`). It owns its own hydration state machine, mirroring `PlanningScreen.tsx`'s established `"loading" | "ready" | "failed"` + generation-ref + retry-token pattern exactly, but as a two-step async function inside the effect (read the ride-state row, then conditionally read the route it references) rather than a `.then()` chain, since the second read depends on the first's result. Never renders the "no session" state while the read is merely unresolved (a restrained `role="status"` "Checking for an unfinished ride…" message covers that gap); a genuine read failure shows an accessible `role="alert"` message plus Retry, never falsely "no session" and never any deletion.
    - **Three resolved states**, `type RidingLauncherSessionState = { status: "none" } | { status: "resumable"; route: PlannedRoute } | { status: "unresumable"; reason: "route-missing" | "unsupported-kind" }`: no active row shows the pre-existing, byte-identical "No route selected yet…" copy plus **Choose a route**; a resumable route session shows the route's name and a `.route-card-meta` distance/ascent line, plus **Resume route** (deliberately not "Resume riding" — that label is reserved for `RidingScreen`'s own pre-ride recovery panel, and a future free-roam session could also be "resumed") and a danger **End ride**; an unresumable session (route deleted, or an unrecognised/unsupported kind) explains the problem and offers only a danger **Discard unfinished ride**, never a Resume action. `Resume route` calls the new `onResumeRoute(route)` prop and never starts geolocation itself — `RidingScreen`'s own pre-ride panel still gates the GPS watch behind its own explicit "Resume riding" tap.
    - **End ride and Discard unfinished ride share one internal mechanism**, `performClearSession(action: "end-ride" | "discard-unfinished")`, parameterised exactly like `RidingScreen.tsx`'s own `performFinalizeRide(source)` via a small per-action copy lookup table (dialog title/message/confirm label/pending label/error message/log context) — since the two actions are mutually exclusive per resolved state, one shared `ConfirmDialog` instance suffices. It calls `clearActiveRideState()` **directly**, deliberately not via `useRideNavigation.finish()`: `finish()`'s only logic beyond the storage clear is resetting hook-local React state (GPS watch, camera, wake lock, completion tracker), none of which has any launcher analogue since `RidingScreen` was never mounted for an unresumed session — constructing `useRideNavigation(route, ...)` merely to call `.finish()` on it would be architecturally backwards and is outright impossible for the route-missing case (no `PlannedRoute` exists there at all). `clearActiveRideState()` itself remains the single function that ever touches `db.rideState.delete(...)` — both call sites reuse it, satisfying "one authoritative clear path" without a second raw Dexie access point. A synchronous `isClearActionPendingRef` guards rapid double submission, mirroring `isFinalizeActionPendingRef`. Cancel and Escape both preserve the row and restore focus to the trigger; a storage-clear failure preserves the row, shows an accessible retryable error, and restores focus via a `useEffect` keyed on the error's own object identity — not a direct `.focus()` call inside the `catch` block, since the trigger is still `disabled` in the DOM at that exact synchronous point (the same real, previously-documented disabled-focus hazard `RidingScreen.tsx`'s own `performFinalizeRide` already guards against).
    - **Finalisation integration.** `RidingScreenProps` gained `onRideFinalized?: () => void`, called as the last statement of `performFinalizeRide`'s try block — after `nav.finish()` has already cleared persisted state and this screen's own existing runtime cleanup (`camera.resetCamera()`, `completion.reset()`, `setReachedManoeuvreIndex(0)`, closing the confirmation dialog) has already applied, so it fires only once finalisation has fully, successfully completed. Wrapped in its own **nested** `try { onRideFinalized?.(); } catch (callbackError) { logError("riding-ride-finalized-callback", callbackError); }`, deliberately separate from the outer catch: by the time this line runs, storage is already cleared, so a throw here left in the outer try would show the existing "The ride could not be ended on this device. Try again." message — a lie, since finalisation already succeeded — while leaving it fully unguarded would surface as an unhandled promise rejection at the `void performFinalizeRide(...)` call site. The nested catch avoids both failure modes and still logs the bug via the existing diagnostics mechanism. `App.tsx` gained `handleResumeRoute(route)` (`setSelectedRoute(route); setScreen("riding"); notifyNewRideContent();` — deliberately **not** capturing `window.scrollY` into `routesScrollYRef` the way `handleOpenRoute` does, since the rider is already on the Ride screen, not Routes, when this fires, and capturing the launcher's own scroll offset here would wrongly overwrite the Routes-restore ref) and `handleRideFinalized()` (`setSelectedRoute(null); notifyNewRideContent();` — the sole point that unmounts `RidingScreen` and mounts `RidingLauncher` in its place; `screen` stays `"riding"` throughout, and the existing `useResetScrollForNewRideContent` token-bump mechanism is reused unchanged to land the launcher at the top of the document). `isRidingActive` reverts to `false` for free via `RidingScreen`'s own existing unmount-driven `onRidingActiveChange` cleanup the instant `selectedRoute` clears and React swaps the conditional's rendered element — no new wiring needed, confirmed by a dedicated App-level test asserting the header returns to sticky.
    - **Failure semantics, held throughout.** The success callback never fires on cancellation, Escape, a genuine storage failure, or a duplicate/re-entrant submission — each of those paths leaves the same route selected and the ride active/resumable, with all of `performFinalizeRide`'s existing focus-restoration/retry semantics untouched. An ordinary nav-tab change, PWA suspension, reload, transient GPS error, or "Try again" never clears `selectedRoute` or persisted state — only a genuinely successful End/Finish transition reaches `onRideFinalized`.
    - **Tests.** `src/storage/mapping.test.ts` (`toStoredRideState` always writes `kind: "route"`; `resolveStoredRideSessionKind` for absent/recognised/unrecognised values) and `src/storage/db.migration.test.ts` (a legacy `rideState` row without `kind` loads cleanly with no schema version bump; a row with `kind: "route"` round-trips) prove the storage layer.     - **Evidence-backed root cause**, confirmed by direct reading of `src/navigation/projection.ts` and independently re-verified with real numeric arithmetic run against the installed `@turf/nearest-point-on-line`: `projectFixOntoRoute` first searches a `WINDOW_RADIUS_METRES` (400 m) route-distance window around `lastMatch` — the mechanism that correctly disambiguates loops, self-intersections and out-and-back sections — and only falls back to a whole-route search when the windowed match is rejected by `isClippedAtEdge` as sitting at a clipped edge of that window. Near a closed loop's finish, `lastMatch.distanceFromStartMetres ≈ total`, so the window `[total − 400, total]` (there is nothing beyond the route's own total distance) is clipped only on its lower side; its upper side naturally reaches the route's own genuine, un-clipped final point.       function isClippedAtEdge(
      ```ts
        match: NearestMatch,
        range: IndexRange,
        pointCount: number,
      ): boolean {
        const clippedAtStart =
          range.startIndex > 0 && match.pointIndex <= range.startIndex;
        const clippedAtEnd =
          range.endIndex < pointCount - 1 && match.pointIndex >= range.endIndex - 1;
        return clippedAtStart || clippedAtEnd;
      }
      ```
